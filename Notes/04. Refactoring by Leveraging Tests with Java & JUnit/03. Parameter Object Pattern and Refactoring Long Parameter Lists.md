# Introduction

The **Parameter Object** is a refactoring technique used to address the **Long Parameter List** code smell.

A method becomes difficult to understand and maintain when it requires many parameters, especially when several parameters are related to each other.

This lesson focuses on:

- Identifying the **Long Parameter List** code smell.    
- Introducing **Parameter Objects** to group related parameters.
- Reordering parameters for better readability.
- Providing sensible default values.
- Improving test readability.
- Applying the **TDD Red → Green → Refactor** cycle.
- Using Java and **JUnit 5** to safely refactor existing code.

> [!NOTE]  
> A Parameter Object is a class that groups multiple related parameters into a single object, allowing a method to accept one meaningful object instead of many individual values.

---

# Long Parameter Lists as a Code Smell

A **Long Parameter List** occurs when a method requires an excessive number of parameters.

For example:

```java
public ExamResult processExamScore(
    double examScore,
    boolean isHomeworkComplete,
    int attendanceScore,
    List<String> bonusActivities,
    double examWeight,
    double homeworkWeight,
    double attendanceWeight,
    int bonusPointsPerActivity,
    double passingThreshold,
    boolean isRetake,
    String courseCode
) {
    // Method implementation...
}
```

This method requires **11 parameters**.

Even though each parameter is valid individually, the overall method signature is difficult to understand.

---

## Problems with Long Parameter Lists

### 1. Readability

It can be difficult to understand what each argument represents.

For example:

```java
processExamScore(85, true, 3, activities, 0.7, 0.1, 0.1, 2, 75, false, "MATH101");
```

A reader has to look at the method definition to understand what `0.7`, `0.1`, `2`, and `75` represent.

---

### 2. Maintainability

Adding or removing a parameter requires changes to:

- The method declaration.
- Existing method calls.
- Tests.
- Potentially many callers throughout the application.

This increases the chance of introducing bugs.

---

### 3. Parameter Ordering Errors

Parameters with similar types can easily be passed in the wrong order.

For example:

```java
processExamScore(
    0.7,
    0.1,
    0.1
);
```

If all three values are `double`, the compiler cannot detect that they were accidentally swapped.

The code may compile but produce incorrect results.

---

### 4. Testing Challenges

Long parameter lists make tests verbose and difficult to understand.

Example:

```java
ExamResult result = examProcessor.processExamScore(
    85,
    true,
    3,
    Arrays.asList("extra_credit", "participation"),
    0.7,
    0.1,
    0.1,
    2,
    75,
    false,
    "MATH101"
);
```

The test contains many values, but the purpose of those values is not immediately obvious.

---

### 5. Lack of Cohesion

A large number of parameters can indicate that several parameters naturally belong together.

For example:

```text
examWeight
homeworkWeight
attendanceWeight
```

are all related to **score weighting**.

Similarly:

```text
bonusPointsPerActivity
passingThreshold
isRetake
```

can represent **course scoring/policy configuration**.

When related values repeatedly appear together, they may be candidates for a Parameter Object.

Consider the following method:

```java
public ExamResult processExamScore(
    double examScore,
    boolean isHomeworkComplete,
    int attendanceScore,
    List<String> bonusActivities,
    double examWeight,
    double homeworkWeight,
    double attendanceWeight,
    int bonusPointsPerActivity,
    double passingThreshold,
    boolean isRetake,
    String courseCode
) {
    // Method implementation...
}
```

The method mixes several types of information:

### Course information

```text
courseCode
```

### Individual performance

```text
examScore
isHomeworkComplete
attendanceScore
bonusActivities
isRetake
```

### Scoring configuration

```text
examWeight
homeworkWeight
attendanceWeight
```

### Course policy

```text
bonusPointsPerActivity
passingThreshold
```

The method signature therefore contains several different concepts.

# Confusing Test

The original test might look like:

```java
public class ExamProcessorTest {

    @Test
    public void calculatesMaximumScoreWithCompletedHomework() {
        ExamProcessor examProcessor = new ExamProcessor();

        ExamResult result = examProcessor.processExamScore(
            85,
            true,
            3,
            Arrays.asList("extra_credit", "participation"),
            0.7,
            0.1,
            0.1,
            2,
            75,
            false,
            "MATH101"
        );

        assertEquals(100, result.getFinalScore());
    }
}
```

The test works, but it has a high **cognitive load**.

For example, it isn't immediately obvious what this means:

```java
0.7
```

or:

```java
75
```

A developer must look at the method definition to understand the test.

# Refactoring with Parameter Objects

The solution is to group related parameters into objects.

For example:

```text
ScoreWeights
├── examWeight
├── homeworkWeight
└── attendanceWeight

CoursePolicy
├── bonusPointsPerActivity
└── passingThreshold
```

The method can then accept these objects instead of individual configuration values.

---

## Refactored Method

```java
public ExamResult processExamScore(
    String courseCode,

    // Individual Performance
    double examScore,
    boolean isHomeworkComplete,
    int attendanceScore,
    List<String> bonusActivities,
    boolean isRetake,

    // Configuration
    ScoreWeights scoreWeights,
    CoursePolicy coursePolicy
) {
    if (bonusActivities == null) {
        bonusActivities = new ArrayList<>();
    }

    if (scoreWeights == null) {
        scoreWeights = getDefaultScoreWeights();
    }

    if (coursePolicy == null) {
        coursePolicy = getDefaultCoursePolicy();
    }

    // Implementation
}
```

The method now has fewer parameters and the parameters have a clearer structure.

---

# Parameter Object

A **Parameter Object** encapsulates several related parameters into a single object.

For example:

```text
ScoreWeights
    │
    ├── examWeight
    ├── homeworkWeight
    └── attendanceWeight
```

Instead of:

```java
double examWeight,
double homeworkWeight,
double attendanceWeight
```

the method receives:

```java
ScoreWeights scoreWeights
```

This makes the relationship between the values explicit.

---

# Reordering Parameters

Another improvement is to **reorder parameters logically**.

Instead of randomly mixing parameters:

```java
double examScore,
boolean isHomeworkComplete,
int attendanceScore,
...
String courseCode
```

the refactored method starts with the course:

```java
String courseCode
```

followed by individual performance information:

```java
double examScore,
boolean isHomeworkComplete,
int attendanceScore,
List<String> bonusActivities,
boolean isRetake
```

and then configuration:

```java
ScoreWeights scoreWeights,
CoursePolicy coursePolicy
```

This creates a logical grouping:

```text
Course
   ↓
Individual Performance
   ↓
Configuration
```

---

# Defaults

The refactored method can also provide sensible defaults.

For example:

```java
if (bonusActivities == null) {
    bonusActivities = new ArrayList<>();
}
```

This means the caller doesn't necessarily need to provide an empty list.

Similarly:

```java
if (scoreWeights == null) {
    scoreWeights = getDefaultScoreWeights();
}
```

and:

```java
if (coursePolicy == null) {
    coursePolicy = getDefaultCoursePolicy();
}
```

provide default configuration when none is supplied.

> [!IMPORTANT]  
> Java does not have native default parameter values like some other languages. Defaults are commonly implemented through overloaded methods, constructors, builders, or explicit handling such as the example above.

---

# Less Confusing Test

After the refactoring, a test can become much simpler:

```java
public class ExamProcessorTest {

    @Test
    public void calculatesMaximumScoreWithCompletedHomework() {
        ExamProcessor examProcessor = new ExamProcessor();

        ExamResult result =
            examProcessor.processExamScore("MATH101", 100);

        assertEquals(100, result.getFinalScore());
    }
}
```

The intent is now much clearer.

The reader immediately understands:

```text
Course = MATH101
Exam Score = 100
```

Instead of having to interpret a long sequence of values.

# Before vs After

|Aspect|Before|After|
|---|---|---|
|Method parameters|Many individual parameters|Related values grouped into objects|
|Readability|Difficult|Improved|
|Parameter ordering|Easy to get wrong|Reduced risk|
|Configuration|Scattered parameters|`ScoreWeights`, `CoursePolicy`|
|Test readability|Low|High|
|Maintainability|Difficult|Easier|
|Defaults|Difficult to manage|Can be centralized|
|Cohesion|Low|Related data grouped together|

# When to Use a Parameter Object

A Parameter Object is particularly useful when:

- A method has many parameters.
- Several parameters are logically related.
- The same group of parameters appears in multiple methods.
- Parameters are frequently added or removed together.
- Method calls are difficult to understand.
- Tests contain many confusing arguments.

For example, an e-commerce application might have:

```text
PaymentDetails
├── cardNumber
├── expiryDate
├── billingAddress
└── paymentMethod
```

Instead of passing all of these separately:

```java
processPayment(
    cardNumber,
    expiryDate,
    billingAddress,
    paymentMethod
);
```

the method can accept:

```java
processPayment(PaymentDetails paymentDetails);
```

---

# Parameter Object vs Alternatives

A Parameter Object is not always the best solution.

Consider alternatives when appropriate:

|Situation|Possible Solution|
|---|---|
|Related parameters|Parameter Object|
|Optional configuration|Builder pattern|
|Small number of optional values|Overloaded methods|
|Complex object construction|Builder|
|Parameters don't naturally belong together|Keep them separate|

The key is that the parameters should have a **meaningful relationship** before grouping them into an object.

# TDD and Refactoring

This exercise follows the **Red → Green → Refactor** cycle.

## Red

Start with a test that describes the expected behavior.

```text
Test fails
   ↓
Identify required behavior
```

## Green

Implement the minimum change necessary to make the test pass.

```text
Test passes
```

## Refactor

Improve the design without changing the expected behavior.

For this lesson:

```text
Long parameter list
        ↓
Group related parameters
        ↓
Create Parameter Objects
        ↓
Reorder parameters
        ↓
Add sensible defaults
        ↓
Run tests
```

The existing tests provide a safety net while the method signature and supporting classes are changed.

```text
        ▼
Identify related parameters
        │
        ▼

        │
        ▼
Group related values
        │
        ▼

        │
        ▼

```

---

> [!TIP]  
> **Rule of thumb:** Don't create a Parameter Object simply because a method has several parameters. Create one when multiple parameters represent a cohesive concept and benefit from being treated as a single unit.

# Key Takeaways

- **Long Parameter List** is a common code smell.
- Too many parameters reduce readability and maintainability.
- Parameters with similar types can easily be passed in the wrong order.
- Long parameter lists make tests harder to understand and maintain.
- A **Parameter Object** groups related parameters into a meaningful class.
- `ScoreWeights` is an example of a Parameter Object for scoring configuration.
- `CoursePolicy` is an example of a Parameter Object for course rules.
- Reordering parameters can make a method signature easier to understand.
- Sensible defaults can reduce unnecessary arguments.
- Parameter Objects are especially useful when related parameters frequently appear together.
- Always consider whether the parameters actually form a cohesive concept before introducing a Parameter Object.
- Use the **Red → Green → Refactor** cycle to safely improve the design without changing behavior.
