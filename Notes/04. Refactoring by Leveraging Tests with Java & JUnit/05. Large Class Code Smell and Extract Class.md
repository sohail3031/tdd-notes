# Introduction

In this final lesson, we focus on a common code smell: the **Large Class**.

Throughout the course, we have used the **TDD Red-Green-Refactor cycle** to guide improvements to code structure while preserving existing behavior.

A Large Class often indicates that a class has accumulated too many responsibilities. This makes the code harder to understand, maintain, test, and reuse.

The **Extract Class** refactoring pattern can be used to break a large class into smaller, more focused classes.

### Main Goal

> Break large, multi-responsibility classes into smaller, cohesive classes with clear responsibilities.

---

# Understanding the Large Class Code Smell

A **Large Class** occurs when a class accumulates too many responsibilities, resulting in excessive size and complexity.

A large class may contain:

- Too many methods
- Too many properties
- Multiple unrelated responsibilities
- Complex conditional logic
- Dependencies on many other parts of the system

This often indicates that the class should be refactored.

---

## Problems Caused by Large Classes

### 1. Reduced Maintainability

When multiple responsibilities are combined into one class, understanding and modifying the code becomes more difficult.

A change to one part of the class can unintentionally affect another responsibility.

For example:

```text
LargeClass
├── User management
├── Payment processing
├── Email notifications
├── Reporting
└── Data transformation
````

A change to payment processing may accidentally affect unrelated functionality.

---

### 2. Poor Readability

Large classes can become difficult to read because developers must understand a large amount of code before they can understand the class's purpose.

Instead of having a clear responsibility:

```text
PaymentProcessor
└── Payment processing
```

a large class may contain:

```text
ApplicationService
├── User management
├── Payment processing
├── Reporting
├── Notifications
└── Data processing
```

This makes the design harder to understand.

---

### 3. Violation of the Single Responsibility Principle

The **Single Responsibility Principle (SRP)** states:

> A class should have one reason to change.

A Large Class often has multiple reasons to change because it handles multiple responsibilities.

For example:

```text
ShoppingCart
├── Item management
├── Pricing
├── Discounts
└── Shipping
```

These responsibilities can change independently.

A better design could be:

```text
ShoppingCart
├── CartItemCollection
├── PriceCalculator
├── DiscountCalculator
└── ShippingCalculator
```

Each class now has a more focused responsibility.

---

### 4. Testing Challenges

Large classes can be difficult to test because they often contain many interdependent behaviors.

Tests may become:

- Large
- Difficult to understand
- Difficult to isolate
- Difficult to maintain

Extracting responsibilities into smaller classes makes it easier to test each responsibility independently.

---

# Recognizing a Large Class

There is no single number of lines that automatically makes a class "large."

Instead, look for multiple warning signs.

## 1. Excessive Line Count

A class containing hundreds or thousands of lines may indicate that it has accumulated too many responsibilities.

However, line count alone is not enough to determine whether a class needs refactoring.

The more important question is:

> Does the class contain multiple unrelated responsibilities?

---

## 2. Numerous Methods and Properties

A class containing many methods and fields may indicate that different responsibilities have been combined.

For example:

```text
Customer
├── Personal information
├── Address management
├── Payment processing
├── Order management
├── Email notifications
└── Reporting
```

This is a warning sign that responsibilities may need to be extracted.

---

## 3. Multiple Responsibilities

Look at the methods and group them according to what they do.

For example:

```text
ShoppingCart
├── addItem()
├── removeItem()
├── updateQuantity()
│
├── calculatePrice()
├── calculateTax()
│
├── applyDiscount()
│
└── calculateShipping()
```

These methods can be grouped into different responsibility areas:

```text
Item Management
├── addItem()
├── removeItem()
└── updateQuantity()

Pricing
├── calculatePrice()
└── calculateTax()

Discounts
└── applyDiscount()

Shipping
└── calculateShipping()
```

These groups are candidates for extraction into separate classes.

---

## 4. Complex Conditional Logic

Large classes frequently contain complex conditional logic because they are responsible for many different scenarios.

For example:

```java
if (type.equals("PREMIUM")) {
    // ...
} else if (type.equals("STUDENT")) {
    // ...
} else if (type.equals("BUSINESS")) {
    // ...
}
```

When a class contains many such branches related to different responsibilities, extracting those responsibilities can simplify the design.

---

## 5. Difficulty Reusing Functionality

A large class may be difficult to reuse because its functionality is tightly coupled to unrelated responsibilities.

For example, if pricing logic is buried inside `ShoppingCart`, another part of the application that needs the same pricing rules may be forced to depend on the entire `ShoppingCart`.

Extracting:

```text
PriceCalculator
```

makes the pricing functionality easier to reuse independently.

---

# Common Anti-Patterns Associated with Large Classes

## God Object

A **God Object** is a class that knows too much or does too much within the system.

Example:

```text
ApplicationManager
├── Users
├── Orders
├── Payments
├── Notifications
├── Reports
├── Authentication
└── Database operations
```

This class becomes difficult to understand and maintain because it controls too many areas of the application.

---

## Multifaceted Abstraction

A class may represent several unrelated concepts at the same time.

For example:

```text
Employee
├── Employee information
├── Payroll calculations
├── Email notifications
└── Performance reports
```

These concerns could potentially be separated into focused classes.

---

## Shotgun Surgery

**Shotgun Surgery** occurs when one small change requires modifications across many different parts of the codebase.

For example, changing one business rule might require modifying:

```text
Class A
Class B
Class C
Class D
Class E
```

A well-organized design can centralize related behavior so that changes are easier to make.

---

# Single Responsibility Principle

The **Single Responsibility Principle (SRP)** is one of the main principles used when refactoring Large Classes.

A common interpretation of SRP is:

> A class should have only one reason to change.

This does **not** necessarily mean that a class can have only one method.

Instead, its methods and properties should belong to a cohesive responsibility.

### Poor Cohesion

```text
ShoppingCart
├── addItem()
├── calculatePrice()
├── sendEmail()
├── calculateShipping()
└── generateReport()
```

There are several unrelated reasons this class could change.

### Better Cohesion

```text
ShoppingCart
└── Item management

PriceCalculator
└── Price calculations

NotificationService
└── Notifications

ShippingCalculator
└── Shipping calculations

ReportGenerator
└── Reports
```

Each class now has a clearer purpose.

# Extract Class Refactoring

**Extract Class** is a refactoring technique used when a class contains a group of responsibilities that can be moved into a separate class.

The general transformation is:

```text
Before:

LargeClass
├── Responsibility A
├── Responsibility B
├── Responsibility C
└── Responsibility D
```

After:

```text
OriginalClass
└── Responsibility A

NewClass
├── Responsibility B
├── Responsibility C
└── Responsibility D
```

The original class can then delegate responsibility to the new class.

---

# Steps for Refactoring a Large Class

## Step 1: Identify Responsibility Segments

Analyze the large class and group related properties and methods.

For example, a `ShoppingCart` might contain:

```text
Item Management
├── addItem()
├── removeItem()
└── updateItemQuantity()

Pricing
├── calculatePrice()
└── calculateTax()

Discounts
└── applyDiscount()

Shipping
└── calculateShipping()
```

These groups are potential candidates for extraction.

---

## Step 2: Define Cohesive Units

For each responsibility group, determine whether it makes sense as a separate class.

For example:

```text
CartItemCollection
PriceCalculator
DiscountCalculator
ShippingCalculator
```

The class names should clearly communicate their responsibilities.

---

## Step 3: Move Properties and Methods

Move the fields and methods associated with the extracted responsibility into the new class.

For example:

```java
public class CartItemCollection {

    private List<CartItem> items;

    public void addItem(CartItem item) {
        items.add(item);
    }

    public void removeItem(CartItem item) {
        items.remove(item);
    }

    public void updateItemQuantity(CartItem item, int quantity) {
        item.setQuantity(quantity);
    }
}
```

The new class now owns the item-management responsibility.

---

## Step 4: Refactor Calls and Dependencies

The original class should use the new class instead of implementing the extracted functionality itself.

For example:

```java
public class ShoppingCart {

    private CartItemCollection items;

    public ShoppingCart() {
        this.items = new CartItemCollection();
    }

    public void addItem(CartItem item) {
        items.addItem(item);
    }
}
```

`ShoppingCart` delegates item management to `CartItemCollection`.

---

## Step 5: Reassess the Original Class

After extracting the responsibility, examine the original class again.

Ask:

- Does it still have a clear responsibility?
- Are the remaining methods cohesive?
- Can more responsibilities be extracted?
- Are the dependencies reasonable?
- Is the class easier to understand?

Refactoring is iterative. One extraction can reveal another opportunity for improvement.

---

# Example: Shopping Cart

## Before

```text
ShoppingCart
├── items
├── addItem()
├── removeItem()
├── updateItemQuantity()
├── calculatePrice()
├── calculateTax()
├── applyDiscount()
└── calculateShipping()
```

The class handles several different responsibilities.

---

## After

```text
ShoppingCart
│
├── CartItemCollection
│   ├── addItem()
│   ├── removeItem()
│   └── updateItemQuantity()
│
├── PriceCalculator
│   ├── calculatePrice()
│   └── calculateTax()
│
├── DiscountCalculator
│   └── applyDiscount()
│
└── ShippingCalculator
    └── calculateShipping()
```

The resulting design separates responsibilities into focused classes.

# TDD and Large Class Refactoring

TDD provides a safety net when performing refactoring.

The cycle remains:

```text
RED
 ↓
Write/fix tests for the existing behavior
 ↓
GREEN
 ↓
Confirm tests pass
 ↓
REFACTOR
 ↓
Extract responsibilities
 ↓
Run tests
 ↓
GREEN
```

The key principle is:

> **Change the design without changing the behavior.**

For example, when extracting `StudentGradeCollection`, tests that previously called:

```java
student.calculateFinalGrade();
```

can continue to call the same method.

The internal implementation changes:

```text
Before:

student.calculateFinalGrade()
        ↓
Student calculates grade


After:

student.calculateFinalGrade()
        ↓
StudentGradeCollection.calculateFinalGrade()
```

The externally observable behavior remains the same.

---

# Testing Extracted Classes

After extracting a responsibility, the new class should also have focused unit tests.

For example, `CartItemCollection` could have tests for:

```text
addItem()
removeItem()
updateItemQuantity()
```

Similarly, `StudentGradeCollection` could have tests for:

```text
addGrade()
calculateFinalGrade()
getFailedAssignments()
```

This creates smaller, more focused test suites.

# Benefits of Extract Class

Applying Extract Class to a Large Class can provide several benefits:

### Maintainability

Smaller classes are easier to modify.

### Readability

Each class has a clearer purpose.

### Testability

Responsibilities can be tested independently.

### Reusability

Focused functionality can potentially be reused elsewhere.

### Cohesion

Related behavior and data stay together.

### Reduced Coupling

Classes depend on focused abstractions rather than one large class.

### Easier Future Changes

Changes to one responsibility are less likely to affect unrelated functionality.

---

# Important Consideration

A class is not automatically bad because it has many lines or methods.

The real question is whether its responsibilities are **cohesive**.

For example, a class with many methods may still have one clear responsibility:

```text
StringParser
├── parse()
├── parseInteger()
├── parseDate()
├── parseBoolean()
└── parseList()
```

These methods may all belong to the same conceptual responsibility.

Therefore:

> **Do not split classes simply to make them smaller. Split them when their responsibilities are distinct and cohesive groups can be extracted.**

---

# Refactoring Checklist

When encountering a potentially Large Class:

-  Identify the class's responsibilities.
-  Group related fields and methods.
-  Look for unrelated responsibilities.
-  Identify cohesive groups that could become classes.
-  Choose meaningful names for extracted classes.
-  Move related fields and methods.
-  Update dependencies and method calls.
-  Keep the public behavior stable where possible.
-  Run existing tests.
-  Add focused tests for extracted responsibilities.
-  Reassess the original class.
-  Look for additional refactoring opportunities.

---

# Summary

The **Large Class** code smell occurs when a class accumulates too many responsibilities.

Common symptoms include:

- Excessive size
- Too many methods and properties
- Multiple unrelated responsibilities
- Complex conditional logic
- Difficult testing
- Poor reuse

The **Extract Class** refactoring helps address this problem by moving a cohesive group of responsibilities into a new class.

The process is:

```text
Identify responsibilities
        ↓
Group related behavior
        ↓
Create focused class
        ↓
Move properties and methods
        ↓
Update dependencies
        ↓
Run tests
        ↓
Reassess the design
```

The **Single Responsibility Principle** provides a useful guideline:

> A class should have one reason to change.
