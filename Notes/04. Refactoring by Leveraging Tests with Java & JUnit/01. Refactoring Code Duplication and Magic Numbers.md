# Code Smells

Before discussing specific refactoring techniques, it is important to understand **code smells**.

A code smell is an indicator that there may be a deeper problem in the code. A code smell is not necessarily a bug, but it often suggests that the code could be improved.

Common code smells include:

- Duplicate code.
- Long methods.
- Large classes.
- Magic numbers.
- Complex conditional logic.

Code smells can make code:

- Harder to read.
- Harder to maintain.
- More difficult to modify.
- More likely to contain bugs in the future.

## Eliminating Code Smells

Refactoring patterns provide structured techniques for improving problematic code while preserving its existing behavior.

In this lesson, we focus on two refactoring techniques:

1. **Extract Method** — Remove duplicated logic by moving it into a reusable method.
2. **Replace Magic Numbers with Constants** — Replace unexplained numeric values with meaningful constants.

An important advantage of working with TDD is that the existing test suite gives us confidence during refactoring.

> If the tests continue to pass after refactoring, we can be more confident that the application's behavior has not changed.

# Code Duplication

## What Is Code Duplication?

**Code duplication** is a code smell that occurs when similar or identical logic appears in multiple places in a codebase.

Duplicate code creates maintenance problems because changes must be made in multiple locations.

For example:

```text
Change required
      ↓
Same logic exists in multiple places
      ↓
Multiple locations must be updated
      ↓
One location may be forgotten
      ↓
Inconsistent behavior or bugs
```

This increases the risk of errors and makes the code more difficult to maintain.

---

# The DRY Principle

The **DRY principle** stands for:

> **Don't Repeat Yourself**

The idea behind DRY is that each piece of knowledge or business logic should have a single, clear representation within the system.

Benefits include:

- Improved maintainability.    
- Reduced duplication.
- Fewer opportunities for inconsistent behavior.
- Easier debugging.
- Easier future modifications.

Refactoring duplicate code supports the DRY principle and fits naturally into the **Refactor** stage of TDD.

# Example: Identifying Duplicate Code

Consider the following `ShoppingCart` implementation.

```java
import java.util.ArrayList;
import java.util.List;

public class ShoppingCart {

    private List<CartItem> items = new ArrayList<>();

    public void addItem(String name, double price, int quantity) {
        items.add(new CartItem(name, price, quantity));
    }

    public double calculateTotal() {
        double total = 0;

        for (CartItem item : items) {
            double itemTotal = item.getPrice() * item.getQuantity();

            if (item.getQuantity() >= 5) {
                itemTotal *= 0.9; // 10% discount
            }

            total += itemTotal;
        }

        return total;
    }

    public double calculateTotalWithStudentDiscount() {
        double total = 0;

        for (CartItem item : items) {
            double itemTotal = item.getPrice() * item.getQuantity();

            if (item.getQuantity() >= 5) {
                itemTotal *= 0.9; // 10% discount
            }

            total += itemTotal;
        }

        // Apply student discount
        return total * 0.85; // 15% student discount
    }
}
```

## The Problem

The following logic appears in both methods:

```java
double total = 0;

for (CartItem item : items) {
    double itemTotal = item.getPrice() * item.getQuantity();

    if (item.getQuantity() >= 5) {
        itemTotal *= 0.9;
    }

    total += itemTotal;
}
```

This is duplicated code.

If the bulk discount logic changes, both methods must be updated.

For example, if the discount threshold changes from `5` to `10`, the change must be made in multiple places.

This violates the **DRY principle**.

---

# Refactoring with Extract Method

## Extracting Common Logic

The duplicated logic can be moved into a separate method.

This technique is called **Extract Method**.

The extracted method can then be reused by multiple methods.

In this example, we create:

```java
private double calculateSubtotal()
```

This method contains the common logic for calculating the total cost of all items.

---

# Refactored Implementation

```java
import java.util.ArrayList;
import java.util.List;

public class ShoppingCart {

    private List<CartItem> items = new ArrayList<>();

    public void addItem(String name, double price, int quantity) {
        items.add(new CartItem(name, price, quantity));
    }

    private double calculateSubtotal() {
        double total = 0;

        for (CartItem item : items) {
            double itemTotal = item.getPrice() * item.getQuantity();

            if (item.getQuantity() >= 5) {
                itemTotal *= 0.9; // 10% discount
            }

            total += itemTotal;
        }

        return total;
    }

    public double calculateTotal() {
        return calculateSubtotal();
    }

    public double calculateTotalWithStudentDiscount() {
        double subtotal = calculateSubtotal();

        // Apply student discount
        return subtotal * 0.85; // 15% student discount
    }
}
```

---

# Benefits of Method Extraction

The refactored implementation provides several benefits.

## Before Refactoring

```text
calculateTotal()
    ↓
Duplicate calculation logic

calculateTotalWithStudentDiscount()
    ↓
Duplicate calculation logic
```

## After Refactoring

```text
calculateSubtotal()
       ↑
       │
       ├── calculateTotal()
       │
       └── calculateTotalWithStudentDiscount()
```

The calculation logic now has a **single source of truth**.

If the calculation rules change, only `calculateSubtotal()` needs to be modified.

# Magic Numbers

## What Are Magic Numbers?

A **magic number** is a numeric value that appears directly in code without clearly explaining its meaning.

Consider the following method:

```java
public static double calculateItemCost(CartItem item) {
    double itemTotal = item.getPrice() * item.getQuantity();

    if (item.getQuantity() >= 5) {
        itemTotal *= 0.9;
    }

    return itemTotal;
}
```

The numbers:

```text
5
0.9
```

are examples of magic numbers.

A developer reading the code may need to determine:

- Why is the quantity `5`?    
- What does `0.9` represent?
- Is `0.9` a 10% discount?
- Is this value used elsewhere?
- What should happen if the business rule changes?

---

# Problems with Magic Numbers

Magic numbers reduce code readability.

For example:

```java
if (item.getQuantity() >= 5)
```

does not clearly communicate why `5` is important.

Similarly:

```java
itemTotal *= 0.9;
```

does not immediately explain that the customer receives a **10% discount**.

Magic numbers also create maintenance problems when the same value appears in multiple locations.

---

# Refactoring Magic Numbers into Constants

The solution is to replace magic numbers with clearly named constants.

```java
public class ShoppingCart {

    private static final int BULK_DISCOUNT_THRESHOLD = 5;
    private static final double BULK_DISCOUNT_RATE = 0.9;

    public static double calculateItemCost(CartItem item) {
        double itemTotal =
                item.getPrice() * item.getQuantity();

        if (item.getQuantity() >= BULK_DISCOUNT_THRESHOLD) {
            itemTotal *= BULK_DISCOUNT_RATE;
        }

        return itemTotal;
    }
}
```

---

# Why Constants Improve Readability

Compare the following code.

## Before

```java
if (item.getQuantity() >= 5) {
    itemTotal *= 0.9;
}
```

## After

```java
if (item.getQuantity() >= BULK_DISCOUNT_THRESHOLD) {
    itemTotal *= BULK_DISCOUNT_RATE;
}
```

The second version communicates the business rule much more clearly.

```text
Quantity reaches bulk discount threshold
        ↓
Apply bulk discount rate
```

The constant names document the purpose of the values.

---

# Benefits of Replacing Magic Numbers

Using named constants provides several benefits:

- Improves code readability.    
- Makes business rules easier to understand.
- Creates a single location for changing values.
- Reduces the risk of inconsistent updates.
- Makes the code more self-documenting.

For example, if the bulk discount threshold changes from `5` to `10`, only one line needs to change:

```java
private static final int BULK_DISCOUNT_THRESHOLD = 10;
```

# Combining Method Extraction and Constants

The code can be improved further by extracting the item cost calculation into its own method.

```java
public class ShoppingCart {

    private static final int BULK_DISCOUNT_THRESHOLD = 5;
    private static final double BULK_DISCOUNT_RATE = 0.9;
    private static final double STUDENT_DISCOUNT_RATE = 0.85;

    private List<CartItem> items = new ArrayList<>();

    public void addItem(String name, double price, int quantity) {
        items.add(new CartItem(name, price, quantity));
    }

    private double calculateItemCost(CartItem item) {
        double itemTotal =
                item.getPrice() * item.getQuantity();

        if (item.getQuantity() >= BULK_DISCOUNT_THRESHOLD) {
            itemTotal *= BULK_DISCOUNT_RATE;
        }

        return itemTotal;
    }

    private double calculateSubtotal() {
        double total = 0;

        for (CartItem item : items) {
            total += calculateItemCost(item);
        }

        return total;
    }

    public double calculateTotal() {
        return calculateSubtotal();
    }

    public double calculateTotalWithStudentDiscount() {
        return calculateSubtotal() * STUDENT_DISCOUNT_RATE;
    }
}
```

This version provides better separation of responsibilities.

---

# Refactored Structure

```text
ShoppingCart
│
├── addItem()
│
├── calculateItemCost()
│       └── Calculates the cost of one item
│           including the bulk discount
│
├── calculateSubtotal()
│       └── Calculates the total cost of all items
│
├── calculateTotal()
│       └── Returns the subtotal
│
└── calculateTotalWithStudentDiscount()
        └── Applies the student discount
```

Each method now has a clear responsibility.

# Refactoring in the TDD Cycle

Refactoring is the third stage of the **Red-Green-Refactor** cycle.

## 🔴 Red

Write a failing test that defines the required behavior.

```text
Write Test
    ↓
Run Test
    ↓
Test Fails
```

---

## 🟢 Green

Write the minimum amount of code required to make the test pass.

```text
Implement Minimum Code
        ↓
Run Test
        ↓
Test Passes
```

---

## 🔵 Refactor

Improve the structure and readability of the code while ensuring that the behavior remains unchanged.

Examples include:

- Removing duplicated code.    
- Extracting methods.
- Renaming variables.
- Replacing magic numbers with constants.
- Simplifying conditional logic.

```text
Tests Passing
      ↓
Identify Code Smell
      ↓
Refactor Code
      ↓
Run Tests Again
      ↓
Tests Still Pass
```

The test suite acts as a safety net during refactoring.

---

# Important Rule During Refactoring

> **Refactoring should improve the internal structure of the code without changing its observable behavior.**

For example:

```text
Before Refactoring
        ↓
Existing tests pass
        ↓
Refactor implementation
        ↓
Run the same tests
        ↓
Tests still pass
```

If tests fail after refactoring, the refactoring may have unintentionally changed the application's behavior.
