# Introduction

In the previous lessons, we learned how to improve code quality by:

- Eliminating duplicated code through **method extraction**    
- Replacing **magic numbers** with meaningful constants

This lesson builds on those techniques by addressing another common **code smell: Long Methods**.

The goal is to use the **Extract Method** refactoring technique to break large, complex methods into smaller methods with focused responsibilities.

This follows the TDD workflow:

```text
Red → Green → Refactor
```

> [!IMPORTANT]  
> During the **Refactor** step, we improve the internal structure of the code without changing its behavior. Existing tests give us confidence that the behavior remains unchanged.

---

# Long Methods as a Code Smell

A **long method** is a method that contains too much logic or handles multiple responsibilities.

Long methods are difficult to:

- Understand
- Test
- Debug
- Maintain
- Reuse
- Modify safely

A method becomes especially problematic when it performs several unrelated tasks.

For example, a single method might:

1. Validate user information
2. Validate a date
3. Validate an address
4. Transform data
5. Store data
6. Handle errors

This violates the **Single Responsibility Principle (SRP)** because one method is responsible for too many things.

---

# Example: Long Method

Consider the following `processUserRegistration()` method:

```java
public class UserRegistrationService {
    private final IDataStore dataStore;

    public UserRegistrationService(IDataStore dataStore) {
        this.dataStore = dataStore;
    }

    public RegistrationResponse processUserRegistration(UserData userData) {
        try {
            // User validation
            if (userData.getUsername() == null || userData.getUsername().isBlank()
                || userData.getUsername().length() < 3
                || userData.getUsername().length() > 20) {
                return new RegistrationResponse(
                    false,
                    "Invalid username. Must be between 3 and 20 characters.",
                    null
                );
            }

            if (userData.getEmail() == null || userData.getEmail().isBlank()
                || !userData.getEmail().contains("@")
                || !userData.getEmail().contains(".")) {
                return new RegistrationResponse(
                    false,
                    "Invalid email format.",
                    null
                );
            }

            if (userData.getPassword() == null
                || userData.getPassword().isBlank()
                || userData.getPassword().length() < 8
                || !userData.getPassword().matches(".*[A-Z].*")
                || !userData.getPassword().matches(".*\\d.*")
                || !userData.getPassword().matches(".*[!@#$%^&*].*")) {
                return new RegistrationResponse(
                    false,
                    "Password must be at least 8 characters and contain uppercase, number, and special character.",
                    null
                );
            }

            // Date validation
            LocalDate birthDate = LocalDate.parse(userData.getDateOfBirth());
            LocalDate today = LocalDate.now();
            Period age = Period.between(birthDate, today);

            if (age.getYears() < 18 || age.getYears() > 120) {
                return new RegistrationResponse(
                    false,
                    "Invalid date of birth or user must be 18+",
                    null
                );
            }

            // Address validation
            Address address = userData.getAddress();

            if (address.getStreet() == null
                || address.getStreet().isBlank()
                || address.getStreet().length() < 5) {
                return new RegistrationResponse(
                    false,
                    "Invalid street address",
                    null
                );
            }

            if (address.getCity() == null
                || address.getCity().isBlank()
                || address.getCity().length() < 2) {
                return new RegistrationResponse(
                    false,
                    "Invalid city",
                    null
                );
            }

            if (address.getCountry() == null
                || address.getCountry().isBlank()
                || address.getCountry().length() < 2) {
                return new RegistrationResponse(
                    false,
                    "Invalid country",
                    null
                );
            }

            if (address.getPostalCode() == null
                || address.getPostalCode().isBlank()
                || !address.getPostalCode().matches("^[A-Z0-9]{3,10}$")) {
                return new RegistrationResponse(
                    false,
                    "Invalid postal code",
                    null
                );
            }

            // Data transformation
            String userId = "USER_"
                + UUID.randomUUID().toString().substring(0, 8);

            UserData normalizedData = new UserData(
                userData.getUsername().toLowerCase(),
                userData.getEmail().toLowerCase(),
                userData.getPassword(),
                birthDate.toString(),
                new Address(
                    address.getStreet().trim(),
                    address.getCity().trim(),
                    address.getCountry().toUpperCase(),
                    address.getPostalCode().toUpperCase()
                )
            );

            dataStore.store(normalizedData);

            return new RegistrationResponse(
                true,
                "User registered successfully",
                userId
            );

        } catch (Exception e) {
            return new RegistrationResponse(
                false,
                "Registration failed: " + e.getMessage(),
                ""
            );
        }
    }
}
```

---

# Responsibilities of the Long Method

The method is responsible for several different tasks.

| Responsibility      | What it does                                     |
| ------------------- | ------------------------------------------------ |
| User validation     | Validates username, email, and password          |
| Date validation     | Validates date of birth and age                  |
| Address validation  | Validates street, city, country, and postal code |
| Data transformation | Normalizes user information                      |
| Data storage        | Stores the normalized user data                  |
| Error handling      | Handles exceptions and creates error responses   |

This makes the method difficult to understand and maintain.

---

# Extract Method

The **Extract Method** refactoring technique takes a logical section of a large method and moves it into a separate method with a meaningful name.

Instead of:

```text
One large method
        ↓
Many responsibilities
```

we aim for:

```text
Main method
    ├── validateUser()
    ├── validateDate()
    ├── validateAddress()
    ├── transformData()
    └── storeData()
```

Each method should have a clear and focused responsibility.

---

# Step 1: Extract User Validation

The first logical responsibility we can extract is user validation.

Create a new method:

```java
private RegistrationResponse validateUser(UserData userData) {
    if (userData.getUsername() == null
        || userData.getUsername().isBlank()
        || userData.getUsername().length() < 3
        || userData.getUsername().length() > 20) {

        return new RegistrationResponse(
            false,
            "Invalid username. Must be between 3 and 20 characters.",
            null
        );
    }

    if (userData.getEmail() == null
        || userData.getEmail().isBlank()
        || !userData.getEmail().contains("@")
        || !userData.getEmail().contains(".")) {

        return new RegistrationResponse(
            false,
            "Invalid email format.",
            null
        );
    }

    if (userData.getPassword() == null
        || userData.getPassword().isBlank()
        || userData.getPassword().length() < 8
        || !userData.getPassword().matches(".*[A-Z].*")
        || !userData.getPassword().matches(".*\\d.*")
        || !userData.getPassword().matches(".*[!@#$%^&*].*")) {

        return new RegistrationResponse(
            false,
            "Password must be at least 8 characters and contain uppercase, number, and special character.",
            null
        );
    }

    return null;
}
```

The original method can now call this method:

```java
RegistrationResponse validationResponse = validateUser(userData);

if (validationResponse != null) {
    return validationResponse;
}
```

---

# Why Does `validateUser()` Return `null`?

The method uses the following convention:

```java
return null;
```

means:

> Validation passed; there is no validation error.

While:

```java
return new RegistrationResponse(false, "...", null);
```

means:

> Validation failed; return the error response.

Therefore:

```java
RegistrationResponse validationResponse = validateUser(userData);

if (validationResponse != null) {
    return validationResponse;
}
```

means:

1. Validate the user.    
2. If an error response exists, return it immediately.
3. Otherwise, continue processing the registration.

> [!NOTE]  
> In production code, a dedicated validation result type or exception-free validation approach may be preferable. For this exercise, returning `null` represents "no validation error."

# Refactored `processUserRegistration()`

After extracting user validation, the main method becomes shorter:

```java

    try {
        // User validation
        RegistrationResponse validationResponse = validateUser(userData);

        if (validationResponse != null) {
            return validationResponse;

        LocalDate birthDate = LocalDate.parse(userData.getDateOfBirth());
        LocalDate today = LocalDate.now();
        Period age = Period.between(birthDate, today);

        if (age.getYears() < 18 || age.getYears() > 120) {
            return new RegistrationResponse(
                false,
                "Invalid date of birth or user must be 18+",
                null
            );
        }

        // Address validation
        Address address = userData.getAddress();

        if (address.getStreet() == null
            || address.getStreet().isBlank()
            || address.getStreet().length() < 5) {
            return new RegistrationResponse(
                false,
                "Invalid street address",
                null
            );
        }

        if (address.getCity() == null
            || address.getCity().isBlank()
            || address.getCity().length() < 2) {
            return new RegistrationResponse(
                false,
                "Invalid city",
                null
            );
        }

        if (address.getCountry() == null
            || address.getCountry().isBlank()
            || address.getCountry().length() < 2) {
            return new RegistrationResponse(
                false,
                "Invalid country",
                null
            );
        }

        if (address.getPostalCode() == null
            || address.getPostalCode().isBlank()
            || !address.getPostalCode().matches("^[A-Z0-9]{3,10}$")) {
            return new RegistrationResponse(
                false,
                "Invalid postal code",
                null
            );
        }

        // Data transformation
        String userId = "USER_"
            + UUID.randomUUID().toString().substring(0, 8);

        UserData normalizedData = new UserData(

                userData.getAddress().getStreet().trim(),
                userData.getAddress().getCity().trim(),

        return new RegistrationResponse(
            true,
            "User registered successfully",
            userId
        );

    } catch (Exception e) {
        return new RegistrationResponse(
            false,
            "Registration failed: " + e.getMessage(),
            ""
        );
    }
}
```

The method is already easier to understand because the user validation details have been moved elsewhere.

# More Opportunities for Extraction

There are still several responsibilities that could be extracted.

### Date validation

```java
validateDateOfBirth(userData.getDateOfBirth())
```

### Address validation

```java
validateAddress(userData.getAddress())
```

### Data transformation

```java
normalizeUserData(userData, birthDate)
```

### User ID generation

```java
generateUserId()
```

The eventual goal is for `processUserRegistration()` to read almost like a high-level description of the registration process.

For example:

```text
Validate user
    ↓
Validate date
    ↓
Validate address
    ↓
Generate ID
    ↓
Normalize data
    ↓
Store data
    ↓
Return success
```

# Benefits of Extract Method

## 1. Improved readability

Instead of reading hundreds of lines of implementation details, the main method can communicate the overall workflow.

## 2. Single responsibility

Each extracted method can focus on one specific responsibility.

For example:

```java
validateUser()
```

focuses on user validation rather than registration as a whole.

## 3. Easier testing

Individual functionality can be tested more easily.

For example, user validation can be tested independently from data storage.

## 4. Easier debugging

If registration fails because of an address problem, the address validation logic can be investigated separately.

## 5. Reusability

An extracted method may be useful in other parts of the application.

## 6. Lower complexity

Smaller methods are easier to reason about and modify.

# Extract Method and TDD

Extract Method fits naturally into the **Refactor** phase of TDD.

```text
       ┌──────────────┐
       │     RED      │
       │ Test fails   │
       └──────┬───────┘
              ↓
       ┌──────────────┐
       │    GREEN     │
       │ Test passes  │
       └──────┬───────┘
              ↓
       ┌──────────────┐
       │   REFACTOR   │
       │ Improve code │
       └──────┬───────┘
              │
              └──────────→ Repeat
```

During refactoring:

1. Make a small structural change.    
2. Run the tests.
3. Confirm that all tests still pass.
4. Make the next improvement.
5. Run the tests again.

> [!IMPORTANT]  
> If the behavior changes during a refactoring, then it is **not simply a refactor**. The purpose of refactoring is to improve the code's structure while preserving its behavior.

---

# Refactoring Safety Net

Existing tests are particularly valuable when working with long methods.

Without tests, extracting code can accidentally:

- Change execution order    
- Change conditions
- Change return values
- Introduce missing logic
- Change exception handling

With a good test suite:

```text
Existing behavior
       ↓
Extract Method
       ↓
Run tests
       ↓
Tests pass
       ↓
Behavior preserved
```

This gives us confidence to make larger structural improvements incrementally.

---

# Key Takeaways

- **Long methods are a code smell.**    
- A method becomes problematic when it contains too many responsibilities.
- Use **Extract Method** to move logical sections into smaller, focused methods.
- Give extracted methods **meaningful names**.
- Smaller methods improve readability, maintainability, testing, and debugging.
- Extract Method supports the **Single Responsibility Principle**.
- Refactor in **small, incremental steps**.
- Run the existing tests after each refactoring.
- The goal of refactoring is to improve **code structure without changing behavior**.
- TDD tests act as a **safety net** that gives us confidence during refactoring.

> [!TIP]  
> When a method becomes difficult to explain because it does "too many things," look for logical sections that can be described with a meaningful verb such as `validate`, `calculate`, `normalize`, `save`, `format`, or `generate`. These are strong candidates for **Extract Method**.
