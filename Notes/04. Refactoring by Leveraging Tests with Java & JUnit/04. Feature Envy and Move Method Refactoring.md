# Introduction

In software design, **code smells** are indicators of potential problems in a codebase that can make software harder to understand, test, and maintain.

One common code smell is **Feature Envy**. It occurs when a method in one class interacts excessively with the data or behavior of another class.

A common way to address Feature Envy is the **Move Method** refactoring technique. The idea is to move a method to the class that owns the data it primarily uses.

This improves:

- Cohesion
- Encapsulation
- Maintainability
- Testability
- Readability

This course uses **Test Driven Development (TDD)** with:

- Java
- JUnit
- Mockito

The development process follows the **Red → Green → Refactor** cycle, allowing us to improve the design while keeping existing behavior protected by tests.

---

# What Is Feature Envy?

**Feature Envy** is a code smell where a method in one class is more interested in the data or behavior of another class than its own class.

For example, a method may repeatedly:

- Call getters on another object.
- Access properties of another class.
- Perform calculations using another object's data.
- Make decisions based primarily on another class's state.

This can indicate that the method is located in the wrong class.

> [!IMPORTANT]
> A method should generally be located close to the data and behavior it primarily operates on.

## Problems Caused by Feature Envy

### 1. Poor Encapsulation

Feature Envy can cause one class to reach deeply into another class's data.

This weakens encapsulation because the class that owns the data is no longer responsible for the behavior associated with that data.

### 2. Increased Coupling

When one class depends heavily on another class's internal data, the classes become tightly coupled.

Changes to one class may then require changes to other classes.

### 3. Reduced Cohesion

A class should ideally contain behavior related to its primary responsibility.

When a method primarily works with another class's data, the class containing the method may have poor cohesion.

### 4. Increased Testing Complexity

Methods affected by Feature Envy may require complicated test setup because they depend heavily on objects from another class.

This can result in:

- More test fixtures
- More mocks or test objects
- More complicated test scenarios
- Less focused unit tests

# Identifying Feature Envy

A useful way to identify Feature Envy is to look for methods that interact disproportionately with another class's data.

Consider a `GradeAnalyzer` that analyzes the grades belonging to a `Student`.

The `calculateFinalGrade()` method accesses the student's grades and performs calculations on each `Grade`.

## Original Code

```java
public class GradeAnalyzer {

    private Student student;

    public double calculateFinalGrade() {
        List<Grade> grades = student.getGrades();

        if (grades.isEmpty()) {
            return 0;
        }

        double totalEarned = 0;
        double totalPossible = 0;

        for (Grade grade : grades) {
            if (isLateSubmission(grade)) {
                totalEarned += grade.getScore() * 0.9; // 10% penalty
            } else {
                totalEarned += grade.getScore();
            }

            totalPossible += grade.getTotalPoints();
        }

        return (totalEarned / totalPossible) * 100;
    }

    // Assume method implementation
    private boolean isLateSubmission(Grade grade) {
        // Logic to determine late submission
        return false;
    }
}
````

## Why Is This Feature Envy?

The method:

```java
student.getGrades()
```

retrieves data owned by `Student`.

The method then iterates over the grades and performs calculations using the `Grade` objects.

This suggests that the grade-related behavior may belong closer to the `Student`/`Grade` domain rather than being controlled entirely by `GradeAnalyzer`.

The method is therefore showing an **excessive interest in another object's data**.

---

# Move Method Refactoring

One way to address Feature Envy is the **Move Method** refactoring technique.

The goal is to move behavior to the class that has the data required by that behavior.

Instead of having `GradeAnalyzer` directly calculate late penalties, the `Grade` object can provide the score after applying its own late-submission rules.

For example:

```java
grade.getScoreWithLatePenalty();
```

This allows the grade-related logic to stay closer to the `Grade` data.

## Refactored Code

```java
public class GradeAnalyzer {

    private List<Grade> grades;

    public double calculateFinalGrade() {
        if (grades.isEmpty()) {
            return 0;
        }

        double totalEarned = 0;
        double totalPossible = 0;

        for (Grade grade : grades) {
            totalEarned += grade.getScoreWithLatePenalty();
            totalPossible += grade.getTotalPoints();
        }

        return (totalEarned / totalPossible) * 100;
    }
}
```

The `GradeAnalyzer` now focuses primarily on **aggregating grades** rather than understanding the details of how an individual grade should be scored.

---

# Before vs. After

|Before|After|
|---|---|
|`GradeAnalyzer` accesses detailed grade data|`Grade` handles grade-specific behavior|
|Late-penalty logic is in `GradeAnalyzer`|Late-penalty behavior is closer to `Grade`|
|More knowledge in `GradeAnalyzer`|`GradeAnalyzer` has a simpler responsibility|
|Higher coupling|Reduced coupling|
|Lower cohesion|Better cohesion|
|More complex responsibilities|More focused responsibilities|

# Why Move Method Helps

The Move Method refactoring can improve the design by placing behavior closer to the data it operates on.

### Before

```text
GradeAnalyzer
      |
      | accesses
      v
   Student
      |
      v
    Grades
```

`GradeAnalyzer` knows too much about the internal grade-related data.

### After

```text
GradeAnalyzer
      |
      | asks Grade for calculated score
      v
    Grade
```

`Grade` becomes responsible for behavior associated with its own data.

# Feature Envy and Object-Oriented Design

Feature Envy is closely related to several object-oriented design principles.

## Encapsulation

Keep data and the behavior that operates on that data together.

Instead of:

```java
grade.getScore()
```

followed by external logic that determines how the score should be modified, the `Grade` class can provide:

```java
grade.getScoreWithLatePenalty()
```

This hides the implementation details from the caller.

## High Cohesion

A highly cohesive class contains behavior that belongs together.

For example:

```text
Grade
├── score
├── totalPoints
├── lateSubmission
└── getScoreWithLatePenalty()
```

The grade-related behavior is grouped with the grade-related data.

## Low Coupling

Moving behavior closer to the data it operates on can reduce unnecessary dependencies between classes.

# TDD and Refactoring

Feature Envy can be addressed safely using **Test Driven Development**.

The TDD cycle is:

```text
Red
 ↓
Green
 ↓
Refactor
 ↓
Red
 ↓
Green
 ↓
...
```

### Red

Write or run a test that describes the expected behavior.

### Green

Implement the minimum code necessary to make the test pass.

### Refactor

Improve the design without changing the externally observable behavior.

> [!TIP]  
> Tests act as a safety net during refactoring. If the tests continue to pass, we have greater confidence that the refactoring did not change the intended behavior.

---

# Key Takeaways

- **Feature Envy** occurs when a method is excessively interested in another class's data or behavior.
- Feature Envy can lead to:
    - Poor encapsulation
    - Increased coupling
    - Reduced cohesion
    - More complicated testing
- **Move Method** is a refactoring technique that can help address Feature Envy.
- Move behavior toward the class that owns the data the behavior primarily operates on.
- `GradeAnalyzer` should focus on **grade aggregation**, while grade-specific behavior should be closer to `Grade`.
- TDD's **Red → Green → Refactor** cycle provides a safety net for making structural improvements.
- The goal of refactoring is to improve the internal design **without changing the external behavior**.

> [!NOTE]  
> Feature Envy does not mean that every method accessing another object's data must be moved. The important question is whether the method's primary responsibility belongs with the other class's data and behavior.
