# Introduction to Fakes

A **Fake** is a type of **test double** that provides a working, simplified implementation of a real dependency.

In this lesson, we use **Java**, **JUnit**, and **Mockito** to understand how fakes can simplify testing by simulating real-world components.

So far, we have explored several types of test doubles:

- **Dummies**
- **Stubs**
- **Spies**
- **Mocks**
- **Fakes**

Fakes are different because they contain actual implementation logic, but the implementation is simplified compared to the real production component.

For example, instead of connecting to a real database during tests, we can create an **in-memory repository** that behaves similarly to a database while keeping all data in memory.

This makes tests:

- Faster
- More predictable
- Easier to maintain
- Independent of external systems
- Easier to run repeatedly

As with other TDD exercises, we follow the:

> **Red → Green → Refactor**

cycle.

---

## Fake Repository

A common example of a fake is an **in-memory repository**.

Suppose our application normally stores users in a database. Instead of using the real database in unit tests, we can create an `InMemoryUserRepository` that implements the same interface as the real repository.

### `InMemoryUserRepository.java`

```java
public class InMemoryUserRepository implements IUserRepository {
    private final Map<String, User> users = new ConcurrentHashMap<>();
    private int currentId = 1;

    private synchronized String generateId() {
        return String.valueOf(currentId++);
    }

    @Override
    public User create(User userData) {
        User user = new User();
        user.setId(generateId());
        user.setEmail(userData.getEmail());
        user.setName(userData.getName());
        user.setCreatedAt(LocalDateTime.now());
        users.put(user.getId(), user);
        return user;
    }

    @Override
    public User findById(String id) {
        return users.get(id);
    }

    @Override
    public User findByEmail(String email) {
        return users.values().stream()
                .filter(u -> u.getEmail().equalsIgnoreCase(email))
                .findFirst()
                .orElse(null);
    }

    @Override
    public User update(String id, User data) {
        User existing = users.get(id);

        if (existing == null) {
            return null;
        }

        if (data.getEmail() != null) {
            existing.setEmail(data.getEmail());
        }

        if (data.getName() != null) {
            existing.setName(data.getName());
        }

        // Prevent modification of id and createdAt
        users.put(id, existing);
        return existing;
    }

    @Override
    public boolean delete(String id) {
        return users.remove(id) != null;
    }

    @Override
    public List<User> findAll() {
        return new ArrayList<>(users.values());
    }

    @Override
    public void clear() {
        users.clear();
        currentId = 1;
    }
}
````

### How the Fake Works

The `InMemoryUserRepository` uses a `ConcurrentHashMap` as an in-memory data store:

```java
private final Map<String, User> users = new ConcurrentHashMap<>();
```

Instead of storing users in an external database, users are stored directly in memory.

The fake implements common repository operations:

- `create()` — Creates and stores a new user.    
- `findById()` — Finds a user by ID.
- `findByEmail()` — Finds a user by email address.
- `update()` — Updates an existing user's information.
- `delete()` — Removes a user from the repository.
- `findAll()` — Returns all users.
- `clear()` — Removes all users and resets the ID counter.

### Why Use `clear()`?

The `clear()` method is important for **test isolation**.

Tests should not depend on data created by previous tests. Clearing the repository ensures that each test can start with a clean state.

This helps make tests:

- **Repeatable**
- **Independent**
- **Predictable**

### Why Use a Fake?

A fake allows us to test business logic without depending on an external database.

Instead of:

```text
UserService → Real Database
```

we can use:

```text
UserService → InMemoryUserRepository
```

This keeps the test environment fast and predictable while still exercising realistic repository behavior.

# Building Tests Using the Fake Repository

We can now use the fake repository to test a `UserService`.

## 1. Red — Write a Failing Test

First, write a test describing the behavior we want.

### `UserServiceTest.java`

```java
public class UserServiceTest {
    private UserService userService;
    private InMemoryUserRepository userRepository;

    @BeforeEach
    public void setUp() {
        // Arrange
        userRepository = new InMemoryUserRepository();
        userService = new UserService(userRepository);
    }

    @Test
    public void testRegisterUserCreatesNewUserSuccessfully() {
        // Act
        User user = userService.registerUser(
                "test@example.com",
                "Test User"
        );

        // Assert
        assertEquals("test@example.com", user.getEmail());
        assertEquals("Test User", user.getName());
        assertNotNull(user.getId());
        assertNotNull(user.getCreatedAt());

        List<User> repositoryUsers = userRepository.findAll();

        assertEquals(1, repositoryUsers.size());
        assertEquals("Test User", repositoryUsers.get(0).getName());
    }
}
```

At this stage, the required `UserService` logic has not been implemented yet.

Therefore, the test should fail.

This is the **Red** phase of TDD.

---

## 2. Green — Implement the Minimum Code

Next, implement the minimum amount of code required to make the test pass.

### `UserService.java`

```java
public class UserService {
    private final IUserRepository repository;

    public UserService(IUserRepository repository) {
        this.repository = repository;
    }

    public User registerUser(String email, String name) {
        return this.repository.create(new User(email, name));
    }
}
```

Run the test again.

The test should now pass.

This completes the **Green** phase.

The implementation is intentionally simple because the goal is to write only enough code to satisfy the requirement.

---

## 3. Refactor — Improve the Code

Once the test passes, we can improve the code without changing its behavior.

The tests provide confidence that our refactoring does not break the existing functionality.

The complete TDD cycle is:

```text
Red → Green → Refactor
```

# Fakes vs. Other Test Doubles

Fakes are different from simpler test doubles because they contain a working implementation.

| Test Double | Purpose                                          |
| ----------- | ------------------------------------------------ |
| **Dummy**   | Passed around but not actually used              |
| **Stub**    | Provides predefined responses                    |
| **Spy**     | Records information about how it was used        |
| **Mock**    | Verifies expected interactions                   |
| **Fake**    | Provides a simplified but working implementation |

For example, an `InMemoryUserRepository` is a fake because it actually stores and retrieves users, but it does so using an in-memory data structure instead of a real database.

---

# Key Takeaways

- A **Fake** is a simplified but working implementation of a real dependency.    
- Fakes are useful when the real dependency is expensive, slow, or difficult to use during tests.
- An **in-memory repository** is a common example of a fake.
- Fakes can simulate database behavior without requiring an actual database.
- `ConcurrentHashMap` can be used to store data in memory.
- A `clear()` method helps maintain **test isolation**.
- Tests should be independent, repeatable, and predictable.
- Fakes allow tests to focus on business logic rather than external systems.
- TDD follows the **Red → Green → Refactor** cycle.

## TDD Cycle

### Red

Write a test that fails and clearly defines the desired behavior.

### Green

Implement the minimum amount of code required to make the test pass.

### Refactor

Improve the code while keeping the existing behavior unchanged.
