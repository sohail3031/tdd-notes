# Introduction

This lesson introduces another type of **test double**: the **stub**.

In the previous lesson, we used **dummies** to satisfy dependencies without providing meaningful behavior. In this lesson, we will explore **stubs**, which provide predefined responses when their methods are called.

The examples use:

- Java
- JUnit 5
- Mockito
- Test-Driven Development (TDD)

By the end of this lesson, you should understand what stubs are and how to use them to isolate dependencies, particularly external services.

---

## What Is a Stub?

A **stub** is a type of test double that provides **predefined answers to method calls** during a test.

Unlike some other test doubles, a stub does not focus on tracking or verifying how it was used. Its primary purpose is to provide controlled data that allows the code under test to execute predictably.

### Why Use Stubs?

Stubs are useful when the code being tested depends on:

- External services
- Databases
- APIs
- Complex dependencies
- Systems that produce unpredictable results

By providing predefined responses, stubs make tests:

- Faster
- More predictable
- Easier to control
- Independent of external systems

> [!NOTE]
> A stub focuses on providing controlled input to the system under test. It does not primarily verify whether or how the dependency was called.

---

## Stubs vs. Dummies

The key difference between a **dummy** and a **stub** is the behavior they provide.

| Test Double | Purpose |
|---|---|
| **Dummy** | Exists only to satisfy a dependency. Its behavior is usually irrelevant to the test. |
| **Stub** | Provides predefined responses that influence the behavior of the system under test. |

For example:

```text
Dummy
└── Required dependency
    └── Provides no meaningful behavior

Stub
└── Required dependency
    └── Returns predefined data
````

A dummy might contain an empty method:

```java
@Override
public void send(String message) {
    // Do nothing
}
```

A stub provides controlled data:

```java
@Override
public WeatherData getCurrentWeather(String location) {
    return currentWeather;
}
```

# Example: WeatherAlertService

To demonstrate stubs, we will build a `WeatherAlertService`.

The service depends on an `IWeatherService` that provides weather information.

```text
WeatherAlertService
        |
        v
IWeatherService
        |
        v
WeatherData
```

The goal is to test the alert logic without relying on a real weather service.

A real external weather service could introduce problems such as:

- Network delays
- Service outages
- Changing weather data
- API limitations
- Slow tests

Instead, we use a stub to provide controlled weather data.

---

# Supporting Classes

## IWeatherService

The `IWeatherService` interface defines the dependency required by `WeatherAlertService`.

```java
public interface IWeatherService {

    WeatherData getCurrentWeather(String location);
}
```

## WeatherData

`WeatherData` represents the weather information returned by the weather service.

```java
public class WeatherData {

    private final int temperature;
    private final String conditions;

    public WeatherData(int temperature, String conditions) {
        this.temperature = temperature;
        this.conditions = conditions;
    }

    public int getTemperature() {
        return temperature;
    }

    public String getConditions() {
        return conditions;
    }
}
```

# Red: Write a Failing Test

The first step in the **Red-Green-Refactor** cycle is to write a test that describes the expected behavior.

The expected behavior is:

> When the temperature is above `35`, the service should return an extreme heat warning.

## Hand-Crafted Stub

We can create a manual stub that implements the `IWeatherService` interface.

```java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

public class WeatherAlertServiceTest {

    private WeatherServiceStub weatherService;
    private WeatherAlertService alertService;

    class WeatherServiceStub implements IWeatherService {

        private WeatherData currentWeather =
            new WeatherData(20, "sunny");

        public void setWeather(
            int temperature,
            String conditions
        ) {
            this.currentWeather =
                new WeatherData(temperature, conditions);
        }

        @Override
        public WeatherData getCurrentWeather(String location) {
            return currentWeather;
        }
    }

    @BeforeEach
    public void setUp() {
        weatherService = new WeatherServiceStub();
        alertService = new WeatherAlertService(weatherService);
    }

    @Test
    public void shouldReturnHeatWarningWhenTemperatureIsAbove35() {
        // Arrange
        weatherService.setWeather(36, "sunny");

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Extreme heat warning. Stay hydrated!",
            alert
        );
    }
}
```

## How the Hand-Crafted Stub Works

The `WeatherServiceStub` stores predefined weather data:

```java
private WeatherData currentWeather =
    new WeatherData(20, "sunny");
```

The `setWeather()` method allows the test to change the data returned by the stub:

```java
weatherService.setWeather(36, "sunny");
```

When `WeatherAlertService` requests the weather data:

```java
weatherService.getCurrentWeather("London");
```

The stub returns the predefined `WeatherData` object.

The test can therefore control the input received by `WeatherAlertService` without using a real weather service.

> [!NOTE]  
> The stub does not retrieve real weather information. It returns data specifically configured for the test.

At this stage, the test should fail because `WeatherAlertService` has not yet implemented the required behavior.

This is the **Red** phase of TDD.

# Green: Make the Test Pass

The next step is to implement the minimum amount of code necessary to make the test pass.

## WeatherAlertService

```java
public class WeatherAlertService {

    private final IWeatherService weatherService;

    public WeatherAlertService(IWeatherService weatherService) {
        this.weatherService = weatherService;
    }

    public String shouldSendAlert(String location) {
        WeatherData weather =
            weatherService.getCurrentWeather(location);

        if (weather.getTemperature() > 35) {
            return "Extreme heat warning. Stay hydrated!";
        }

        return null;
    }
}
```

The service receives `IWeatherService` through constructor dependency injection:

```java
public WeatherAlertService(
    IWeatherService weatherService
)
```

It then retrieves the weather data:

```java
WeatherData weather =
    weatherService.getCurrentWeather(location);
```

Finally, it checks the temperature:

```java
if (weather.getTemperature() > 35) {
    return "Extreme heat warning. Stay hydrated!";
}
```

If the temperature is not above `35`, the method currently returns `null`.

> [!NOTE]  
> During the Green phase, the goal is to write only enough code to make the current test pass. Additional scenarios can be implemented later as new tests are added.

# Refactor: Using Mockito to Create a Stub

The hand-crafted `WeatherServiceStub` works correctly, but it requires us to create and maintain a separate class.

We can simplify the test by using **Mockito**.

Mockito allows us to create a test double dynamically and configure predefined return values.

Instead of creating:

```java
class WeatherServiceStub implements IWeatherService {
    // Custom implementation
}
```

We can create a Mockito mock:

```java
IWeatherService weatherServiceMock =
    mock(IWeatherService.class);
```

Although Mockito uses the term **mock**, the behavior we configure can be used as a **stub** when we only define return values and do not verify interactions.

---

## Stubbing a Method with Mockito

Mockito uses `when()` and `thenReturn()` to define the expected behavior.

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

This means:

> When `getCurrentWeather("London")` is called, return a `WeatherData` object with a temperature of `36` and conditions of `"sunny"`.

The test can now control the response from the dependency without creating a custom stub class.

---

# WeatherAlertServiceTest Using Mockito

```java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.when;

public class WeatherAlertServiceTest {

    private IWeatherService weatherServiceMock;
    private WeatherAlertService alertService;

    @BeforeEach
    public void setUp() {
        weatherServiceMock = mock(IWeatherService.class);

        alertService =
            new WeatherAlertService(weatherServiceMock);
    }

    @Test
    public void shouldReturnHeatWarningWhenTemperatureIsAbove35() {
        // Arrange
        when(weatherServiceMock.getCurrentWeather("London"))
            .thenReturn(new WeatherData(36, "sunny"));

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Extreme heat warning. Stay hydrated!",
            alert
        );
    }
}
```

## How the Mockito Stub Works

### 1. Create the Test Double

```java
weatherServiceMock =
    mock(IWeatherService.class);
```

Mockito creates an implementation of `IWeatherService` that can be configured during the test.

### 2. Define the Predefined Response

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

This configures the response returned by the dependency.

### 3. Inject the Dependency

```java
alertService =
    new WeatherAlertService(weatherServiceMock);
```

The stubbed dependency is passed to `WeatherAlertService`.

### 4. Execute the Code Under Test

```java
String alert =
    alertService.shouldSendAlert("London");
```

When `WeatherAlertService` calls:

```java
weatherService.getCurrentWeather("London");
```

Mockito returns:

```java
new WeatherData(36, "sunny");
```

The service then processes this controlled data and returns the expected alert.

# Using Mockito Annotations with JUnit 5

Mockito can also simplify test setup by using annotations.

The following annotations are commonly used:

- `@ExtendWith(MockitoExtension.class)`
- `@Mock`
- `@InjectMocks`

```java
import org.junit.jupiter.api.extension.ExtendWith;

import org.mockito.InjectMocks;
import org.mockito.Mock;

import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
public class WeatherAlertServiceTest {

    @Mock
    private IWeatherService weatherServiceMock;

    @InjectMocks
    private WeatherAlertService alertService;

    // Test methods...
}
```

## @ExtendWith(MockitoExtension.class)

```java
@ExtendWith(MockitoExtension.class)
```

This activates Mockito's JUnit 5 integration.

It allows Mockito to process annotations such as `@Mock` and `@InjectMocks`.

## @Mock

```java
@Mock
private IWeatherService weatherServiceMock;
```

`@Mock` creates and initializes a Mockito test double for `IWeatherService`.

## @InjectMocks

```java
@InjectMocks
private WeatherAlertService alertService;
```

`@InjectMocks` creates the `WeatherAlertService` and automatically injects suitable mocks into it.

This removes the need to manually initialize the mock and pass it to the constructor in the `setUp()` method.

# Manual Setup vs. Mockito Annotations

## Manual Setup

```java
@BeforeEach
public void setUp() {
    weatherServiceMock = mock(IWeatherService.class);

    alertService =
        new WeatherAlertService(weatherServiceMock);
}
```

## Annotation-Based Setup

```java
@ExtendWith(MockitoExtension.class)
public class WeatherAlertServiceTest {

    @Mock
    private IWeatherService weatherServiceMock;

    @InjectMocks
    private WeatherAlertService alertService;
}
```

Both approaches achieve the same goal.

The annotation-based approach reduces boilerplate code and can make tests easier to read.

> [!TIP]  
> Understanding the manual approach is important before relying heavily on annotations because it makes the dependency injection process more explicit.

# Key Concepts

## Stub

A stub provides predefined responses to method calls.

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

The purpose is to provide controlled data to the system under test.

## Dependency Injection

`WeatherAlertService` receives its dependency through the constructor:

```java
public WeatherAlertService(
    IWeatherService weatherService
)
```

This allows the real dependency to be replaced with a test double.

## Isolation

The test does not depend on a real weather service.

This makes the test:

- Fast
- Predictable
- Independent of external systems

## Red-Green-Refactor

The development process follows the TDD cycle:

### Red

Write a failing test.

```text
Expected:
"Extreme heat warning. Stay hydrated!"

Actual:
Test fails because the functionality is not implemented.
```

### Green

Write the minimum implementation necessary to pass the test.

```java
if (weather.getTemperature() > 35) {
    return "Extreme heat warning. Stay hydrated!";
}
```

### Refactor

Improve the test or implementation without changing its external behavior.

In this example, the hand-crafted stub is replaced with a Mockito-based test double.

---

# Summary

## Key Takeaways

- **Stubs** are test doubles that provide predefined responses.
- Stubs are useful for isolating external services and complex dependencies.
- A hand-crafted stub can implement an interface and return controlled data.
- Mockito can simplify the creation and configuration of stubs.
- `when()` and `thenReturn()` are used to define predefined responses.
- Constructor dependency injection makes it easier to replace real dependencies with test doubles.
- `@Mock` and `@InjectMocks` can reduce boilerplate when using Mockito with JUnit 5.
- The **Red-Green-Refactor** cycle encourages incremental implementation and continuous improvement.

> [!IMPORTANT]  
> Mockito can create an object referred to as a **mock**, but when it is configured only to return predefined values and no interactions are verified, it is being used in the role of a **stub**.
