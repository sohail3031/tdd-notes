# 1. What Are Dependencies?

A **dependency** is a component or service that a class relies on to perform its work.

Examples:

- Database    
- Logging system
- External API
- Email service
- File system
- Payment service

For example:

```java
public class EmailService {
    private final ILogger logger;
    private final IEmailSender emailSender;
}
```

`EmailService` depends on:

- `ILogger`
- `IEmailSender`

These are its **dependencies**.

---

## 2. Why Are Dependencies a Problem in Testing?

Real dependencies can make tests:

- Slower
- More complicated
- Unreliable
- Difficult to isolate
- Dependent on external systems

For example, if `EmailService` uses a real email server during a test, the test could:

- Actually send an email
- Fail because the server is unavailable
- Take longer to execute
- Require network access

Ideally, a unit test should focus on the **logic of the class being tested**, not on external systems.

---

# Test Doubles

A **test double** is an object that replaces a real dependency during testing.

Test doubles allow us to isolate the code under test from its dependencies.

There are **five common types**:

|Test Double|Purpose|
|---|---|
|**Dummy**|Placeholder used only to satisfy a parameter/dependency requirement|
|**Stub**|Returns predefined responses|
|**Spy**|Records interactions for later verification|
|**Mock**|Defines and verifies expected interactions|
|**Fake**|Simplified working implementation of a real dependency|

### Easy way to remember

> **Dummy = Does nothing**  
> **Stub = Gives answers**  
> **Spy = Records what happened**  
> **Mock = Checks expected behavior**  
> **Fake = Actually works, but simplified**

---

# Dummies

A **dummy** is the simplest type of test double.

It exists only to satisfy a dependency requirement.

A dummy generally:

- Contains little or no logic
- Doesn't perform meaningful work
- Isn't the focus of the test
- Allows the test to construct the class under test

---

## Example

Suppose `EmailService` requires:

```java
ILogger logger
IEmailSender emailSender
```

We can provide dummy implementations.

### DummyLogger

```java
class DummyLogger implements ILogger {

    @Override
    public void log(String message) {
        // Do nothing
    }
}
```

### DummyEmailSender

```java
class DummyEmailSender implements IEmailSender {

    @Override
    public void send(String to, String subject, String body) {
        // Do nothing
    }
}
```

These classes don't actually log anything or send emails.

They simply satisfy the dependencies required by `EmailService`.

---

# Interfaces and Dependencies

The dependencies are defined through interfaces.

### ILogger

```java
public interface ILogger {
    void log(String message);
}
```

### IEmailSender

```java
public interface IEmailSender {
    void send(String to, String subject, String body);
}
```

Using interfaces makes it possible to replace real implementations with test doubles.

---

# EmailService

```java
public class EmailService {

    private final ILogger logger;
    private final IEmailSender emailSender;

    public EmailService(ILogger logger, IEmailSender emailSender) {
        this.logger = logger;
        this.emailSender = emailSender;
    }

    public boolean sendEmail(String to, String subject, String body) {

        if (to == null || !to.contains("@")) {
            return false;
        }

        if (subject == null || subject.isEmpty()) {
            return false;
        }

        if (body == null || body.isEmpty() || body.length() > 1000) {
            return false;
        }

        logger.log("Sending email to " + to);
        emailSender.send(to, subject, body);

        return true;
    }
}
```

The constructor uses **dependency injection**:

```java
public EmailService(ILogger logger, IEmailSender emailSender)
```

The dependencies are provided from outside instead of being created inside `EmailService`.

This makes the class easier to test.

# Testing with Dummies

```java
public class EmailServiceTest {

    private EmailService emailService;

    @BeforeEach
    public void setUp() {
        emailService = new EmailService(
            new DummyLogger(),
            new DummyEmailSender()
        );
    }

    @Test
    public void shouldAcceptValidEmailParameters() {

        boolean result = emailService.sendEmail(
            "test@example.com",
            "Hello",
            "This is a test"
        );

        assertTrue(result);
    }
}
```

The test is primarily checking:

```java
EmailService.sendEmail()
```

It doesn't need to test:

- Real logging
- Real email delivery
- Email server connectivity
- Network communication

The dummy objects simply allow `EmailService` to operate during the test.

---

# Why Use Dummies?

Without dummies, we might need to create real implementations:

```text
EmailService
     |
     +---- Real Logger
     |
     +---- Real Email Server
```

This introduces unnecessary complexity.

With dummies:

```text
EmailService
     |
     +---- DummyLogger
     |
     +---- DummyEmailSender
```

The test becomes simpler and more isolated.

---

# Important Distinction

A dummy is **not intended to verify behavior**.

For example, this dummy:

```java
class DummyLogger implements ILogger {

    @Override
    public void log(String message) {
        // Do nothing
    }
}
```

doesn't record whether `log()` was called.

If we wanted to verify that logging happened, we would need another type of test double, such as a **spy** or **mock**.

# Test Doubles Comparison

### Dummy

```text
Purpose: Satisfy a dependency
Behavior: None
Example: DummyLogger
```

### Stub

```text
Purpose: Provide predefined data
Behavior: Returns controlled values
```

### Spy

```text
Purpose: Record interactions
Behavior: Keeps track of calls/arguments
```

### Mock

```text
Purpose: Verify expected interactions
Behavior: Defines expectations and verifies them
```

### Fake

```text
Purpose: Provide a simplified working implementation
Behavior: Has real logic
Example: In-memory database
```

---

# Key Concepts

### Dependency

Something that a class relies on.

### Test Double

A replacement for a real dependency during testing.

### Dummy

A test double that exists primarily to satisfy a dependency requirement without providing meaningful behavior.

### Dependency Injection

Providing dependencies to a class from outside, commonly through its constructor.

Example:

```java
new EmailService(logger, emailSender);
```

### Isolation

Testing one component without relying on the real behavior of its external dependencies.

---

# Quick Mental Model

Think of a class as a machine:

```text
        Dependencies
             ↓
      ┌──────────────┐
      │     Class    │
      │  Under Test  │
      └──────────────┘
             ↓
           Result
```

During unit testing, replace complicated dependencies:

```text
Real Dependency
      ↓
Test Double
      ↓
Class Under Test
```

For a **dummy**, the test double essentially says:

> "You need this dependency? Here it is. Don't worry about what it actually does."

---

## Summary

- **Dependencies** are components that a class relies on.
- Real dependencies can make unit tests slow, unreliable, and difficult to isolate.
- **Test doubles** replace real dependencies during testing.
- There are five common types:
    - **Dummy** → placeholder
    - **Stub** → predefined response
    - **Spy** → records interactions
    - **Mock** → verifies expected interactions
    - **Fake** → simplified working implementation
- **Dummies** are the simplest test double.
- Dummies generally contain **no meaningful behavior**.
- Interfaces make dependencies easier to replace with test doubles.
- **Dependency injection** makes code more testable.
- Dummies allow tests to focus on the **logic of the class under test** rather than external systems.
