# Overview

In the journey of isolating dependencies with **test doubles**, we have explored:

- Dummies
- Stubs
- Spies
- **Mocks**

This lesson focuses on **mocks**, which are powerful test doubles used to simulate external dependencies during software testing.

In previous examples, spying on a real implementation could sometimes be messy because the actual implementation was still involved. Mocks provide a cleaner way to isolate the system under test.

Mocks can imitate the behavior of complex systems, allowing us to test application logic without depending on real and potentially unpredictable systems such as:

- Databases
- External APIs
- Web services
- File systems
- Network services

---

# TDD Workflow

The Test-Driven Development (TDD) workflow follows the **Red-Green-Refactor** cycle.

## 1. Red

Write a test for the desired behavior.

The test initially fails because the required functionality has not yet been implemented.

```text
Red → Write a failing test
````

## 2. Green

Write the minimum amount of production code necessary to make the test pass.

```text
Green → Make the test pass
```

## 3. Refactor

Improve the structure and quality of the code without changing its behavior.

```text
Refactor → Improve the code while keeping tests passing
```

## Complete Cycle

```text
┌──────────┐
│   Red    │
│ Write a  │
│ failing  │
│   test   │
└────┬─────┘
     │
     ▼
┌──────────┐
│  Green   │
│ Write the│
│ minimum  │
│   code   │
└────┬─────┘
     │
     ▼
┌──────────┐
│ Refactor │
│ Improve  │
│ the code │
└────┬─────┘
     │
     └──────────► Repeat
```

Mocks help us apply this workflow by allowing us to isolate dependencies and focus tests on the specific behavior being developed.

# Why Use Mocks in TDD?

Mocks are useful because they allow us to test code independently of dependencies that we do not control.

For example, consider a `PricingService` that depends on an external currency conversion service.

```text
PricingService
      │
      ▼
IExchangeRateService
      │
      ▼
External Currency API
```

If the test depends on a real external API, several problems can occur:

- The API may be unavailable.
- The exchange rate may change.
- The network may fail.
- The API may be slow.
- The API may have rate limits.
- The test may become unpredictable or flaky.

Instead of using the real dependency, we can replace it with a mock.

```text
PricingService
      │
      ▼
Mock IExchangeRateService
      │
      ▼
Controlled Test Response
```

This makes the test:

- Faster
- More reliable
- More predictable
- Independent of external systems
- Focused on the application logic

---

# Mock vs Spy

Mocks and spies are both test doubles, but they behave differently.

|Feature|Mock|Spy|
|---|---|---|
|Wraps a real object|No|Yes|
|Executes real implementation by default|No|Yes|
|Simulates dependency behavior|Yes|Can|
|Records interactions|Yes|Yes|
|Requires stubbing for expected behavior|Usually|Optional|
|Suitable for external dependencies|Yes|Sometimes|

## Mock

A mock completely replaces a dependency.

The real implementation is not executed.

```java
@Mock
private IExchangeRateService exchangeRateService;
```

We define the behavior we want the mock to simulate.

```java
when(exchangeRateService.getRate("USD", "EUR"))
    .thenReturn(1.5);
```

## Spy

A spy wraps a real object.

```java
@Spy
private RealNotificationSender senderSpy =
    new RealNotificationSender();
```

By default, the real methods are executed, while Mockito also records the interactions.

# Mocking Fundamentals with Mockito

Consider an `IExchangeRateService` that retrieves exchange rates.

The `PricingService` depends on this service to convert prices between currencies.

## Test Using a Mock

```java
@ExtendWith(MockitoExtension.class)
public class PricingServiceTest {

    @Mock
    private IExchangeRateService mockIExchangeRateService;

    @InjectMocks
    private PricingService pricingService;

    @Test
    public void testConvertPriceUsesExchangeRate() throws Exception {
        // Arrange
        when(mockIExchangeRateService.getRate("USD", "EUR"))
            .thenReturn(1.5);

        // Act
        double result =
            pricingService.convertPrice(100, "USD", "EUR");

        // Assert
        verify(mockIExchangeRateService, times(1))
            .getRate("USD", "EUR");

        assertEquals(150.00, result);
    }
}
```

---

# Understanding the Mock Setup

## `@Mock`

```java
@Mock
private IExchangeRateService mockIExchangeRateService;
```

`@Mock` tells Mockito to create a mock implementation of `IExchangeRateService`.

The real implementation is not used.

The mock allows us to:

- Define return values.
- Simulate exceptions.
- Verify method calls.
- Control dependency behavior.

---

## `@InjectMocks`

```java
@InjectMocks
private PricingService pricingService;
```

`@InjectMocks` tells Mockito to create an instance of the class being tested and inject the available mocks into it.

Conceptually, this is similar to:

```java
pricingService =
    new PricingService(mockIExchangeRateService);
```

This ensures that `PricingService` uses the mock instead of a real exchange rate service.

---

# Stubbing Mock Behavior

The following code defines how the mock should behave:

```java
when(mockIExchangeRateService.getRate("USD", "EUR"))
    .thenReturn(1.5);
```

This means:

> When `getRate("USD", "EUR")` is called, return `1.5`.

The real exchange rate service is never called.

```text
PricingService
      │
      │ getRate("USD", "EUR")
      ▼
Mock IExchangeRateService
      │
      │ returns 1.5
      ▼
PricingService
```

---

# Verifying Mock Interactions

Mocks can also verify whether a method was called.

```java
verify(mockIExchangeRateService, times(1))
    .getRate("USD", "EUR");
```

This verifies that:

- `getRate()` was called.
- It was called exactly once.
- The correct arguments were passed.

# Example: Currency Conversion

## `IExchangeRateService`

The dependency is represented by an interface.

```java
public interface IExchangeRateService {

    double getRate(
        String fromCurrency,
        String toCurrency
    ) throws Exception;
}
```

The method retrieves the exchange rate between two currencies.

For example:

```text
USD → EUR
```

could return:

```text
1.5
```

---

# `PricingService`

The `PricingService` depends on `IExchangeRateService`.

```java
public class PricingService {

    private final IExchangeRateService exchangeRateService;

    public PricingService(
        IExchangeRateService exchangeRateService
    ) {
        this.exchangeRateService = exchangeRateService;
    }

    public double convertPrice(
        double amount,
        String fromCurrency,
        String toCurrency
    ) throws Exception {

        double rate =
            exchangeRateService.getRate(
                fromCurrency,
                toCurrency
            );

        return Math.round(amount * rate * 100.0) / 100.0;
    }
}
```

## How the Conversion Works

The service performs the following steps:

1. Retrieve the exchange rate.
2. Multiply the amount by the exchange rate.
3. Round the result to two decimal places.

For example:

```text
Amount = 100
Rate   = 1.5

100 × 1.5 = 150
```

Therefore:

```java
convertPrice(100, "USD", "EUR")
```

returns:

```text
150.00
```

# Advanced Mocking Techniques

Mocks are not limited to returning a single predefined value.

Mockito can simulate:

- Different responses based on input.
- Exceptions.
- Complex behavior.
- Multiple method calls.

---

## Returning Different Values Based on Input

Mockito's `thenAnswer()` allows us to define custom behavior.

```java
when(
    mockIExchangeRateService.getRate(
        anyString(),
        anyString()
    )
).thenAnswer(invocation -> {

    String from = invocation.getArgument(0);
    String to = invocation.getArgument(1);

    if ("USD".equals(from) && "EUR".equals(to)) {
        return 0.85;
    } else if ("USD".equals(from) && "GBP".equals(to)) {
        return 0.73;
    }

    return 1.0;
});
```

The mock examines the arguments passed to the method and returns a different value depending on the currencies.

---

# Understanding `thenAnswer()`

The `invocation` object represents the method call.

```java
String from = invocation.getArgument(0);
String to = invocation.getArgument(1);
```

The arguments are retrieved using their index.

|Index|Argument|
|---|---|
|`0`|`fromCurrency`|
|`1`|`toCurrency`|

For example:

```java
getRate("USD", "EUR")
```

results in:

```text
invocation.getArgument(0) → "USD"

invocation.getArgument(1) → "EUR"
```

The mock can then determine the appropriate response.

---

# Example Mock Behavior

Given the following configuration:

```java
when(
    mockIExchangeRateService.getRate(
        anyString(),
        anyString()
    )
).thenAnswer(invocation -> {

    String from = invocation.getArgument(0);
    String to = invocation.getArgument(1);

    if ("USD".equals(from) && "EUR".equals(to)) {
        return 0.85;
    } else if ("USD".equals(from) && "GBP".equals(to)) {
        return 0.73;
    }

    return 1.0;
});
```

The mock behaves as follows:

|From|To|Returned Rate|
|---|---|---|
|`USD`|`EUR`|`0.85`|
|`USD`|`GBP`|`0.73`|
|Any other combination|`1.0`||

# Key Mockito Concepts

## Creating a Mock

```java
@Mock
private IExchangeRateService exchangeRateService;
```

Creates a mock implementation of the dependency.

---

```java
when(exchangeRateService.getRate("USD", "EUR"))
```

```java

thenAnswer(invocation -> {
    // Custom behavior
```

# Benefits of Using Mocks

Mocks provide several benefits when testing software.

## 1. Isolation

The class under test can be tested independently from its dependencies.

```text
PricingService
      │
      ▼
Mock Dependency
```

---

## 2. Predictability

The mock always returns the value defined by the test.

```java
thenReturn(1.5);
```

The test is not affected by changing external data.

---

## 3. Faster Tests

Mocks do not make real:

- Network requests
- Database queries
- API calls

This makes tests faster.

---

## 4. Testing Edge Cases

Mocks allow us to simulate scenarios that may be difficult to reproduce with real dependencies.

For example:

- API failures
- Unexpected responses
- Different exchange rates
- Network problems
- Exceptions

---

## 5. Interaction Verification

Mocks allow us to verify how dependencies are used.

For example:

```java
verify(exchangeRateService, times(1))
    .getRate("USD", "EUR");
```

This verifies that the application communicates with its dependency correctly.

---

# Summary

Mocks are powerful test doubles that allow us to isolate application logic from external dependencies.

Unlike spies, mocks do not execute the real implementation by default. Instead, their behavior is controlled by the test.

The main Mockito operations used with mocks are:

```java
@Mock
```

Create a mock dependency.

```java
when(...).thenReturn(...)
```

Define the behavior of the mock.

```java
when(...).thenAnswer(...)
```

Define dynamic behavior based on the method invocation.

```java
verify(...)
```

Verify that an expected interaction occurred.

---

# Key Takeaways

- A **mock** is a test double that replaces a real dependency.
- Mocks allow tests to run without real external systems.
- The real implementation of a mocked dependency is not executed.
- `@Mock` creates a mock object.
- `@InjectMocks` injects mocks into the class being tested.
- `when(...).thenReturn(...)` defines a predefined response.
- `thenAnswer(...)` allows dynamic responses based on method arguments.
- `verify(...)` checks whether a method was called correctly.
- Mocks make tests faster, more reliable, and more predictable.
- Mocks are especially useful for dependencies such as APIs, databases, and external services.
- Mocks support the [[Test-Driven Development]] workflow by allowing application logic to be tested in isolation.
