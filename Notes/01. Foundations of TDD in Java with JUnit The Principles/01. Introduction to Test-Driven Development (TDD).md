# What is TDD?

**Test-Driven Development (TDD)** is an iterative software development methodology in which **tests are written before the actual implementation**. Instead of writing code first, you begin by defining the expected behavior through tests.

### Benefits of TDD

- Improves code quality and reliability.
- Encourages developers to focus on requirements first.
- Produces more maintainable and modular code.
- Makes refactoring safer by ensuring existing functionality remains intact.
- Helps catch defects early in the development process.

> [!note]
> In this course, TDD is implemented using **Java** and **JUnit**.

---

# The TDD Cycle

The core of TDD follows the **Red → Green → Refactor** cycle.

```text
🔴 Red
    ↓
🟢 Green
    ↓
🔵 Refactor
    ↺ Repeat
```

## 🔴 Red

Write a test **before** implementing the functionality.

The test should fail because the required functionality does not yet exist.

**Purpose**

- Define the expected behavior.
- Confirm that the test correctly detects missing functionality.
- Prevent writing unnecessary code.

### Example Test

```java
public class MathTest {

    @Test
    public void testSumAddsTwoNumbersCorrectly() {
        Math math = new Math();
        assertEquals(5, math.sum(2, 3));
    }
}
```

### Breakdown

- `@Test` marks the method as a test case.
- Creates an instance of the `Math` class.
- Calls the `sum()` method.
- Uses `assertEquals(expected, actual)` to verify the result.

### Expected Result

Since the `sum()` method does not exist yet, the test fails.

```text
MathTest.java:10: error: cannot find symbol
        assertEquals(5, math.sum(2, 3));
                            ^
  symbol:   method sum(int,int)
  location: variable math of type Math
1 error
```

> [!important]
> A failing test is **expected** during the Red phase. It confirms that the test is correctly identifying missing functionality.

---

## 🟢 Green

Write the **minimum amount of code** required to make the test pass.

The goal is **not** to write the complete solution immediately. Instead, write only enough code to satisfy the current test.

### Minimal Implementation

```java
public class Math {

    public int sum(int a, int b) {
        return 5;
    }
}
```

Although this implementation is technically incorrect for a general-purpose `sum()` method, it satisfies the current test case.

### Test Result

```text
> Task :test

MathTest > testSumAddsTwoNumbersCorrectly() PASSED
```

> [!tip]
> During the Green phase, avoid overengineering. Write only enough code to make the current test pass.

---

## 🔵 Refactor

Once the test passes, improve the code without changing its behavior.

The objective is to make the code:

- Easier to read
- Easier to maintain
- Easier to extend

### Improved Test

Instead of calling the method directly inside `assertEquals()`, separate the execution from the assertion.

```java
public class MathTest {

    @Test
    public void testSumAddsTwoNumbersCorrectly() {
        Math math = new Math();

        int result = math.sum(2, 3);

        assertEquals(5, result);
    }
}
```

### Why is this better?

- Separates **execution** from **verification**.
- Makes debugging easier.
- Improves readability.
- Simplifies adding logging or additional assertions later.

> [!note]
> Refactoring should **never change the external behavior** of the code. All tests must continue to pass.

---

# Summary

The TDD workflow consists of three repeating steps:

| Phase       | Description                                                 |
| ----------- | ----------------------------------------------------------- |
| 🔴 Red      | Write a failing test.                                       |
| 🟢 Green    | Write the minimum code required to pass the test.           |
| 🔵 Refactor | Improve the implementation while keeping all tests passing. |

# Key Takeaways

- **TDD** follows the **Red → Green → Refactor** cycle.
- Always write a **failing test first**.
- During the **Green** phase, write only enough code to pass the test.
- **Refactor** only after all tests pass.
- Refactoring should improve readability and maintainability **without changing behavior**.
- Tests act as a safety net, allowing code to evolve confidently.
- TDD encourages small, incremental development with continuous feedback.
