# Overview

In the previous lesson, we learned the fundamentals of **Test-Driven Development (TDD)** and the **Red → Green → Refactor** cycle.

In this lesson, the focus is on **generalizing solutions** by expanding existing functionality through additional test cases while continuing to follow the TDD workflow.

> [!note]
> The objective is to gradually evolve the implementation by adding new test scenarios rather than trying to solve every possible case from the beginning.

---

# Recap: The TDD Cycle

The TDD workflow consists of three iterative steps:

## 🔴 Red

Write a **new failing test** that defines the next piece of required functionality.

## 🟢 Green

Write the **minimum amount of code** necessary to make the new test pass.

## 🔵 Refactor

Improve the code and tests while ensuring **all existing tests continue to pass**.

```text
🔴 Red
    ↓
🟢 Green
    ↓
🔵 Refactor
    ↺ Repeat
```

---

# Starting Point

We begin with the implementation created in the previous lesson.

## Existing Test

```java
public class MathTest {

    @Test
    public void testSumAddsTwoNumbersCorrectly() {
        Math math = new Math();

        int result = math.sum(2, 3);

        assertEquals(5, result);
    }
}
```

## Existing Implementation

```java
public class Math {

    public int sum(int a, int b) {
        return 5;
    }
}
```

Although the test passes, the implementation is **not generalized** because it always returns `5`.

---

# 🔴 Red Phase — Add a New Failing Test

To generalize the implementation, introduce another test case with different input values.

## Updated Test Class

```java
public class MathTest {

    @Test
    public void testSumAddsTwoNumbersCorrectly() {
        Math math = new Math();

        int result = math.sum(2, 3);

        assertEquals(5, result);
    }

    @Test
    public void testSumShouldAddTwoMoreNumbersCorrectly() {
        Math math = new Math();

        int result = math.sum(5, 6);

        assertEquals(11, result);
    }
}
```

### Why Add Another Test?

The original implementation works **only** for `2 + 3`.

Adding another test forces us to implement a **generic solution** rather than a hardcoded one.

### Expected Result

The new test fails.

```text
MathTest > testSumShouldAddTwoMoreNumbersCorrectly() FAILED

org.opentest4j.AssertionFailedError:
expected: <11>
but was: <5>
```

> [!important]
> A failing test is a success in TDD—it confirms that the current implementation does **not** satisfy the new requirement.

---

# 🟢 Green Phase — Generalize the Implementation

Now modify the implementation so that **all tests pass**.

## Updated Implementation

```java
public class Math {

    public int sum(int a, int b) {
        return a + b;
    }
}
```

Instead of returning a hardcoded value, the method now performs the actual addition.

### Test Result

```text
MathTest > testSumShouldAddTwoMoreNumbersCorrectly() PASSED
```

Both tests now pass successfully.

> [!tip]
> The Green phase is complete once **all tests pass**, not just the newly added one.

# 🔵 Refactor Phase — Improve the Tests

Although the implementation is already simple, the tests contain duplicated code.

Instead of creating separate test methods for every input combination, we can use **parameterized tests**.

---

# Parameterized Testing

A **parameterized test** allows a single test method to execute multiple times with different sets of input data.

Instead of writing many nearly identical test methods, we provide multiple test cases to one method.

## Benefits

- Reduces duplicate test code.
- Makes tests easier to maintain.
- Makes adding new test cases simple.
- Improves readability.

---

# Refactored Test Using Parameterized Tests

```java
public class MathTest {

    @ParameterizedTest
    @MethodSource("sumTestCases")
    public void testSumAddsTwoNumbersCorrectly(int a, int b, int expected) {

        Math math = new Math();

        int result = math.sum(a, b);

        assertEquals(expected, result);
    }

    private static Stream<Arguments> sumTestCases() {

        return Stream.of(
            Arguments.of(2, 3, 5),
            Arguments.of(5, 6, 11)
        );
    }
}
```

---

# Understanding the Refactored Test

## `@ParameterizedTest`

Marks the test as a parameterized test.

Instead of executing once, it runs **once for every set of supplied arguments**.

---

## `@MethodSource`

```java
@MethodSource("sumTestCases")
```

Specifies the method that supplies the test data.

The referenced method must be:

- `static`
- Return a supported source type (such as `Stream<Arguments>`)

---

## Test Data Provider

```java
private static Stream<Arguments> sumTestCases() {

    return Stream.of(
        Arguments.of(2, 3, 5),
        Arguments.of(5, 6, 11)
    );
}
```

Each `Arguments.of(...)` represents one test case.

| Input A | Input B | Expected |
|---------:|---------:|---------:|
| 2 | 3 | 5 |
| 5 | 6 | 11 |

The parameterized test executes once for every row.

---

# Execution Flow

```text
sumTestCases()

        │
        ▼

Arguments.of(2,3,5)
        │
        ▼
testSumAddsTwoNumbersCorrectly(2,3,5)

        │
        ▼

Arguments.of(5,6,11)
        │
        ▼
testSumAddsTwoNumbersCorrectly(5,6,11)
```

---

# Why Parameterized Tests?

Without parameterized tests:

```java
@Test
void testCase1() { ... }

@Test
void testCase2() { ... }

@Test
void testCase3() { ... }

@Test
void testCase4() { ... }
```

With parameterized tests:

```java
@ParameterizedTest
@MethodSource("sumTestCases")
void testSum(int a, int b, int expected) {
    ...
}
```

Adding another test case only requires adding another `Arguments.of(...)`.

```java
Arguments.of(10, 15, 25)
```

No additional test methods are needed.

---

# Generalization in TDD

Generalization means evolving your implementation **only when new tests require it**.

Example progression:

```text
Test:
2 + 3 = 5

↓

Implementation:
return 5;

↓

New Test:
5 + 6 = 11

↓

Generalized Implementation:
return a + b;
```

> [!important]
> Don't generalize prematurely. Let each new failing test guide the evolution of your implementation.

---

# Key Takeaways

- TDD encourages gradual improvement through small iterations.
- New requirements should always begin with a **new failing test**.
- Generalize the implementation **only after a test demands it**.
- Write the minimum code necessary to satisfy all current tests.
- Refactor after all tests pass.
- **Parameterized tests** reduce duplication and make test suites easier to maintain.
- Parameterized tests execute the same logic using multiple sets of input data.
- A clean test suite is just as important as clean production code.
