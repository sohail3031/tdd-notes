# Overview

This lesson demonstrates how to apply the **Test-Driven Development (TDD)** mindset using a real-world example: implementing a `calculateTotal()` function for a shopping cart.

The goal is to understand how TDD guides the design of software by writing tests **before** writing implementation code.

Throughout this lesson, we'll follow the **Red → Green → Refactor** cycle while building a shopping cart that calculates the total price of items.

> [!note]
> This example uses **Java** and **JUnit**.

---

# Learning Objectives

By the end of this lesson, you should be able to:

- Design software by writing tests first.
- Let tests define the API and expected behavior.
- Implement only the code required to satisfy the tests.
- Continuously improve the implementation through refactoring.
- Use Java Streams to write cleaner aggregation logic.

---

# TDD Workflow

```text
🔴 Red
Write a failing test.

        ↓

🟢 Green
Write the minimum implementation
required to make the test pass.

        ↓

🔵 Refactor
Improve the implementation
without breaking existing tests.

        ↺ Repeat
```

# Problem Statement

Implement a method:

```java
double calculateTotal(List<CartItem> items)
```

The method should calculate the total cost of all items in a shopping cart.

Each `CartItem` contains:

- Name
- Price
- Quantity

The total price of a single item is:

```text
price × quantity
```

The cart total is the sum of all item totals.

---

# 🔴 Red Phase — First Failing Test

Before writing any implementation, define the expected behavior.

## Scenario

An **empty cart** should return a total of **0**.

### Test

```java
public class CartTest {

    @Test
    public void calculateTotalShouldReturnZeroForEmptyCart() {

        List<CartItem> items = List.of();

        Cart cart = new Cart();

        double total = cart.calculateTotal(items);

        assertEquals(0, total, 0.001);
    }
}
```

### Understanding the Test

The test defines the API before it exists.

```java
cart.calculateTotal(items)
```

This immediately answers several design questions:

- What is the method called?
- What input does it accept?
- What does it return?

> [!important]
> In TDD, writing tests first helps design a clean and intuitive interface before implementation.

---

# Why Use a Delta?

```java
assertEquals(0, total, 0.001);
```

Floating-point values (`double`) can contain tiny precision errors.

Instead of checking for an exact match, JUnit allows a **delta (tolerance)**.

```
Expected ± Delta
```

Example:

```
Expected = 1.5

Actual = 1.5000001

Delta = 0.001

✅ Test Passes
```

# 🟢 Green Phase — Minimal Implementation

Write only enough code to satisfy the current test.

```java
public class Cart {

    public double calculateTotal(List<CartItem> items) {
        return 0;
    }
}
```

Although this implementation isn't useful yet, it satisfies the only requirement we currently have.

> [!tip]
> Resist the urge to implement future functionality. Let future tests drive future code.

---

# 🔴 Red Phase — Add Another Test

Now introduce another requirement.

A cart containing one item should return the correct total.

### Test

```java
@Test
public void calculateTotalShouldReturnCorrectTotalForSingleItem() {

    List<CartItem> items = List.of(
        new CartItem("Apple", 0.5, 3)
    );

    Cart cart = new Cart();

    double total = cart.calculateTotal(items);

    assertEquals(1.5, total, 0.001);
}
```

### Expected Result

```
Apple

Price = 0.5

Quantity = 3

Total = 0.5 × 3 = 1.5
```

The test now fails because the implementation always returns `0`.

---

# 🟢 Green Phase — Make It Pass

Implement only enough logic for the current test.

```java
public class Cart {

    public double calculateTotal(List<CartItem> items) {

        if (!items.isEmpty()) {
            return items.get(0).getPrice() * items.get(0).getQuantity();
        }

        return 0;
    }
}
```

This implementation is intentionally limited.

It works because there is only one item in the cart.

Both tests now pass.

---

# 🔵 Refactor Phase

The implementation works, but it can be made more readable.

Instead of repeatedly accessing the first item:

```java
items.get(0)
```

Store it in a variable.

```java
public class Cart {

    public double calculateTotal(CartItem[] items) {

        if (items.length > 0) {

            CartItem item = items[0];

            return item.getPrice() * item.getQuantity();
        }

        return 0;
    }
}
```

This makes the code easier to understand and maintain.

---

# Creating the `CartItem` Class

Each cart item should encapsulate its own data.

```java
public class CartItem {

    private final String name;
    private final double price;
    private final int quantity;

    public CartItem(String name, double price, int quantity) {
        this.name = name;
        this.price = price;
        this.quantity = quantity;
    }

    public double getPrice() {
        return price;
    }

    public int getQuantity() {
        return quantity;
    }
}
```

## Benefits

- Immutable object (`final` fields)
- Better encapsulation
- Cleaner code
- Easy to extend later

# 🔴 Red Phase — Generalize Further

The current implementation only works for one item.

Let's introduce another test.

```java
@Test
public void calculateTotalShouldReturnCorrectTotalForMultipleItems() {

    List<CartItem> items = List.of(
        new CartItem("Apple", 0.5, 3),
        new CartItem("Banana", 0.3, 2)
    );

    Cart cart = new Cart();

    double total = cart.calculateTotal(items);

    assertEquals(2.1, total, 0.001);
}
```

### Calculation

| Item | Price | Quantity | Total |
|------|------:|---------:|------:|
| Apple | 0.5 | 3 | 1.5 |
| Banana | 0.3 | 2 | 0.6 |

**Grand Total = 2.1**

The test fails because the implementation only calculates the first item.

---

# 🟢 Green Phase — Generalize the Implementation

Use a loop to process every cart item.

```java
public class Cart {

    public double calculateTotal(List<CartItem> items) {

        double total = 0;

        for (CartItem item : items) {
            total += item.getPrice() * item.getQuantity();
        }

        return total;
    }
}
```

Now every item contributes to the final total.

All tests pass again.

---

# 🔵 Refactor — Using Java Streams

The loop works, but Java Streams provide a cleaner solution for aggregation.

```java
public class Cart {

    public double calculateTotal(List<CartItem> items) {

        return items.stream()
                .mapToDouble(item -> item.getPrice() * item.getQuantity())
                .sum();
    }
}
```

---

# Understanding the Stream Pipeline

## `stream()`

Converts the collection into a stream.

```java
items.stream()
```

---

## `mapToDouble()`

Transforms each `CartItem` into its total price.

```java
item -> item.getPrice() * item.getQuantity()
```

Example:

```
Apple

0.5 × 3

↓

1.5
```

---

## `sum()`

Adds all values together.

```
1.5
+
0.6
------
2.1
```

---

# Stream Execution Flow

```text
List<CartItem>

        │
        ▼

stream()

        │
        ▼

mapToDouble()

        │
        ▼

price × quantity

        │
        ▼

sum()

        │
        ▼

Total Price
```

---

# Why Streams?

Traditional loop:

```java
double total = 0;

for (CartItem item : items) {
    total += item.getPrice() * item.getQuantity();
}

return total;
```

Java Stream:

```java
return items.stream()
        .mapToDouble(item -> item.getPrice() * item.getQuantity())
        .sum();
```

### Advantages

- Less boilerplate
- More expressive
- Easier to read
- Functional programming style
- Ideal for aggregation operations

# Key Takeaways

- Write tests **before** writing implementation.
- Let tests drive the design of your API.
- Implement only enough code to satisfy the current tests.
- Add new tests whenever new requirements arise.
- Refactor only after all tests pass.
- Small, incremental improvements lead to clean and maintainable code.
- Java Streams provide a concise and expressive way to perform aggregation operations.
- Tests serve as a safety net, enabling confident refactoring without breaking functionality.
