# Overview

As applications grow, classes often depend on other components (e.g., databases, loggers, APIs, file systems). These **dependencies** can make unit testing difficult because tests may rely on external systems.

This lesson focuses on **managing dependencies** in TDD using:

- **Interfaces**
- **Dependency Injection (DI)**
- **Mock Objects**

These techniques allow each unit to be tested **in isolation**, resulting in faster, more reliable, and maintainable tests.

> [!note]
> Examples in this lesson use **Java** and **JUnit**.

---

# Why Manage Dependencies?

A **dependency** is any object or service that another class relies on to perform its work.

Examples of common dependencies:

- Database
- Logger
- REST API
- Email service
- File system
- Message queue

Without proper abstraction, unit tests become dependent on external systems, making them:

- Slow
- Fragile
- Difficult to maintain

---

# The Goal of Unit Testing

A unit test should verify **only one unit of code**.

It should **not** test:

- The database
- The logging framework
- The network
- External APIs

Instead, these dependencies should be replaced with **test doubles** (e.g., mocks or stubs).

```text
Bad Unit Test

UserManager
     │
     ├── Database
     ├── Logger
     ├── Network
     └── File System

Many things can fail ❌
```

```text
Good Unit Test

UserManager
     │
     └── Mock Logger

Only UserManager is being tested ✅
```

---

# Using Interfaces for Abstraction

An **interface** defines a contract that classes must implement.

Instead of depending on a concrete class, depend on an interface.

## `ILogger` Interface

```java
public interface ILogger {

    void log(String message);

}
```

This interface specifies **what** a logger can do without specifying **how** it does it.

Any class implementing `ILogger` can now be used interchangeably.

---

# Benefits of Interfaces

- Loose coupling
- Easier testing
- Better maintainability
- Swappable implementations
- Supports dependency injection

---

# Dependency Injection (DI)

Instead of creating dependencies inside a class, **inject** them from the outside.

## Without Dependency Injection

```text
UserManager

	↓

creates Logger itself
```

```text
UserManager
      │
      ▼
Real Logger
```

The dependency is tightly coupled.

---

## With Dependency Injection

```text
UserManager
      ▲
      │
  ILogger
      ▲
      │
Injected from outside
```

The implementation can easily be replaced.

---

# Building `UserManager`

The logger is injected through the constructor.

```java
public class UserManager {

    private final ILogger logger;
    private final List<String> users = new ArrayList<>();

    public UserManager(ILogger logger) {
        this.logger = logger;
    }

    public void addUser(String username) {

        users.add(username);

        logger.log("User " + username + " added");
    }

    public List<String> getUsers() {
        return users;
    }
}
```

---

# How It Works

When a user is added:

1. Store the username.
2. Log the action.

```text
addUser("john")

        │
        ▼

users.add("john")

        │
        ▼

logger.log("User john added")
```

Notice that `UserManager` has **no idea** what kind of logger it is using.

It only knows that the object implements `ILogger`.

---

# Creating a Mock Logger

During testing, we don't want to use a real logging framework.

Instead, create a **MockLogger**.

```java
public class MockLogger implements ILogger {

    private final List<String> logs = new ArrayList<>();

    @Override
    public void log(String message) {
        logs.add(message);
    }

    public List<String> getLogs() {
        return logs;
    }
}
```

Instead of writing to a console or log file, the mock stores messages in memory.

---

# Why Use a Mock?

A mock allows us to verify interactions.

Instead of asking:

> "Did the logger write to a file?"

We ask:

> "Was the correct log message sent?"

This keeps the test focused on the behavior of `UserManager`.

---

# Testing `UserManager`

## Test 1 - User Is Added Successfully

```java
@Test
public void shouldAddUserSuccessfully() {

    MockLogger mockLogger = new MockLogger();

    UserManager userManager = new UserManager(mockLogger);

    userManager.addUser("john");

    assertTrue(userManager.getUsers().contains("john"));
}
```

### What This Test Verifies

```text
addUser("john")

	↓

User exists in users list

✅ PASS
```

The logger is irrelevant for this test.

---

## Test 2 - Correct Log Message Is Generated

```java
@Test
public void shouldLogMessageWhenUserIsAdded() {

    MockLogger mockLogger = new MockLogger();

    UserManager userManager = new UserManager(mockLogger);

    userManager.addUser("john");

    assertEquals(
        List.of("User john added"),
        mockLogger.getLogs()
    );
}
```

### What This Test Verifies

```text
addUser("john")

	↓

Mock Logger

	↓

Stored message

	↓

"User john added"

✅ PASS
```

Instead of checking an external logging system, we inspect the mock object.

# Understanding the Design

```text
               ILogger
                  ▲
                  │
      ┌───────────┴───────────┐
      │                       │
      │                       │
Real Logger             MockLogger
      │                       │
      └───────────┬───────────┘
                  │
                  ▼
             UserManager
```

Because `UserManager` depends only on the **interface**, we can swap implementations without changing its code.

# Applying the TDD Cycle

## 🔴 Red

Write tests first.

Example:

- User should be added.
- Logger should receive a message.

Tests fail because `UserManager` doesn't exist yet.

---

## 🟢 Green

Implement the minimum functionality.

```text
add user

	+

log message
```

All tests pass.

---

## 🔵 Refactor

Improve the code while keeping all tests green.

Possible refactoring ideas:

- Improve naming.
- Extract reusable methods.
- Improve readability.
- Simplify logic.

The tests ensure that behavior remains unchanged.

# Advantages of Dependency Injection

| Without DI | With DI |
|------------|---------|
| Tightly coupled | Loosely coupled |
| Difficult to test | Easy to test |
| Hard to replace dependencies | Dependencies are swappable |
| Requires real services | Can use mocks or stubs |
| Less maintainable | More maintainable |

---

# Interfaces + Dependency Injection + Mocking

These three concepts work together.

```text
Interface

	↓

Defines a contract

	↓

Dependency Injection

	↓

Supplies the implementation

	↓

Mock Object

	↓

Replaces the real implementation during testing
```

This combination makes unit testing simple and reliable.

---

# Key Takeaways

- A **dependency** is any external component a class relies on.
- Unit tests should isolate the class being tested from external systems.
- **Interfaces** define contracts, allowing multiple interchangeable implementations.
- **Dependency Injection (DI)** supplies dependencies from outside the class, reducing coupling.
- **Mock objects** replace real dependencies during testing and allow verification of interactions.
- `UserManager` depends on the `ILogger` interface rather than a concrete logger implementation.
- TDD still follows the **Red → Green → Refactor** cycle when working with dependencies.
- Combining **interfaces**, **dependency injection**, and **mocking** leads to cleaner, more modular, and more testable code.
