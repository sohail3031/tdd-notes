# Task

The goal of this exercise is to verify that calling `notifyUser()` on `NotificationService` causes the `send()` method of `RealNotificationSender` to be called **exactly once** with the correct `Notification` object.

This exercise demonstrates how to use a **Spy** with **Mockito** to observe interactions between objects.

### Expected Behavior

When:

```java
notificationService.notifyUser("user1", "Hi!");
```

is called, the service should send a `Notification` containing:

- **User ID:** `"user1"`
- **Message:** `"Hi!"`
- **Priority:** `Priority.LOW`

# Implementing the Test

The first step is to call the method under test:

```java

```

Then we use Mockito's `verify()` method:

```java
verify(senderSpy, times(1)).send(...);
```

The `argThat()` matcher allows us to inspect the `Notification` object passed to `send()`.

```java
verify(senderSpy, times(1)).send(argThat(notification ->

    notification.getMessage().equals("Hi!") &&

));
```

# Final Test

```java
import org.junit.jupiter.api.Test;

import org.mockito.InjectMocks;
import org.mockito.Spy;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.mockito.Mockito.*;

import static org.mockito.ArgumentMatchers.argThat;

import org.junit.jupiter.api.extension.ExtendWith;

@ExtendWith(MockitoExtension.class)
public class NotificationServiceTest {

    static {
        // Work around Byte Buddy not officially supporting Java 25 yet
        System.setProperty("net.bytebuddy.experimental", "true");
    }

    @Spy
    private RealNotificationSender senderSpy = new RealNotificationSender();

    @InjectMocks
    private NotificationService notificationService;

    @Test
    public void testNotifyUserSendsNotificationWithLowPriorityForShortMessages() throws Exception {
        // Act
        notificationService.notifyUser("user1", "Hi!");

        // Assert
        verify(senderSpy, times(1)).send(argThat(notification ->
            notification.getUserId().equals("user1") &&
            notification.getMessage().equals("Hi!") &&
            notification.getPriority() == Priority.LOW
        ));
    }
}
```

> **Note:** The `net.bytebuddy.experimental` system property was added in the exercise's final code as a workaround for Byte Buddy compatibility with Java 25. It is unrelated to the Spy concept itself.

# Understanding the Verification

The most important part of the test is:

```java
verify(senderSpy, times(1)).send(argThat(notification ->
    notification.getUserId().equals("user1") &&
    notification.getMessage().equals("Hi!") &&
    notification.getPriority() == Priority.LOW
));
```

Let's break it down.

## `verify()`

```java
verify(senderSpy, times(1))
```

This tells Mockito:

> Verify that the specified interaction with `senderSpy` happened exactly once.

---

## `send()`

```java
.send(...)
```

We are specifically verifying the `send()` method.

Therefore, the test fails if `send()`:

- Was never called.
- Was called more than once.
- Was called with an incorrect argument.

---

## `argThat()`

```java
argThat(notification -> ...)
```

`argThat()` allows us to define a condition that the argument must satisfy.

In this case, the `Notification` must contain:

```java
notification.getUserId().equals("user1")
```

```java
notification.getMessage().equals("Hi!")
```

and:

```java
notification.getPriority() == Priority.LOW
```

All three conditions must be true.

# Why Use a Spy?

The important point is that `senderSpy` is based on the real `RealNotificationSender`.

```java
@Spy
private RealNotificationSender senderSpy = new RealNotificationSender();
```

The Spy allows us to:

- Use the real object's behavior.
- Observe calls made to the object.
- Verify how the object was used.

The real sender implementation is:

```java
public class RealNotificationSender implements INotificationSender {

    @Override
    public void send(Notification notification) {
        System.out.println("Sending notification: " + notification);
    }
}
```

Because this is a Spy, the real `send()` implementation can still execute unless specifically stubbed.

---

# Important Distinction: Testing State vs. Testing Interaction

This exercise demonstrates **interaction testing**.

We are not only interested in the return value of:

```java
notificationService.notifyUser(...)
```

The method returns `void`.

Instead, we care about what happened to the dependency.

Specifically:

```text
NotificationService
       |
       | send(Notification)
       ↓
RealNotificationSender
```

The Spy allows us to observe this interaction.

We can therefore verify:

```text
Was send() called?
       ↓
Was it called exactly once?
       ↓
Was the correct Notification passed?
```

# Test Double Comparison

At this point, we have covered three important types of test doubles.

|Test Double|Purpose|
|---|---|
|**Dummy**|Satisfies a dependency without providing meaningful behavior|
|**Stub**|Provides predefined responses|
|**Spy**|Records and verifies interactions|

### Dummy

Used when we simply need an object to satisfy a dependency.

```java
DummyLogger dummyLogger = new DummyLogger();
```

### Stub

Used when we need to control what a dependency returns.

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, Condition.Sunny));
```

### Spy

Used when we need to observe how a dependency is called.

```java
verify(senderSpy, times(1)).send(...);
```

# Key Takeaways

- A **Spy** allows us to observe interactions with a real object.
- Mockito provides the `@Spy` annotation for creating Spies.
- `@InjectMocks` can inject the Spy into the class under test.
- `verify()` checks whether an interaction occurred.
- `times(1)` verifies that a method was called exactly once.
- `argThat()` allows us to verify the contents of complex arguments.
- Spies are particularly useful for testing **side effects and interactions**.
- In this example, the test verifies that `NotificationService` correctly delegates the notification to `RealNotificationSender`.
- The implementation should remain minimal during the **Green** phase of TDD.
