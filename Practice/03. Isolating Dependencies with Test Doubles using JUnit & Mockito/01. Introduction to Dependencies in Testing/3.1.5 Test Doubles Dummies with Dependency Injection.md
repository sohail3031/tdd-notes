# Task

This exercise builds on the previous example of using **dummies** to test an email service.

The goal is to implement a complete test suite for a `NewsletterService` while reinforcing the concept of **test doubles**, specifically **dummies**.

The exercise demonstrates how dependencies can be:

- Defined as interfaces.
- Injected into a class through its constructor.
- Replaced with dummy implementations during testing.

## Requirements

### Implementation File

The `NewsletterService` implementation should:

1. Define an `ILogger` interface.
2. Define an `INewsletterSender` interface.
3. Receive `ILogger` and `INewsletterSender` as dependencies.
4. Call the `logger` when sending a newsletter.
5. Call the `newsletterSender` to send the newsletter.

### Test File

The test setup should:

1. Create a `DummyLogger`.
2. Create a `DummyNewsletterSender`.
3. Pass both dummies to the `NewsletterService` constructor.

The tests should continue to pass without implementing any real logging or newsletter-sending functionality.

---

# Interfaces

The dependencies of `NewsletterService` are defined as interfaces.

## ILogger

`ILogger` defines the logging operation required by `NewsletterService`.

```java
package interfaces;

public interface ILogger {

    void log(String message);
}
````

## INewsletterSender

`INewsletterSender` defines the operation required to send a newsletter.

```java
package interfaces;

public interface INewsletterSender {

    void send(String to, String subject, String body);
}
```

Using interfaces allows `NewsletterService` to depend on abstractions rather than concrete implementations.

---

# NewsletterService

`NewsletterService` receives `ILogger` and `INewsletterSender` through its constructor.

```java
import interfaces.*;

public class NewsletterService {

    private ILogger iLogger;
    private INewsletterSender iNewsletterSender;

    public NewsletterService(
        ILogger iLogger,
        INewsletterSender iNewsletterSender
    ) {
        this.iLogger = iLogger;
        this.iNewsletterSender = iNewsletterSender;
    }

    public boolean sendNewsletter(String to, String subject, String body) {
        if (to == null || to.isEmpty() || !to.contains("@")) {
            return false;
        }

        if (subject == null || subject.isEmpty()) {
            return false;
        }

        if (body == null || body.isEmpty() || body.length() > 1000) {
            return false;
        }

        iLogger.log("Sending of the newsletter");
        iNewsletterSender.send(to, subject, body);

        return true;
    }
}
```

## Dependency Injection

The dependencies are passed into the constructor:

```java
public NewsletterService(
    ILogger iLogger,
    INewsletterSender iNewsletterSender
)
```

This is an example of **constructor dependency injection**.

Instead of creating the dependencies inside `NewsletterService`, the class receives them from the outside.

This makes the class easier to test because the tests can provide dummy implementations.

# Creating the Dummies

## DummyLogger

`DummyLogger` implements the `ILogger` interface.

The `log()` method does not need to perform any real logging because logging is not the focus of these tests.

```java
package dummies;

import interfaces.ILogger;

public class DummyLogger implements ILogger {

    @Override
    public void log(String message) {
        // Do nothing
    }
}
```

## DummyNewsletterSender

`DummyNewsletterSender` implements the `INewsletterSender` interface.

The `send()` method does not need to send a real newsletter.

```java
package dummies;

import interfaces.INewsletterSender;

public class DummyNewsletterSender implements INewsletterSender {

    @Override
    public void send(String to, String subject, String body) {
        // Do nothing
    }
}
```

These classes are **dummies** because their purpose is primarily to satisfy the dependencies required by `NewsletterService`.

---

# Using the Dummies in the Test

The test class creates instances of both dummy dependencies:

```java
private DummyLogger dummyLogger = new DummyLogger();
private DummyNewsletterSender dummyNewsletterSender =
    new DummyNewsletterSender();
```

These dependencies are passed to `NewsletterService` during test setup:

```java
@BeforeEach
public void setUp() {
    // Arrange
    newsletterService = new NewsletterService(
        dummyLogger,
        dummyNewsletterSender
    );
}
```

`@BeforeEach` ensures that a properly initialized `NewsletterService` is created before every test.

---

# NewsletterServiceTest

```java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

import dummies.*;

public class NewsletterServiceTest {

    private NewsletterService newsletterService;

    private DummyLogger dummyLogger = new DummyLogger();

    private DummyNewsletterSender dummyNewsletterSender =
        new DummyNewsletterSender();

    @BeforeEach
    public void setUp() {
        // Arrange
        newsletterService = new NewsletterService(
            dummyLogger,
            dummyNewsletterSender
        );
    }

    @Test
    public void acceptValidNewsletterParameters() {
        // Act
        boolean result = newsletterService.sendNewsletter(
            "subscriber@example.com",
            "Latest Updates",
            "Check out our latest newsletter!"
        );

        // Assert
        assertTrue(result);
    }

    @Test
    public void rejectInvalidEmailAddress() {
        // Act
        boolean result = newsletterService.sendNewsletter(
            "invalid-email",
            "Latest Updates",
            "Check out our latest newsletter!"
        );

        // Assert
        assertFalse(result);
    }

    @Test
    public void rejectEmptySubject() {
        // Act
        boolean result = newsletterService.sendNewsletter(
            "subscriber@example.com",
            "",
            "Check out our latest newsletter!"
        );

        // Assert
        assertFalse(result);
    }

    @Test
    public void rejectContentExceeding2000Characters() {
        // Arrange
        String longContent = new String(new char[2001])
            .replace('\0', 'a');

        // Act
        boolean result = newsletterService.sendNewsletter(
            "subscriber@example.com",
            "Latest Updates",
            longContent
        );

        // Assert
        assertFalse(result);
    }
}
```

# How the Dependencies Work

The dependency relationship can be visualized as:

```text
NewsletterService
       |
       +------------------+
       |                  |
       v                  v
    ILogger       INewsletterSender
       |                  |
       v                  v
 DummyLogger     DummyNewsletterSender
```

The test provides the dummy implementations to the service:

```text
NewsletterServiceTest
       |
       +------------------+
       |                  |
       v                  v
 DummyLogger     DummyNewsletterSender
       |                  |
       +--------+---------+
                |
                v
       NewsletterService
```

The service can therefore execute without requiring real logging or newsletter-sending functionality.

# Key Lesson

A **dummy** is a type of test double used primarily to satisfy a dependency.

In this exercise:

- `ILogger` defines the logging dependency.
    
- `INewsletterSender` defines the newsletter-sending dependency.
    
- `DummyLogger` provides a dummy implementation of `ILogger`.
    
- `DummyNewsletterSender` provides a dummy implementation of `INewsletterSender`.
    
- `NewsletterService` receives these dependencies through constructor injection.
    
- The tests focus on the validation behavior of `NewsletterService`.
    

> [!NOTE]  
> The dummies do not contain real functionality. Their purpose is to allow `NewsletterService` to operate during the unit tests without depending on real external services.

## Important Concept

The main idea is that **dependencies should be defined as interfaces and supplied from outside the class**.

This makes it possible for tests to replace real implementations with test doubles such as dummies.

```text
Real Application

NewsletterService
    |
    +--> Real Logger
    |
    +--> Real Newsletter Sender


Unit Test

NewsletterService
    |
    +--> DummyLogger
    |
    +--> DummyNewsletterSender
```

This approach keeps unit tests isolated and prevents them from depending on real external functionality.

> [!TIP]  
> In future exercises, other types of test doubles such as **stubs, mocks, and fakes** can provide more useful behavior than simple dummies.
