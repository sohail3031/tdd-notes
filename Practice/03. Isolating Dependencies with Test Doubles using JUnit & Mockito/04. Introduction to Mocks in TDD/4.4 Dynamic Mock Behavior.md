# Task

In this task, we learn how to create **custom mock behavior** using Mockito's `thenAnswer()` method.

Unlike `thenReturn()`, which always returns a predefined value, `thenAnswer()` allows the return value to depend on the arguments passed to the mocked method.

The objective is to simulate different exchange rates based on the destination currency and verify that `PricingService` correctly handles each scenario.

---

# Learning Objectives

By completing this task, you will learn how to:

- Create dynamic mock behavior using `thenAnswer()`.    
- Access method arguments using Mockito's `InvocationOnMock`.
- Return different values depending on input parameters.
- Test multiple scenarios using a single mock configuration.
- Verify multiple interactions with a mocked dependency.
- Combine output verification with interaction verification.

# Scenario

The `IExchangeRateService` dependency provides exchange rates.

For this exercise, the mock should return:

|Destination Currency|Exchange Rate|
|---|--:|
|`EUR`|`0.85`|
|`GBP`|`0.73`|
|Any other currency|`1.0`|

For example:

```text
USD → EUR = 0.85
USD → GBP = 0.73
```

---

# Why Use `thenAnswer()`?

A simple mock configuration using `thenReturn()` looks like this:

```java
when(mockExchangeRateService.getRate("USD", "EUR"))
        .thenReturn(0.85);
```

This works well when the mocked method should always return the same value for a specific input.

However, if we want the mock to behave differently depending on the arguments, we can use:

```java
thenAnswer(invocation -> {
    // Custom logic
});
```

This allows us to inspect the arguments passed to the mocked method and dynamically determine the return value.

# Understanding `anyString()`

The mock configuration uses:

```java
anyString()
```

for both arguments:

```java
when(mockExchangeRateService.getRate(anyString(), anyString()))
```

This means that Mockito should intercept calls to `getRate()` regardless of which `String` values are passed.

The custom behavior inside `thenAnswer()` will then determine what value should be returned.

---

# Accessing Method Arguments

The `getRate()` method has two parameters:

```java
getRate(String fromCurrency, String toCurrency)
```

Their indexes are:

```text
Argument Index 0 → fromCurrency
Argument Index 1 → toCurrency
```

Therefore:

```java
String fromCurrency = invocation.getArgument(0);
```

retrieves the source currency.

And:

```java
String toCurrency = invocation.getArgument(1);
```

retrieves the destination currency.

In this exercise, we only need the destination currency:

```java
String toCurrency = invocation.getArgument(1);
```

# Final Test Implementation

## `PricingServiceTest.java`

```java
import org.junit.jupiter.api.Test;

import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import org.junit.jupiter.api.extension.ExtendWith;

import static org.mockito.Mockito.*;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

@ExtendWith(MockitoExtension.class)
public class PricingServiceTest {

    @Mock
    private IExchangeRateService mockExchangeRateService;

    @InjectMocks
    private PricingService pricingService;

    @Test
    public void testConvertPriceUsesExchangeRate() throws Exception {

        // Arrange
        when(mockExchangeRateService.getRate("USD", "EUR"))
                .thenReturn(1.5);

        // Act
        double result =
                pricingService.convertPrice(100, "USD", "EUR");

        // Assert
        verify(mockExchangeRateService, times(1))
                .getRate("USD", "EUR");

        assertEquals(150.00, result);
    }

    @Test
    public void testConvertPriceWithSameCurrenciesDoesNotCallGetRate()
            throws Exception {

        // Arrange
        // No setup is needed because getRate() should not be called.

        // Act
        double result =
                pricingService.convertPrice(100, "USD", "USD");

        // Assert
        verify(mockExchangeRateService, never())
                .getRate(anyString(), anyString());

        assertEquals(100.00, result);
    }

    @Test
    public void testConvertPriceThrowsExceptionForNegativeAmount()
            throws Exception {

        // Arrange
        // No setup is needed because getRate() should not be called.

        // Act & Assert
        Exception exception = assertThrows(
                IllegalArgumentException.class,
                () -> pricingService.convertPrice(
                        -50,
                        "USD",
                        "EUR"
                )
        );

        assertEquals(
                "Amount cannot be negative",
                exception.getMessage()
        );

        verify(mockExchangeRateService, never())
                .getRate(anyString(), anyString());
    }

    @Test
    public void testConvertPriceHandlesDifferentExchangeRates()
            throws Exception {

        // Arrange
        when(mockExchangeRateService.getRate(
                anyString(),
                anyString()
        )).thenAnswer(invocation -> {

            // Argument index 1 represents toCurrency.
            String toCurrency =
                    invocation.getArgument(1);

            if ("EUR".equalsIgnoreCase(toCurrency)) {
                return 0.85;
            } else if ("GBP".equalsIgnoreCase(toCurrency)) {
                return 0.73;
            }

            // Default fallback exchange rate.
            return 1.0;
        });

        // Act
        double resultEUR =
                pricingService.convertPrice(
                        100,
                        "USD",
                        "EUR"
                );

        double resultGBP =
                pricingService.convertPrice(
                        100,
                        "USD",
                        "GBP"
                );

        // Assert

        // 100 × 0.85 = 85.00
        assertEquals(85.00, resultEUR);

        // 100 × 0.73 = 73.00
        assertEquals(73.00, resultGBP);

        // Verify each currency pair was requested exactly once.
        verify(mockExchangeRateService, times(1))
                .getRate("USD", "EUR");

        verify(mockExchangeRateService, times(1))
                .getRate("USD", "GBP");
    }
}
```

# `thenReturn()` vs `thenAnswer()`

## `thenReturn()`

Use `thenReturn()` when the mock should return a fixed value.

```java
when(mockExchangeRateService.getRate("USD", "EUR"))
        .thenReturn(0.85);
```

This is simple and ideal for predictable behavior.

---

## `thenAnswer()`

Use `thenAnswer()` when the return value depends on the method arguments or when custom logic is required.

```java
when(mockExchangeRateService.getRate(
        anyString(),
        anyString()
)).thenAnswer(invocation -> {

    String toCurrency =
            invocation.getArgument(1);

    if ("EUR".equalsIgnoreCase(toCurrency)) {
        return 0.85;
    }

    return 1.0;
});
```

This allows the mock to simulate multiple scenarios with one configuration.

---

# Why Use a Default Return Value?

The final line of the mock implementation is:

```java
return 1.0;
```

This acts as a fallback.

For example:

```java
pricingService.convertPrice(100, "USD", "CAD");
```

Since `CAD` is neither `EUR` nor `GBP`, the mock returns:

```text
1.0
```

The conversion becomes:

```text
100 × 1.0 = 100
```

This prevents the mock from returning an unexpected value when an unhandled currency is used.

---

# Verifying Multiple Interactions

The test performs two calls:

```java
pricingService.convertPrice(100, "USD", "EUR");
```

and:

```java
pricingService.convertPrice(100, "USD", "GBP");
```

Therefore, we verify both interactions separately:

```java
verify(mockExchangeRateService, times(1))
        .getRate("USD", "EUR");

verify(mockExchangeRateService, times(1))
        .getRate("USD", "GBP");
```

This verifies:

```text
getRate("USD", "EUR") → Called once

getRate("USD", "GBP") → Called once
```

As a result, the total number of `getRate()` calls is:

```text
1 + 1 = 2 calls
```

---

# Alternative Total Interaction Verification

You could also verify that `getRate()` was called exactly twice in total:

```java
verify(mockExchangeRateService, times(2))
        .getRate(anyString(), anyString());
```

However, this alone does not verify the specific currency pairs.

A stronger test verifies both:

1. The total number of interactions.
    
2. The arguments used for each interaction.
    

For example:

```java
verify(mockExchangeRateService, times(2))
        .getRate(anyString(), anyString());

verify(mockExchangeRateService, times(1))
        .getRate("USD", "EUR");

verify(mockExchangeRateService, times(1))
        .getRate("USD", "GBP");
```

For this exercise, verifying each specific currency pair is sufficient to establish that the method was called twice with the expected arguments.

# Existing `PricingService` Implementation

The current implementation already supports this test:

```java
public class PricingService {

    private final IExchangeRateService exchangeRateService;

    public PricingService(
            IExchangeRateService exchangeRateService
    ) {
        this.exchangeRateService =
                exchangeRateService;
    }

    public double convertPrice(
            double amount,
            String fromCurrency,
            String toCurrency
    ) throws Exception {

        if (amount < 0) {
            throw new IllegalArgumentException(
                    "Amount cannot be negative"
            );
        }

        if (fromCurrency.equalsIgnoreCase(toCurrency)) {
            return Math.round(amount * 100.0) / 100.0;
        }

        double rate =
                exchangeRateService.getRate(
                        fromCurrency,
                        toCurrency
                );

        return Math.round(
                amount * rate * 100.0
        ) / 100.0;
    }
}
```

No changes are required to `PricingService` for this task because the new behavior exists entirely within the test's mock configuration.

# Key Concept: The Mock Is Acting Like a Custom Implementation

The `thenAnswer()` block effectively creates dynamic behavior similar to manually writing:

```java
public double getRate(
        String fromCurrency,
        String toCurrency
) {

    if ("EUR".equalsIgnoreCase(toCurrency)) {
        return 0.85;
    }

    if ("GBP".equalsIgnoreCase(toCurrency)) {
        return 0.73;
    }

    return 1.0;
}
```

However, this behavior exists only inside the test.

The real `IExchangeRateService` implementation is not required.

This allows the unit test to remain:

- Fast
- Isolated
- Deterministic
- Independent of external APIs

# Key Mockito Concepts Used

## `@Mock`

```java
@Mock
private IExchangeRateService mockExchangeRateService;
```

Creates a mock implementation of the dependency.

---

## `when()`

```java
when(mockExchangeRateService.getRate(
        anyString(),
        anyString()
))
```

Defines which mocked method call should be intercepted.

---

## `thenAnswer()`

```java
.thenAnswer(invocation -> {
    // Dynamic behavior
});
```

Allows custom logic to determine the return value.

---

## `invocation.getArgument()`

```java
invocation.getArgument(1);
```

Retrieves an argument passed to the mocked method.

```text
Index 0 → fromCurrency
Index 1 → toCurrency
```

---

## `verify()`

```java
verify(mockExchangeRateService, times(1))
        .getRate("USD", "EUR");
```

Verifies that the mocked method was called with the expected arguments.

# Key Takeaways

- `thenReturn()` is useful for fixed mock behavior.
- `thenAnswer()` is useful when mock behavior depends on method arguments.
- `invocation.getArgument(index)` allows access to arguments passed to a mocked method.
- Argument index `0` represents the first parameter.
- Argument index `1` represents the second parameter.
- A single `thenAnswer()` configuration can simulate multiple scenarios.
- Mocks allow unit tests to simulate external dependencies without calling real services.
- Verify both the returned results and the interactions with mocked dependencies.
- Dynamic mock behavior is useful for testing multiple input combinations.
- The production `PricingService` code does not need to change because this task only adds additional test coverage.
