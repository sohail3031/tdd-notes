# Task

The goal of this exercise is to make the `conditions` property in `WeatherData` strongly typed by replacing the `String` type with a Java `Condition` enum.

Previously, weather conditions were represented as arbitrary strings such as:

```java
"sunny"
```

```java
"thunderstorm"
```

Using an enum restricts the possible values to a predefined set of valid weather conditions.

---

# Objectives

The refactoring should:

1. Create a new `Condition` enum.
2. Define the allowed weather conditions inside the enum.
3. Change `WeatherData.conditions` from `String` to `Condition`.
4. Update the `WeatherData` constructor and getter.
5. Update the test helper method to accept a `Condition`.
6. Update all tests to use enum values.
7. Update `WeatherAlertService` to compare the condition using the enum.
8. Preserve the existing test behavior.

---

# Why Use an Enum?

Before the refactoring, `conditions` was a `String`:

```java
private final String conditions;
```

This allowed any string to be passed:

```java
new WeatherData(20, "sunny");
```

but also allowed invalid values:

```java
new WeatherData(20, "banana");
```

There is nothing in the `String` type preventing this.

With an enum:

```java
private final Condition conditions;
```

only values defined in `Condition` can be used.

For example:

```java
Condition.Sunny
```

```java
Condition.Clear
```

```java
Condition.Thunderstorm
```

This provides **compile-time type safety**.

# Refactoring WeatherData

## Before

Previously, `WeatherData` stored the condition as a `String`:

```java
private final String conditions;
```

and the constructor accepted a `String`:

```java
public WeatherData(int temperature, String conditions) {
    this.temperature = temperature;
    this.conditions = conditions;
}
```

The getter also returned a `String`:

```java
public String getConditions() {
    return conditions;
}
```

---

## After

Change all three to use `Condition`.

```java
public class WeatherData {

    private final int temperature;
    private final Condition conditions;

    public WeatherData(int temperature, Condition conditions) {
        this.temperature = temperature;
        this.conditions = conditions;
    }

    public int getTemperature() {
        return temperature;
    }

    public Condition getConditions() {
        return conditions;
    }
}
```

Now the compiler ensures that only a valid `Condition` can be passed to `WeatherData`.

# Updating WeatherAlertService

Previously, the service compared the condition as a string:

```java
weather.getConditions().equalsIgnoreCase("thunderstorm")
```

After introducing the enum, this is no longer necessary.

The condition can be compared directly:

```java
weather.getConditions() == Condition.Thunderstorm
```

Because enum constants are unique instances, `==` is the standard way to compare enum values in Java.

The complete implementation is:

```java
public class WeatherAlertService {

    private final IWeatherService weatherService;

    public WeatherAlertService(IWeatherService weatherService) {
        this.weatherService = weatherService;
    }

    public String shouldSendAlert(String location) {
        WeatherData weather =
            weatherService.getCurrentWeather(location);

        if (weather.getTemperature() > 35) {
            return "Extreme heat warning. Stay hydrated!";
        } else if (weather.getTemperature() < 0) {
            return "Freezing warning. Stay warm!";
        } else if (weather.getConditions() == Condition.Thunderstorm) {
            return "Storm warning. Stay indoors if possible!";
        }

        return null;
    }
}
```

# Type Safety Improvement

The main benefit of this refactoring is that invalid conditions can no longer be passed accidentally.

### Before

```java
new WeatherData(20, "thunderstorm");
```

Any string was allowed:

```java
new WeatherData(20, "something-invalid");
```

### After

```java
new WeatherData(20, Condition.Thunderstorm);
```

Only values from the `Condition` enum are accepted.

For example:

```java
new WeatherData(20, Condition.Sunny);
new WeatherData(20, Condition.Clear);
new WeatherData(20, Condition.Thunderstorm);
new WeatherData(20, Condition.Snowy);
```

An arbitrary string is no longer accepted by the constructor.

---

# String Comparison vs. Enum Comparison

## Before

```java
weather.getConditions().equalsIgnoreCase("thunderstorm")
```

The code had to perform a string comparison.

## After

```java
weather.getConditions() == Condition.Thunderstorm
```

The comparison is now between two `Condition` values.

This is simpler and safer because the compiler already knows that `getConditions()` returns a `Condition`.

---

# Why `==` Works for Enums

Java enum constants are unique instances.

Therefore, this is appropriate:

```java
weather.getConditions() == Condition.Thunderstorm
```

For example:

```java
Condition condition = Condition.Thunderstorm;

if (condition == Condition.Thunderstorm) {
    // Storm condition
}
```

This is the normal Java pattern for comparing enum constants.

The main changes are:

```text
Before:

WeatherData
    |
    └── conditions: String
            |
            └── "sunny"
            └── "snowy"
            └── "thunderstorm"


After:

WeatherData
    |
    └── conditions: Condition
            |
            ├── Condition.Sunny
            ├── Condition.Clear
            ├── Condition.Thunderstorm
            └── Condition.Snowy
```

The dependency structure and test behavior remain unchanged. Only the representation of weather conditions becomes more strongly typed.

# Key Takeaways

- Java enums provide a fixed set of allowed values.
- Enums provide stronger type safety than arbitrary strings.
- `WeatherData.conditions` should use `Condition` instead of `String`.
- The `WeatherData` constructor and getter must also use `Condition`.
- Mockito test helpers should accept the enum type.
- Tests should use values such as `Condition.Sunny` and `Condition.Thunderstorm`.
- Enum constants can be compared using `==`.
- String-specific methods such as `equalsIgnoreCase()` are no longer necessary.
- Be careful with enum spelling: use `Condition.Thunderstorm`, not `Condition.Thunderstrom`.
- This refactoring changes the data representation while preserving the existing behavior of `WeatherAlertService`.
