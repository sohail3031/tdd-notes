# Task

In this exercise, we extend the `WeatherAlertService` to handle a new extreme weather condition: a **thunderstorm**.

The goal is to:

1. Use a Mockito test double to simulate weather data.    
2. Add a test for a storm warning.
3. Update `WeatherAlertService` to return the correct storm warning.
4. Refactor repeated stubbing logic into a helper method named `stubWeatherData`.

The expected storm alert is:

> `Storm warning. Stay indoors if possible!`

---

# Objectives

By completing this exercise, we should be able to:

- Configure different weather conditions using Mockito.    
- Add a new test case following the **Arrange-Act-Assert (AAA)** pattern.
- Extend the production code with the minimum logic required to pass the new test.
- Reduce duplicated test setup by extracting a reusable helper method.
- Understand how a Mockito mock can be used as a **stub** by configuring predefined return values.

# Refactor: Extract a Weather Stubbing Helper

The existing tests repeatedly use the same Mockito setup pattern:

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

and:

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(-5, "snowy"));
```

and for the storm scenario:

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(20, "thunderstorm"));
```

To reduce duplication, extract this behavior into a helper method.

## `stubWeatherData` Helper Method

```java
private void stubWeatherData(
        String location,
        int temperature,
        String conditions
) {
    when(weatherServiceMock.getCurrentWeather(location))
        .thenReturn(new WeatherData(temperature, conditions));
}
```

This helper method:

1. Receives the location.
2. Receives the temperature.
3. Receives the weather conditions.
4. Creates a `WeatherData` object.
5. Configures the Mockito mock to return that weather data.

The tests can now focus on the scenario being tested instead of repeating Mockito setup code.

# Green: Implement the Storm Warning

The `WeatherAlertService` must retrieve the weather data and check the conditions.

The storm warning should depend on the weather condition being `"thunderstorm"`.

```java
if ("thunderstorm".equals(weather.getConditions())) {
    return "Storm warning. Stay indoors if possible!";
}
```

> [!IMPORTANT]  
> The starter task specifies the condition as `"thunderstorm"`. The provided final code contains the misspelling `"thunderstrom"`. The correct spelling should be used consistently in both the test and implementation.

The alert should **not** depend on the temperature being exactly `20°C`. The test uses `20°C` as the scenario, but the business rule is based on the weather condition being a thunderstorm.

Therefore, this would be unnecessarily restrictive:

```java
if (weather.getTemperature() == 20
        && weather.getConditions().equals("thunderstorm")) {
    return "Storm warning. Stay indoors if possible!";
}
```

A thunderstorm can occur at temperatures other than `20°C`, so checking the condition alone better represents the requirement.

# Complete Test Class

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
public class WeatherAlertServiceTest {

    @Mock
    private IWeatherService weatherServiceMock;

    @InjectMocks
    private WeatherAlertService alertService;

    private void stubWeatherData(
            String location,
            int temperature,
            String conditions
    ) {
        when(weatherServiceMock.getCurrentWeather(location))
            .thenReturn(new WeatherData(temperature, conditions));
    }

    @Test
    public void testShouldReturnHeatWarningWhenTemperatureIsAbove35() {
        // Arrange
        stubWeatherData("London", 36, "sunny");

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Extreme heat warning. Stay hydrated!",
            alert
        );
    }

    @Test
    public void testShouldReturnFreezingWarningWhenTemperatureIsBelow0() {
        // Arrange
        stubWeatherData("London", -5, "snowy");

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Freezing warning. Stay warm!",
            alert
        );
    }

    @Test
    public void testShouldReturnStormWarningWhenConditionsAreThunderstorm() {
        // Arrange
        stubWeatherData("London", 20, "thunderstorm");

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Storm warning. Stay indoors if possible!",
            alert
        );
    }
}
```

# Complete WeatherAlertService Implementation

```java
public class WeatherAlertService {

    private final IWeatherService weatherService;

    public WeatherAlertService(IWeatherService weatherService) {
        this.weatherService = weatherService;
    }

    public String shouldSendAlert(String location) {
        WeatherData weather =
            weatherService.getCurrentWeather(location);

        if ("thunderstorm".equals(weather.getConditions())) {
            return "Storm warning. Stay indoors if possible!";
        }

        if (weather.getTemperature() > 35) {
            return "Extreme heat warning. Stay hydrated!";
        }

        if (weather.getTemperature() < 0) {
            return "Freezing warning. Stay warm!";
        }

        return null;
    }
}
```

# Why Use a Helper Method?

Without the helper method, every test must manually configure the mock:

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

With the helper method:

```java
stubWeatherData("London", 36, "sunny");
```

This makes the tests:

- More concise.
- Easier to read.
- Easier to maintain.
- More focused on the test scenario.

The helper also provides a descriptive abstraction for the repeated test setup.

The provided final implementation checks:

```java

        && weather.getConditions().equals("thunderstorm")) {
    return "Storm warning. Stay indoors if possible!";

```

This makes the implementation unnecessarily specific to the test data.

The requirement is to issue a storm warning when the conditions are `"thunderstorm"`.

Therefore, the preferred implementation is:

This implementation handles thunderstorms regardless of temperature.

> [!TIP]  
> Do not overfit production code to the exact values used in a test. Tests provide examples of expected behavior, while the implementation should reflect the actual business rule.

# Why Use `"thunderstorm".equals(...)`?

This form:

```java
"thunderstorm".equals(weather.getConditions())
```

is safer than:

```java
weather.getConditions().equals("thunderstorm")
```

If `weather.getConditions()` is `null`, the second version throws a `NullPointerException`.

Calling `equals()` on the known non-null string avoids this problem:

```java
"thunderstorm".equals(null);
```

returns:

```text
false
```

# Key Takeaways

- Mockito can be used to configure predefined dependency responses.
- `when()` and `thenReturn()` allow a mock to behave like a **stub**.
- The `stubWeatherData()` helper method reduces duplicated test setup.
- The storm test follows the **Arrange-Act-Assert (AAA)** pattern.
- A storm warning should be based on the `"thunderstorm"` condition.
- The temperature of `20°C` is part of the test scenario and should not necessarily become part of the business rule.
- Use the correct spelling: `"thunderstorm"`.
- Avoid overfitting implementation logic to specific test values.
- A safe string comparison is:

```java
"expectedValue".equals(actualValue)
```

- Refactoring test setup improves readability without changing test behavior.
