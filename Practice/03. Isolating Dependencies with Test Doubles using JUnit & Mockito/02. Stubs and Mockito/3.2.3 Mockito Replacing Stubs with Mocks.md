# Task

In this exercise, we replace the hand-built `WeatherServiceStub` with a Mockito-based test double.

The goal is to use Mockito to create a mock of the `IWeatherService` interface and configure predefined weather responses for each test.

This approach makes the tests more flexible and reduces the need to maintain custom stub classes.

---

# Objectives

The objectives of this exercise are to:

1. Remove the hand-built `WeatherServiceStub`.    
2. Create a Mockito mock for `IWeatherService`.
3. Inject the mock into `WeatherAlertService`.
4. Configure predefined weather responses using `when()` and `thenReturn()`.
5. Verify that the heat and freezing alert tests continue to pass.

---

# Before: Hand-Built Stub

Previously, the test contained a custom implementation of `IWeatherService`.

```java
class WeatherServiceStub implements IWeatherService {

    private WeatherData currentWeather =
        new WeatherData(20, "sunny");

    public void setWeather(
        int temperature,
        String conditions
    ) {
        this.currentWeather =
            new WeatherData(temperature, conditions);
    }

    @Override
    public WeatherData getCurrentWeather(String location) {
        return currentWeather;
    }
}
```

The tests configured the weather using:

```java
weatherService.setWeather(36, "sunny");
```

Although this approach works, the custom stub must be written and maintained manually.

Mockito can create a test double dynamically, allowing us to configure the required behavior directly in each test.

# Using Mockito

The key Mockito concepts used in this exercise are:

- `@ExtendWith(MockitoExtension.class)`
- `@Mock`
- `@InjectMocks`
- `when()`
- `thenReturn()`

## Required Imports

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.when;
```

> [!NOTE]  
> When using `@Mock` together with `@ExtendWith(MockitoExtension.class)`, Mockito creates and initializes the mock automatically. Therefore, an explicit `mock(IWeatherService.class)` call is unnecessary.

---

# Mockito Extension

The Mockito extension integrates Mockito with JUnit 5.

```java
@ExtendWith(MockitoExtension.class)
public class WeatherAlertServiceTest {
```

This enables Mockito annotations such as:

- `@Mock`
- `@InjectMocks`

Without the Mockito extension, these annotations will not be initialized automatically by JUnit 5.

---

# Creating the IWeatherService Mock

Instead of creating a `WeatherServiceStub`, define a mock field.

```java
@Mock
private IWeatherService weatherServiceMock;
```

Mockito creates a mock implementation of `IWeatherService`.

The mock can then be configured differently for each test.

For example:

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

This means:

> When `getCurrentWeather("London")` is called, return `new WeatherData(36, "sunny")`.

---

# Injecting the Mock

The mock dependency can be injected into `WeatherAlertService` using `@InjectMocks`.

```java
@InjectMocks
private WeatherAlertService alertService;
```

Mockito detects that `WeatherAlertService` requires an `IWeatherService` dependency through its constructor and injects `weatherServiceMock`.

The equivalent manual setup would be:

```java
IWeatherService weatherServiceMock =
    mock(IWeatherService.class);

WeatherAlertService alertService =
    new WeatherAlertService(weatherServiceMock);
```

However, when using both `@Mock` and `@InjectMocks`, Mockito performs this initialization automatically.

> [!TIP]  
> Use either annotation-based initialization or manual initialization. Avoid mixing both approaches unnecessarily.

# Complete Refactored Test Class

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
public class WeatherAlertServiceTest {

    @Mock
    private IWeatherService weatherServiceMock;

    @InjectMocks
    private WeatherAlertService alertService;

    @Test
    public void testShouldReturnHeatWarningWhenTemperatureIsAbove35() {
        // Arrange
        when(weatherServiceMock.getCurrentWeather("London"))
            .thenReturn(new WeatherData(36, "sunny"));

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Extreme heat warning. Stay hydrated!",
            alert
        );
    }

    @Test
    public void testShouldReturnFreezingWarningWhenTemperatureIsBelow0() {
        // Arrange
        when(weatherServiceMock.getCurrentWeather("London"))
            .thenReturn(new WeatherData(-5, "snowy"));

        // Act
        String alert = alertService.shouldSendAlert("London");

        // Assert
        assertEquals(
            "Freezing warning. Stay warm!",
            alert
        );
    }
}
```

# Important Correction to the Final Code

The provided final code uses both:

```java
@Mock
private IWeatherService wIWeatherServiceMock;

@InjectMocks
private WeatherAlertService alertService;
```

and manual initialization inside `@BeforeEach`:

```java
wIWeatherServiceMock = mock(IWeatherService.class);
alertService = new WeatherAlertService(wIWeatherServiceMock);
```

This is redundant.

When using:

```java
@ExtendWith(MockitoExtension.class)
```

together with:

```java
@Mock
```

and:

```java
@InjectMocks
```

Mockito already creates the mock and injects it into `WeatherAlertService`.

Therefore, the cleaner solution is to remove:

- The `@BeforeEach` method.
- The `mock()` import.
- The manual calls to `mock()` and `new WeatherAlertService()`.

The annotation-based version shown above is the preferred implementation for this exercise.

# WeatherAlertService

The production code remains unchanged.

```java
public class WeatherAlertService {

    private final IWeatherService weatherService;

    public WeatherAlertService(
        IWeatherService weatherService
    ) {
        this.weatherService = weatherService;
    }

    public String shouldSendAlert(String location) {
        WeatherData weather =
            weatherService.getCurrentWeather(location);

        if (weather.getTemperature() > 35) {
            return "Extreme heat warning. Stay hydrated!";
        } else if (weather.getTemperature() < 0) {
            return "Freezing warning. Stay warm!";
        }

        return null;
    }
}
```

# Hand-Built Stub vs. Mockito

|Hand-Built Stub|Mockito|
|---|---|
|Requires a custom class|No custom implementation required|
|Requires methods such as `setWeather()`|Behavior is configured with `when()` and `thenReturn()`|
|State must be managed manually|Responses are configured directly|
|More code for each custom dependency|Less boilerplate|
|Useful for simple, explicit behavior|Flexible for different test scenarios|

### Hand-Built Stub

```java
weatherService.setWeather(36, "sunny");
```

### Mockito-Based Test Double

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

Both approaches provide controlled data to the system under test.

# Is This Technically a Stub or a Mock?

Mockito creates an object commonly called a **mock**:

```java
@Mock
private IWeatherService weatherServiceMock;
```

However, in these tests, it is being used to provide predefined return values:

```java
when(weatherServiceMock.getCurrentWeather("London"))
    .thenReturn(new WeatherData(36, "sunny"));
```

No interaction is verified using methods such as:

```java
verify(weatherServiceMock).getCurrentWeather("London");
```

Therefore, conceptually, the Mockito test double is serving the role of a **stub** because its purpose is to provide controlled responses.

> [!IMPORTANT]  
> `@Mock` describes how Mockito creates the test double. Whether it behaves conceptually as a mock or a stub depends on how it is used in the test.

# Key Concepts

## `@Mock`

Creates a Mockito test double.

```java
@Mock
private IWeatherService weatherServiceMock;
```

## `@InjectMocks`

Creates the system under test and injects suitable mocks into it.

```java
@InjectMocks
private WeatherAlertService alertService;
```

## `when()`

Defines the method call that should be stubbed.

```java
when(weatherServiceMock.getCurrentWeather("London"))
```

## `thenReturn()`

Defines the value that should be returned.

```java
.thenReturn(new WeatherData(36, "sunny"));
```

## `MockitoExtension`

Enables annotation-based Mockito support in JUnit 5.

```java
@ExtendWith(MockitoExtension.class)
```

# Key Takeaways

- Mockito can replace hand-built test doubles with dynamically created mocks.
- `@Mock` creates the `IWeatherService` test double.
- `@InjectMocks` injects the mock into `WeatherAlertService`.
- `when()` and `thenReturn()` define predefined responses.
- The custom `WeatherServiceStub` is no longer required.
- Mockito reduces boilerplate and makes it easier to configure different scenarios.
- When using `@Mock` and `@InjectMocks` with `MockitoExtension`, manual initialization is unnecessary.
- Although Mockito creates a **mock**, it is functioning as a **stub** in this exercise because it provides predefined return values without verifying interactions.
