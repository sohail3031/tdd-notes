# Task Objective

In the previous refactoring, grade-related behavior was moved from `GradeAnalyzer` into `Student`.

This improved the design by eliminating `GradeAnalyzer`, but it introduced another problem: the `Student` class now manages both:

- Student information
- Student grade collection and grade-related operations

This creates another form of excessive responsibility.

The goal of this refactoring is to extract the grade-management responsibilities into a dedicated `StudentGradeCollection` class.

### Goals

- Create a new `StudentGradeCollection` class.
- Move the grade collection and grade-related operations from `Student` into it.
- Move the following responsibilities:
  - `addGrade()`
  - `calculateFinalGrade()`
  - `getFailedAssignments()`
  - Grade list storage
- Make `Student` delegate grade-related operations to `StudentGradeCollection`.
- Preserve the existing public behavior of `Student`.
- Ensure all existing tests continue to pass.

---

# Why Extract `StudentGradeCollection`?

The `Student` class currently contains:

```java
private List<StudentGrade> grades;
````

and is responsible for:

```text
Student
├── Student information
│   ├── id
│   └── name
│
└── Grade management
    ├── Store grades
    ├── Add grades
    ├── Calculate final grade
    └── Find failed assignments
```

The grade-related responsibilities are closely related to each other and can be grouped into a dedicated collection class.

The new design becomes:

```text
Student
├── id
├── name
└── StudentGradeCollection
      ├── grades
      ├── addGrade()
      ├── calculateFinalGrade()
      └── getFailedAssignments()
```

This improves **cohesion** because `StudentGradeCollection` becomes responsible for everything related to managing a collection of `StudentGrade` objects.

---

# What Is Being Extracted?

The following field moves from `Student`:

```java
private List<StudentGrade> grades;
```

The following methods move to `StudentGradeCollection`:

```java
public List<StudentGrade> getGrades()
```

```java
public void addGrade(StudentGrade grade)
```

```java
public double calculateFinalGrade()
```

```java
public List<StudentGrade> getFailedAssignments()
```

The `Student` class will then delegate these operations to the new collection object.

# Step 1: Create `StudentGradeCollection`

Create a new class:

```text
StudentGradeCollection.java
```

It owns the list of grades:

```java
private List<StudentGrade> grades;
```

Initialize the collection in the constructor:

```java
public StudentGradeCollection() {
    this.grades = new ArrayList<>();
}
```

# Final `StudentGradeCollection.java`

```java
import java.util.ArrayList;
import java.util.List;
import java.util.stream.Collectors;

public class StudentGradeCollection {
    private List<StudentGrade> grades;

    public StudentGradeCollection() {
        this.grades = new ArrayList<>();
    }

    public List<StudentGrade> getGrades() {
        return grades;
    }

    public void addGrade(StudentGrade grade) {
        grades.add(grade);
    }

    public double calculateFinalGrade() {
        if (grades.isEmpty()) return 0;

        double totalEarned = 0;
        double totalPossible = 0;

        for (StudentGrade grade : grades) {
            totalEarned += grade.getScoreWithLatePenalty();
            totalPossible += grade.getTotalPoints();
        }

        return (totalEarned / totalPossible) * 100;
    }

    public List<StudentGrade> getFailedAssignments() {
        return grades.stream()
                .filter(grade ->
                        (grade.getScore() / grade.getTotalPoints()) < 0.6)
                .collect(Collectors.toList());
    }
}
```

# Step 2: Update `Student`

The `Student` class no longer needs to directly manage a `List<StudentGrade>`.

Instead, it owns a `StudentGradeCollection`:

```java
private StudentGradeCollection gradeCollection;
```

Initialize it in the constructor:

```java
this.gradeCollection = new StudentGradeCollection();
```

The `Student` methods now delegate to the collection.

---

# Delegation

### Adding a grade

Instead of:

```java
grades.add(grade);
```

`Student` delegates:

```java
gradeCollection.addGrade(grade);
```

### Calculating the final grade

Instead of performing the calculation itself:

```java
return gradeCollection.calculateFinalGrade();
```

### Finding failed assignments

Instead of filtering the grades itself:

```java
return gradeCollection.getFailedAssignments();
```

This is called **delegation**.

`Student` provides a convenient interface to callers while the specialized collection handles the actual grade-management logic.

---

# Final `Student.java`

```java
import java.util.List;

public class Student {
    private String id;
    private String name;
    private StudentGradeCollection gradeCollection;

    public Student(String id, String name) {
        this.id = id;
        this.name = name;
        this.gradeCollection = new StudentGradeCollection();
    }

    public String getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public List<StudentGrade> getGrades() {
        return gradeCollection.getGrades();
    }

    public void addGrade(StudentGrade grade) {
        gradeCollection.addGrade(grade);
    }

    public double calculateFinalGrade() {
        return gradeCollection.calculateFinalGrade();
    }

    public List<StudentGrade> getFailedAssignments() {
        return gradeCollection.getFailedAssignments();
    }
}
```

# Why Keep These Methods on `Student`?

A question might arise:

> If the grade logic belongs in `StudentGradeCollection`, why does `Student` still have `addGrade()`, `calculateFinalGrade()`, and `getFailedAssignments()`?

Because `Student` is the public abstraction that callers interact with.

For example:

```java
student.addGrade(grade);
```

is more natural than requiring callers to know about the internal collection:

```java
student.getGradeCollection().addGrade(grade);
```

The `Student` class therefore acts as a **facade/delegator** for its grade collection.

The important distinction is:

```text
Student
    ↓ delegates
StudentGradeCollection
    ↓ manages
StudentGrade objects
```

`Student` no longer contains the grade-management implementation.

# Why This Is an Extract Class Refactoring

This task is an example of the **Extract Class** refactoring.

The original `Student` class contained a group of closely related responsibilities:

```text
Grade collection responsibilities
├── grades
├── addGrade()
├── calculateFinalGrade()
└── getFailedAssignments()
```

These responsibilities are extracted into:

```java
StudentGradeCollection
```

The original class then delegates to the new class.

### Extract Class Pattern

```text
Before:

Student
├── Student data
└── Grade collection logic


After:

Student
├── Student data
└── StudentGradeCollection

StudentGradeCollection
└── Grade collection logic
```

# What Happens to the Tests?

An important part of this refactoring is that the existing tests can remain unchanged.

For example:

```java
Student student = new Student("2", "Jane Smith");

student.addGrade(failingGrade);

List<StudentGrade> failedAssignments =
        student.getFailedAssignments();
```

The test does not need to know that `Student` now delegates to `StudentGradeCollection`.

The public behavior remains the same.

This is a key benefit of encapsulation.

---

# TDD Perspective

The existing tests act as a safety net.

We are changing the internal design while keeping the external behavior unchanged.

### Before refactoring

```text
Test
 ↓
Student
 ↓
grades
```

### After refactoring

```text
Test
 ↓
Student
 ↓
StudentGradeCollection
 ↓
grades
```

The test still interacts with `Student`.

Therefore, the tests verify that the refactoring has not changed the observable behavior.

---

# Red-Green-Refactor

```text
RED
 ↓
Existing tests define expected behavior
 ↓
REFACTOR
 ↓
Create StudentGradeCollection
 ↓
Move grade-related state and behavior
 ↓
Make Student delegate to StudentGradeCollection
 ↓
GREEN
 ↓
All existing tests pass
```

The important point is that we are not changing the business rules.

For example, the failed-assignment rule remains:

```java
(grade.getScore() / grade.getTotalPoints()) < 0.6
```

A grade of exactly 60% still passes:

```text
60 / 100 = 0.60
0.60 < 0.60 → false
```

A grade of 50% still fails:

```text
50 / 100 = 0.50
0.50 < 0.60 → true
```

The refactoring only changes **where the logic lives**.

This task is part of a sequence of related refactorings.

```text

      ↓

```

### 3. Extract Class

`Student` became too responsible for grade management.

The grade-related responsibilities are now extracted into:

```text

```

The progression is:

```text

      ↓
Move Method
      ↓
Remove unnecessary GradeAnalyzer
      ↓

      ↓

      ↓

```

This demonstrates an important lesson in refactoring:

> Fixing one code smell can sometimes reveal another design problem.

# Design Improvement

The final architecture has three clear levels of responsibility:

```text
Student
│
│ owns
▼
StudentGradeCollection
│
│ manages
▼
StudentGrade
```

### `Student`

Answers:

> Who is the student?

It owns:

- ID
- Name
- Grade collection

### `StudentGradeCollection`

Answers:

> How are this student's grades managed?

It owns:

- Grade collection
- Adding grades
- Final-grade calculation
- Failed-assignment filtering

### `StudentGrade`

Answers:

> What is the information and behavior of one grade?

It owns:

- Assignment ID
- Score
- Total points
- Submission date
- Late-status calculation
- Late penalty calculation

# Key Takeaways

- **Extract Class** is useful when one class contains a group of related responsibilities that can be separated into a cohesive unit.
- `Student` was becoming responsible for both student information and grade collection management.
- `StudentGradeCollection` provides a natural home for grade collection behavior.
- `Student` delegates grade operations instead of implementing them.
- Delegation allows the public API of `Student` to remain unchanged.
- Existing tests can continue to verify behavior without knowing about the internal refactoring.
- This improves **cohesion** and reduces the amount of grade-management logic directly contained in `Student`.
- The design now follows a clear responsibility hierarchy:

```text
Student
   ↓
StudentGradeCollection
   ↓
StudentGrade
```

## Main Principle

> **A class should have a focused set of responsibilities, and related collection behavior can often be extracted into a specialized collection class.**

In this refactoring, `Student` represents the student, while `StudentGradeCollection` represents and manages the student's collection of grades.
