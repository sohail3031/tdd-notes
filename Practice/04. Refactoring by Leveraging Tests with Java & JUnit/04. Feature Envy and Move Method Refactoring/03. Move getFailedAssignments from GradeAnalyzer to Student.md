# Task Objective

Refactor the `getFailedAssignments()` method so that it is moved from the `GradeAnalyzer` class into the `Student` class.

The existing `GradeAnalyzer` class does not add meaningful value because it only interacts with the `Student` object's data. Since `getFailedAssignments()` deals exclusively with a student's grades, the behavior belongs directly in `Student`.

### Goals

- Move `getFailedAssignments()` from `GradeAnalyzer` to `Student`.
- Update the tests to call `student.getFailedAssignments()`.
- Remove the unnecessary `GradeAnalyzer` class.
- Preserve all existing behavior.
- Ensure all tests continue to pass.

---

## Why Refactor `getFailedAssignments()`?

The original implementation was:

```java
public List<StudentGrade> getFailedAssignments() {
    return student.getGrades().stream()
            .filter(grade -> (grade.getScore() / grade.getTotalPoints()) < 0.6)
            .collect(Collectors.toList());
}
````

This method:

1. Gets the grades from `Student`.
2. Processes those grades.
3. Determines which assignments are below 60%.

The `GradeAnalyzer` class does not own any meaningful data or behavior. It simply delegates to `Student`.

This creates unnecessary indirection:

```text
Test
 ↓
GradeAnalyzer
 ↓
Student
 ↓
grades
```

After the refactoring:

```text
Test
 ↓
Student
 ↓
grades
```

The second design is simpler and gives `Student` responsibility for behavior involving its own grades.

---

# Original Design

## `Student`

`Student` already owns the grades:

```java
private List<StudentGrade> grades;
```

It also provides:

```java
public void addGrade(StudentGrade grade) {
    grades.add(grade);
}
```

and:

```java
public List<StudentGrade> getGrades() {
    return grades;
}
```

It already contains `calculateFinalGrade()`, which operates on the student's grades.

Therefore, `getFailedAssignments()` is also a natural responsibility for `Student`.

---

## Original `GradeAnalyzer`

```java
import java.util.List;
import java.util.stream.Collectors;

public class GradeAnalyzer {
    private Student student;

    public GradeAnalyzer(Student student) {
        this.student = student;
    }

    public List<StudentGrade> getFailedAssignments() {
        return student.getGrades().stream()
                .filter(grade -> (grade.getScore() / grade.getTotalPoints()) < 0.6)
                .collect(Collectors.toList());
    }
}
```

### Problem

`GradeAnalyzer` is essentially acting as a middleman.

It does not own the grades and does not provide meaningful analysis beyond operating directly on `Student`'s data.

This is an example of **Feature Envy**.

---

# Refactoring Strategy

Move the method directly into `Student`.

### Before

```java
GradeAnalyzer analyzer = new GradeAnalyzer(student);

List<StudentGrade> failedAssignments =
        analyzer.getFailedAssignments();
```

### After

```java
List<StudentGrade> failedAssignments =
        student.getFailedAssignments();
```

This removes the unnecessary `GradeAnalyzer` dependency.

# Step 1: Move the Method to `Student`

Add the required import:

```java
import java.util.stream.Collectors;
```

Then add `getFailedAssignments()` to `Student`:

```java
public List<StudentGrade> getFailedAssignments() {
    return grades.stream()
            .filter(grade -> (grade.getScore() / grade.getTotalPoints()) < 0.6)
            .collect(Collectors.toList());
}
```

The method now operates directly on the `grades` field.

# Final `Student.java`

```java
import java.util.ArrayList;
import java.util.List;
import java.util.stream.Collectors;

public class Student {
    private String id;
    private String name;
    private List<StudentGrade> grades;

    public Student(String id, String name) {
        this.id = id;
        this.name = name;
        this.grades = new ArrayList<>();
    }

    public String getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public List<StudentGrade> getGrades() {
        return grades;
    }

    public void addGrade(StudentGrade grade) {
        grades.add(grade);
    }

    public double calculateFinalGrade() {
        if (grades.isEmpty()) return 0;

        double totalEarned = 0;
        double totalPossible = 0;

        for (StudentGrade grade : grades) {
            totalEarned += grade.getScoreWithLatePenalty();
            totalPossible += grade.getTotalPoints();
        }

        return (totalEarned / totalPossible) * 100;
    }

    public List<StudentGrade> getFailedAssignments() {
        return grades.stream()
                .filter(grade -> (grade.getScore() / grade.getTotalPoints()) < 0.6)
                .collect(Collectors.toList());
    }
}
```

# Why This Improves Cohesion

**Cohesion** describes how closely related the responsibilities of a class are.

`Student` already:

- owns the student's grades,
- adds grades,
- exposes grades,
- calculates the student's final grade.

Adding:

```java
getFailedAssignments()
```

is highly cohesive because it also operates on the student's grades.

The resulting responsibility is:

```text
Student
├── Own student information
├── Manage grades
├── Calculate final grade
└── Find failed assignments
```

These responsibilities are closely related.

# Feature Envy Refactoring Chain

This exercise continues the Feature Envy refactoring from the previous tasks.

The overall progression is:

```text
Feature Envy
    ↓
Move behavior closer to the data it uses
    ↓
StudentGrade owns grade-specific behavior
    ↓
Student owns student-specific behavior
    ↓
GradeAnalyzer has no meaningful responsibility
    ↓
Delete GradeAnalyzer
```

This is a good example of progressively improving object-oriented design rather than trying to perform one large refactoring all at once.

# TDD Perspective

The existing tests provide the safety net for the refactoring.

The important thing is that the **expected behavior does not change**.

For example, this test:

```java
assertEquals(1, failedAssignments.size());
assertEquals("hw1", failedAssignments.get(0).getAssignmentId());
```

remains unchanged.

Only the way the behavior is accessed changes:

```java
// Before
analyzer.getFailedAssignments();
```

becomes:

```java
// After
student.getFailedAssignments();
```

This is a classic **behavior-preserving refactoring**.

### Red-Green-Refactor

```text
RED
 ↓
Existing tests establish the expected behavior
 ↓
REFACTOR
 ↓
Move getFailedAssignments() from GradeAnalyzer to Student
 ↓
Update test invocation
 ↓
Delete GradeAnalyzer
 ↓
GREEN
 ↓
All tests still pass
```

The assertions should remain the same because the purpose of this refactoring is to improve the design without changing functionality.

# Key Takeaways

- **Feature Envy** occurs when a method is more interested in another object's data than its own class.
- `getFailedAssignments()` was primarily interested in `Student`'s grades.
- The method belongs naturally in `Student`.
- Moving behavior closer to the data it operates on improves **cohesion**.
- Removing `GradeAnalyzer` eliminates unnecessary indirection.
- Tests should verify that behavior remains unchanged after refactoring.
- When a class has no meaningful responsibility after moving its behavior, consider deleting it.
- Refactoring does not necessarily mean adding more classes; sometimes good refactoring means **removing a class**.

## Final Design

```text
Student
├── id
├── name
├── grades
├── addGrade()
├── calculateFinalGrade()
└── getFailedAssignments()

StudentGrade
├── assignmentId
├── score
├── totalPoints
├── submittedDate
├── isLate()
└── getScoreWithLatePenalty()

GradeAnalyzer
└── Removed
```

### Main Principle

> **Keep behavior close to the data it operates on.**

In this case, `Student` owns the grades, so student-level operations such as calculating the final grade and finding failed assignments belong in `Student`.
