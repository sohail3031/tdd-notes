# Task Objective

The goal of this task is to refactor `GradeAnalyzer.java` to address the **Feature Envy** code smell.

Currently, `GradeAnalyzer` contains logic that is primarily concerned with the internal data of `StudentGrade`.

The refactoring will move that behavior into `StudentGrade`, improving:

- Encapsulation
- Cohesion
- Separation of concerns
- Maintainability
- Testability

### Required Refactoring

1. Add properties to the `StudentGrade` class.
2. Move the `dueDate` information into `StudentGrade`.
3. Provide a default due date.
4. Move late-submission detection into `StudentGrade`.
5. Move late-penalty calculation into `StudentGrade`.
6. Remove `isLateSubmission()` from `GradeAnalyzer`.
7. Update `GradeAnalyzer` to use the new `StudentGrade` behavior.
8. Update the tests without losing existing test coverage.

---

# 1. Original Design

Originally, `GradeAnalyzer` was responsible for examining the internal details of `StudentGrade`.

For example:

```java
if (isLateSubmission(grade)) {
    totalEarned += grade.getScore() * 0.9;
} else {
    totalEarned += grade.getScore();
}
````

The `isLateSubmission()` method also accessed `StudentGrade` data:

```java
private boolean isLateSubmission(StudentGrade grade) {
    LocalDate submissionDate = grade.getSubmittedDate();
    LocalDate dueDate = LocalDate.of(2024, 1, 1);

    return submissionDate.isAfter(dueDate);
}
```

This is a Feature Envy code smell because the logic is primarily concerned with `StudentGrade`.

---

# 2. Problems with the Original Design

`GradeAnalyzer` knows too much about how a `StudentGrade` works.

It knows:

- How to determine the due date.
- How to determine whether a submission is late.
- How to calculate the late penalty.
- How to access the submission date.
- How to access the score.

This creates unnecessary coupling between `GradeAnalyzer` and `StudentGrade`.

Ideally, `StudentGrade` should know how to answer questions about its own state.

For example:

```java
grade.isLateSubmission()
```

and:

```java
grade.getScoreWithLatePenalty()
```

This follows the principle:

> **Keep behavior close to the data it operates on.**

---

# 3. Refactoring `StudentGrade`

The first step is to add a `dueDate` property.

The original code had the due date hard-coded inside `GradeAnalyzer`:

```java
LocalDate dueDate = LocalDate.of(2024, 1, 1);
```

The refactored class provides a default value:

```java
public static final LocalDate DEFAULT_DUE_DATE =
        LocalDate.of(2024, 1, 1);
```

Each `StudentGrade` then starts with this default due date.

## Late Penalty Constant

The late penalty is also moved into `StudentGrade`:

```java
private static final double LATE_PENALTY_RATE = 0.9;
```

A value of `0.9` means that a late submission receives **90% of its original score**, which represents a **10% penalty**.

---

# 4. Refactored `StudentGrade`

```java
import java.time.LocalDate;

public class StudentGrade {

    // Default due date for assignments that don't specify one
    public static final LocalDate DEFAULT_DUE_DATE =
            LocalDate.of(2024, 1, 1);

    // Late penalty rate (10%)
    private static final double LATE_PENALTY_RATE = 0.9;

    private String assignmentId;
    private double score;
    private double totalPoints;
    private LocalDate submittedDate;
    private LocalDate dueDate = DEFAULT_DUE_DATE;

    public String getAssignmentId() {
        return assignmentId;
    }

    public void setAssignmentId(String assignmentId) {
        this.assignmentId = assignmentId;
    }

    public double getScore() {
        return score;
    }

    public void setScore(double score) {
        this.score = score;
    }

    public double getTotalPoints() {
        return totalPoints;
    }

    public void setTotalPoints(double totalPoints) {
        this.totalPoints = totalPoints;
    }

    public LocalDate getSubmittedDate() {
        return submittedDate;
    }

    public void setSubmittedDate(LocalDate submittedDate) {
        this.submittedDate = submittedDate;
    }

    public LocalDate getDueDate() {
        return dueDate;
    }

    public void setDueDate(LocalDate dueDate) {
        this.dueDate = dueDate;
    }

    /**
     * Returns true if this grade was submitted after its due date.
     * A submission exactly on the due date is NOT late.
     */
    public boolean isLateSubmission() {
        if (submittedDate == null || dueDate == null) {
            return false;
        }

        return submittedDate.isAfter(dueDate);
    }

    /**
     * Returns the score after applying the late penalty if applicable.
     * On-time submissions return the raw score.
     * Late submissions receive a 10% penalty.
     */
    public double getScoreWithLatePenalty() {
        return isLateSubmission()
                ? score * LATE_PENALTY_RATE
                : score;
    }
}
```

---

# 5. Why `isLateSubmission()` Belongs in `StudentGrade`

The method:

```java
public boolean isLateSubmission()
```

only needs information from the current `StudentGrade`:

- `submittedDate`
- `dueDate`

Therefore, `StudentGrade` is the natural place for this behavior.

Instead of:

```java
analyzer.isLateSubmission(grade)
```

we can now write:

```java
grade.isLateSubmission()
```

This improves encapsulation because the caller does not need to know how lateness is determined.

---

# 6. Why `getScoreWithLatePenalty()` Belongs in `StudentGrade`

The late penalty is also directly related to the grade itself.

The old code contained:

```java
if (isLateSubmission(grade)) {
    totalEarned += grade.getScore() * 0.9;
} else {
    totalEarned += grade.getScore();
}
```

The new design moves this responsibility into `StudentGrade`:

```java
public double getScoreWithLatePenalty() {
    return isLateSubmission()
            ? score * LATE_PENALTY_RATE
            : score;
}
```

Now `GradeAnalyzer` does not need to understand the penalty calculation.

It simply asks the grade for the appropriate score:

```java
grade.getScoreWithLatePenalty()
```

# 7. Refactored `GradeAnalyzer`

The `isLateSubmission()` method is removed completely.

`calculateFinalGrade()` becomes much simpler:

```java
import java.util.List;
import java.util.stream.Collectors;

public class GradeAnalyzer {

    private Student student;

    public GradeAnalyzer(Student student) {
        this.student = student;
    }

    public double calculateFinalGrade() {
        List<StudentGrade> grades = student.getGrades();

        if (grades.isEmpty()) {
            return 0;
        }

        double totalEarned = 0;
        double totalPossible = 0;

        for (StudentGrade grade : grades) {
            totalEarned += grade.getScoreWithLatePenalty();
            totalPossible += grade.getTotalPoints();
        }

        return (totalEarned / totalPossible) * 100;
    }

    public List<StudentGrade> getFailedAssignments() {
        return student.getGrades().stream()
                .filter(grade ->
                        (grade.getScore() / grade.getTotalPoints()) < 0.6)
                .collect(Collectors.toList());
    }
}
```

The important change is:

### Before

```java
if (isLateSubmission(grade)) {
    totalEarned += grade.getScore() * 0.9;
} else {
    totalEarned += grade.getScore();
}
```

### After

```java
totalEarned += grade.getScoreWithLatePenalty();
```

This is much easier to read and better encapsulates the grade-specific behavior.

---

# 8. What Happened to `getFailedAssignments()`?

The task specifically focuses on the due-date and late-penalty logic.

`getFailedAssignments()` still contains:

```java
.filter(grade ->
    (grade.getScore() / grade.getTotalPoints()) < 0.6)
```

This is another potential example of Feature Envy because `GradeAnalyzer` is calculating information using `StudentGrade`'s data.

However, it is **outside the scope of this particular refactoring step**.

A future refactoring could move this logic into `StudentGrade`, for example:

```java
public boolean isFailing() {
    return (score / totalPoints) < 0.6;
}
```

Then `GradeAnalyzer` could use:

```java
.filter(StudentGrade::isFailing)
```

This would further reduce Feature Envy.

> [!NOTE]  
> Do not make this additional refactoring unless the exercise specifically asks for it. In TDD/refactoring exercises, it is usually better to make one focused change at a time.

# 9. Updating the Tests

The existing tests continue to test the same externally observable behavior.

For example, the late-submission test still creates a late grade:

```java
StudentGrade lateGrade = new StudentGrade();

lateGrade.setAssignmentId("hw1");
lateGrade.setScore(90);
lateGrade.setTotalPoints(100);
lateGrade.setSubmittedDate(LocalDate.of(2024, 1, 5));
```

Because the default due date is:

```java
LocalDate.of(2024, 1, 1)
```

the grade is late.

Therefore:

```text
90 × 0.9 = 81
```

The on-time grade receives no penalty:

```text
80
```

The final calculation becomes:

```text
(81 + 80) / 200 × 100
= 80.5
```

The existing test therefore remains valid.

# 10. Important Boundary Case: Submission on Due Date

The test:

```java
testCalculateFinalGradeHandlesSubmissionExactlyOnDueDate()
```

checks an important boundary condition.

The submission date is:

```java
LocalDate.of(2024, 1, 1)
```

and the due date is also:

```java
LocalDate.of(2024, 1, 1)
```

The implementation uses:

```java
submittedDate.isAfter(dueDate)
```

Therefore:

```text
submittedDate > dueDate → late
submittedDate == dueDate → on time
submittedDate < dueDate → on time
```

This means a submission exactly on the due date is **not late**.

---

# 11. Why the Tests Are Still Important

The refactoring changes the internal structure but should not change the externally observable behavior.

The tests protect against accidentally changing:

- Empty-grade behavior
- Late-submission penalties
- On-time submissions
- Boundary conditions
- Perfect scores
- Zero scores
- Different assignment point values
- Failed-assignment behavior

This is an example of using TDD tests as a **safety net for refactoring**.

# 12. Refactoring Flow

The refactoring can be viewed as:

```text
Original Design

GradeAnalyzer
    |
    ├── reads StudentGrade data
    ├── determines due date
    ├── determines whether submission is late
    └── calculates late penalty


             ↓ Move Behavior


Refactored Design

GradeAnalyzer
    |
    └── aggregates grade scores

StudentGrade
    |
    ├── owns dueDate
    ├── determines whether it is late
    └── calculates score with late penalty
```

# 13. Feature Envy Before and After

|Before|After|
|---|---|
|`GradeAnalyzer` determines due date|`StudentGrade` owns `dueDate`|
|`GradeAnalyzer` determines lateness|`StudentGrade.isLateSubmission()`|
|`GradeAnalyzer` calculates late penalty|`StudentGrade.getScoreWithLatePenalty()`|
|`GradeAnalyzer` knows penalty details|`StudentGrade` encapsulates penalty|
|More detailed knowledge in analyzer|Simpler `GradeAnalyzer`|
|Higher coupling|Lower coupling|
|Lower cohesion|Better cohesion|

# 14. TDD Perspective

This refactoring follows the **Red → Green → Refactor** cycle.

### Red

Existing tests describe the expected behavior.

### Green

The original implementation satisfies the tests.

### Refactor

Move the grade-specific behavior into `StudentGrade` while preserving the existing behavior.

The tests should continue to pass.

The important principle is:

> **Refactoring changes the structure of the code, not its intended behavior.**

---

# Key Takeaways

- **Feature Envy** occurs when a method is overly interested in another object's data.
- `GradeAnalyzer` was responsible for too much `StudentGrade`-specific logic.
- The `dueDate` property belongs in `StudentGrade`.
- `isLateSubmission()` belongs in `StudentGrade` because it operates entirely on grade data.
- `getScoreWithLatePenalty()` belongs in `StudentGrade` because the penalty is part of how a grade is evaluated.
- `GradeAnalyzer` should focus on **aggregating grades**, not understanding the internal rules of an individual grade.
- Existing tests should continue to pass after the refactoring.
- `getFailedAssignments()` still contains some Feature Envy, but that is intentionally left for a future refactoring step.
- TDD provides a safety net that allows us to make structural improvements with confidence.

> [!IMPORTANT]  
> **Core principle:** Move behavior toward the data it primarily operates on. This generally improves cohesion, reduces unnecessary coupling, and makes the design easier to maintain.
