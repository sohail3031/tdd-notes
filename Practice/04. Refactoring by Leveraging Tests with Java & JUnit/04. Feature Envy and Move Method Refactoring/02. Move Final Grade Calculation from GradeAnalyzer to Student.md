# Task Objective

The goal of this task is to refactor the `calculateFinalGrade()` method from the `GradeAnalyzer` class into the `Student` class.

The reason for this refactoring is that `calculateFinalGrade()` operates entirely on a student's own grades.

The `Student` class:

- Owns the student's grades.
- Adds and manages grades.
- Already provides access to its grades.
- Is therefore the natural place for calculating the student's final grade.

Moving the method to `Student` improves:

- Encapsulation
- Cohesion
- Separation of responsibilities
- Readability
- Maintainability

It also raises an important design question:

> **Do we even need `GradeAnalyzer` anymore?**

After moving both `calculateFinalGrade()` and `getFailedAssignments()` into `Student`, there may be no meaningful responsibility left for `GradeAnalyzer`.

---

# 1. Original Design

Originally, `GradeAnalyzer` contained:

```java
public double calculateFinalGrade()
````

The method accessed:

```java
student.getGrades()
```

and then performed calculations on those grades.

```java
public double calculateFinalGrade() {
    List<StudentGrade> grades = student.getGrades();

    if (grades.isEmpty()) {
        return 0;
    }

    double totalEarned = 0;
    double totalPossible = 0;

    for (StudentGrade grade : grades) {
        totalEarned += grade.getScoreWithLatePenalty();
        totalPossible += grade.getTotalPoints();
    }

    return (totalEarned / totalPossible) * 100;
}
```

This is another example of **Feature Envy**.

`GradeAnalyzer` does not own the grades. `Student` does.

Therefore, `GradeAnalyzer` is performing behavior using data that belongs to `Student`.

---

# 2. Why Move the Method to `Student`?

The `Student` class already owns:

```java
private List<StudentGrade> grades;
```

It also manages that data through:

```java
public void addGrade(StudentGrade grade)
```

Therefore, calculating the final grade is naturally part of the `Student`'s responsibilities.

Instead of:

```java
GradeAnalyzer analyzer = new GradeAnalyzer(student);

double finalGrade = analyzer.calculateFinalGrade();
```

we can use:

```java
double finalGrade = student.calculateFinalGrade();
```

This is simpler and more object-oriented.

> [!IMPORTANT]  
> The class that owns the data should generally own the behavior that operates primarily on that data.

---

# 3. Move `calculateFinalGrade()` into `Student`

The method is moved directly into the `Student` class.

```java
/**
 * Computes the final grade as a percentage, applying late penalties
 * to individual grades where applicable. Returns 0 if there are no grades.
 */
public double calculateFinalGrade() {
    if (grades.isEmpty()) {
        return 0;
    }

    double totalEarned = 0;
    double totalPossible = 0;

    for (StudentGrade grade : grades) {
        totalEarned += grade.getScoreWithLatePenalty();
        totalPossible += grade.getTotalPoints();
    }

    return (totalEarned / totalPossible) * 100;
}
```

Notice that the method no longer needs:

```java
student.getGrades()
```

because it is already inside `Student`.

It can directly access:

```java
grades
```

This removes an unnecessary level of indirection.

---

# 4. Move `getFailedAssignments()` Too

The task also reveals that `getFailedAssignments()` has a similar design problem.

The original method in `GradeAnalyzer` was:

```java
public List<StudentGrade> getFailedAssignments() {
    return student.getGrades().stream()
            .filter(grade ->
                    (grade.getScore() / grade.getTotalPoints()) < 0.6)
            .collect(Collectors.toList());
}
```

This method also operates entirely on the student's grades.

Therefore, it is appropriate to move it into `Student` as well.

```java
/**
 * Returns the list of grades whose raw score/totalPoints ratio is below 60%.
 */
public List<StudentGrade> getFailedAssignments() {
    return grades.stream()
            .filter(grade ->
                    (grade.getScore() / grade.getTotalPoints()) < 0.6)
            .collect(Collectors.toList());
}
```

Now both operations are directly associated with the object that owns the data.

# 5. Refactored `Student`

The final `Student` class becomes:

```java
import java.util.ArrayList;
import java.util.List;
import java.util.stream.Collectors;

public class Student {

    private String id;
    private String name;
    private List<StudentGrade> grades;

    public Student(String id, String name) {
        this.id = id;
        this.name = name;
        this.grades = new ArrayList<>();
    }

    public String getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public List<StudentGrade> getGrades() {
        return grades;
    }

    public void addGrade(StudentGrade grade) {
        grades.add(grade);
    }

    /**
     * Computes the final grade as a percentage, applying late penalties
     * to individual grades where applicable. Returns 0 if there are no grades.
     */
    public double calculateFinalGrade() {
        if (grades.isEmpty()) {
            return 0;
        }

        double totalEarned = 0;
        double totalPossible = 0;

        for (StudentGrade grade : grades) {
            totalEarned += grade.getScoreWithLatePenalty();
            totalPossible += grade.getTotalPoints();
        }

        return (totalEarned / totalPossible) * 100;
    }

    /**
     * Returns the list of grades whose raw score/totalPoints ratio is below 60%.
     */
    public List<StudentGrade> getFailedAssignments() {
        return grades.stream()
                .filter(grade ->
                        (grade.getScore() / grade.getTotalPoints()) < 0.6)
                .collect(Collectors.toList());
    }
}
```

# 6. What Happens to `GradeAnalyzer`?

After moving both methods into `Student`, the original `GradeAnalyzer` no longer needs to perform the actual business logic.

The exercise keeps it as a **thin delegating shim**:

```java
// Deprecated: behavior moved to Student.
// Kept only as a thin delegating shim.
@Deprecated
public class GradeAnalyzer {

    private final Student student;

    public GradeAnalyzer(Student student) {
        this.student = student;
    }

    public double calculateFinalGrade() {
        return student.calculateFinalGrade();
    }

    public java.util.List<StudentGrade> getFailedAssignments() {
        return student.getFailedAssignments();
    }
}
```

This means existing code using `GradeAnalyzer` can continue to work temporarily.

For example:

```java
GradeAnalyzer analyzer = new GradeAnalyzer(student);

double finalGrade = analyzer.calculateFinalGrade();
```

still works because it delegates to:

```java
student.calculateFinalGrade();
```

However, new code should use `Student` directly.

---

# 7. Do We Even Need `GradeAnalyzer`?

This is the important design question raised by the exercise.

After the refactoring, `GradeAnalyzer` has no real business logic.

It simply forwards calls:

```text
GradeAnalyzer
    |
    ├── calculateFinalGrade()
    |       ↓
    |   student.calculateFinalGrade()
    |
    └── getFailedAssignments()
            ↓
        student.getFailedAssignments()
```

This suggests that `GradeAnalyzer` may no longer be necessary.

If there are no other responsibilities that belong to `GradeAnalyzer`, it can eventually be removed.

> [!IMPORTANT]  
> A class should exist because it has a meaningful responsibility, not simply because the original design contained one.

The `@Deprecated` shim provides a gradual migration path if other parts of the application still depend on `GradeAnalyzer`.

# 11. Before vs. After

## Before

```text
Student
  |
  └── owns grades

GradeAnalyzer
  |
  ├── accesses Student
  ├── calculates final grade
  └── finds failed assignments
```

`GradeAnalyzer` is acting as an external manager of `Student`'s data.

## After

```text
Student
  |
  ├── owns grades
  ├── calculates final grade
  └── finds failed assignments
```

The responsibilities are now located with the data they operate on.

---

# 12. Responsibility Distribution

After the refactoring, responsibilities are clearer:

|Class|Responsibility|
|---|---|
|`Student`|Owns and manages grades|
|`Student`|Calculates the student's final grade|
|`Student`|Finds the student's failed assignments|
|`StudentGrade`|Owns individual grade data|
|`StudentGrade`|Determines whether a submission is late|
|`StudentGrade`|Calculates score after late penalty|
|`GradeAnalyzer`|No longer has meaningful business responsibility|

This is a much more cohesive design.

---

# 13. Refactoring Chain

This exercise demonstrates a progression of refactorings:

```text
Feature Envy
     ↓
Move behavior closer to the data
     ↓
StudentGrade owns grade-specific behavior
     ↓
Student owns student-specific behavior
     ↓
GradeAnalyzer becomes unnecessary
```

This is an important object-oriented design principle:

> **Behavior should generally live with the object that owns the data required to perform that behavior.**

The tests make this refactoring safe.

The existing tests already verify:

- Late submissions
    
- Late penalties
    
- Submissions exactly on the due date
    
- Perfect scores
    
- Zero scores
    
- Failed assignments
    
- The 60% boundary
    
- Different total-point values
    

The refactoring changes **where the behavior lives**, not what the behavior does.

Therefore, the assertions should remain the same.

The main change is how the behavior is invoked:

```java
// Before
analyzer.calculateFinalGrade();
```

becomes:

```java
// After
student.calculateFinalGrade();
```

This is a classic example of **behavior-preserving refactoring**.

# Key Takeaways

- `calculateFinalGrade()` primarily operates on `Student`'s own data.
- Therefore, `calculateFinalGrade()` belongs in `Student`.
- `getFailedAssignments()` has the same characteristic and can also be moved to `Student`.
- Once both responsibilities move to `Student`, `GradeAnalyzer` has little or no meaningful responsibility.
- A deprecated delegating `GradeAnalyzer` can temporarily preserve backward compatibility.
- Tests should be moved from `GradeAnalyzerTest` to `StudentTest`.
- The test assertions remain unchanged because the expected behavior has not changed.
- This refactoring improves cohesion and reduces unnecessary coupling.
- The broader lesson is to **put behavior where the data it operates on lives**.

> [!IMPORTANT]  
> **Design question to remember:** If a class only exists to access another object's data and perform operations on that data, ask whether that behavior belongs directly on the object that owns the data.
