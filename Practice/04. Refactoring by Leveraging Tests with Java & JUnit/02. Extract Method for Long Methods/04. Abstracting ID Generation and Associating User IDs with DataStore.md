# Task

The code has already been refactored to separate responsibilities such as:

- User validation    
- Address validation
- Data normalization
- Data storage

However, there is still an issue with **user ID generation**.

Previously, `UserRegistrationService` generated the user ID directly using `UUID`:

```java
String userId = "USER_" + UUID.randomUUID().toString().substring(0, 8);
```

The generated ID was returned in the `RegistrationResponse`, but it was **not passed to the `DataStore`**. This meant the stored user data was not associated with its generated ID.

The goal is to:

1. Abstract ID generation behind an interface.
2. Move UUID-based ID generation into a dedicated class.
3. Pass the generated user ID to the `DataStore`.
4. Change `FakeDataStore` from a `List` to a `Map`.
5. Update the tests to work with the new ID-based storage.

---

## Refactoring Goals

### Before

The service generated the ID itself:

```java
String userId = "USER_" + UUID.randomUUID().toString().substring(0, 8);
```

And stored only the user data:

```java
dataStore.store(normalizedData);
```

The problem was that the relationship between the generated ID and the stored user was lost.

### After

The ID generation responsibility is moved into `IDGenerator`:

```java
String userId = idGenerator.generateId();
```

The generated ID is then passed to the data store:

```java
dataStore.store(userId, normalizedData);
```

The `FakeDataStore` uses the ID as the key:

```java
storage.put(userId, userData);
```

This creates an explicit relationship:

```text
User ID → UserData
```

---

# 1. Create the `IIDGenerator` Interface

The first step is to create an abstraction for ID generation.

## `IIDGenerator.java`

```java
public interface IIDGenerator {

    String generateId();

}
```

### Why use an interface?

The service should not need to know **how** IDs are generated.

It only needs to know that an ID can be generated:

```java
String userId = idGenerator.generateId();
```

This makes ID generation:

- Testable
- Replaceable
- Reusable
- Independent from `UUID`
- Easier to mock or fake in unit tests

For example, the production implementation can use UUIDs, while a test implementation could return a predictable ID such as:

```text
USER_TEST123
```

---

# 2. Create the `IDGenerator` Implementation

The actual UUID-based implementation is moved into a separate class.

## `IDGenerator.java`

```java
import java.util.UUID;

public class IDGenerator implements IIDGenerator {

    @Override
    public String generateId() {
        return "USER_" + UUID.randomUUID().toString().substring(0, 8);
    }

}
```

The responsibility is now clearly separated:

|Class|Responsibility|
|---|---|
|`IIDGenerator`|Defines the ID generation contract|
|`IDGenerator`|Generates real UUID-based IDs|
|`UserRegistrationService`|Uses the ID generator|
|`IDataStore`|Defines how user data is stored|

### Before

```text
UserRegistrationService
        │
        └── Generates UUID
```

### After

```text
UserRegistrationService
        │
        ▼
    IIDGenerator
        │
        ▼
    IDGenerator
        │
        ▼
      UUID
```

---

# 3. Update `IDataStore`

Previously, the `DataStore` only accepted `UserData`:

```java
void store(UserData userData);
```

Now the store needs both:

- `userId`
- `userData`

## `IDataStore.java`

```java
package datastore;

import models.UserData;

public interface IDataStore {

    void store(String userId, UserData userData);

}
```

This allows implementations of `IDataStore` to associate the user data with its ID.

---

# 4. Change `FakeDataStore` from `List` to `Map`

Previously, `FakeDataStore` used a `List`:

```java
private final List<UserData> storedData = new ArrayList<>();
```

This stored users like:

```text
[UserData1, UserData2, UserData3]
```

There was no direct relationship between a user ID and the corresponding user.

The new implementation uses:

```java
Map<String, UserData>
```

where:

```text
Key   → userId
Value → UserData
```

## `FakeDataStore.java`

```java
package datastore;

import java.util.HashMap;
import java.util.Map;

import models.UserData;

public class FakeDataStore implements IDataStore {

    private final Map<String, UserData> storage = new HashMap<>();

    @Override
    public void store(String userId, UserData userData) {
        storage.put(userId, userData);
    }

    public UserData findById(String userId) {
        return storage.get(userId);
    }

    public boolean hasUser(String userId) {
        return storage.containsKey(userId);
    }

}
```

---

## Why use a `Map`?

A `Map` is appropriate because the user ID acts as a unique identifier.

For example:

```text
USER_A1234567 → John
USER_B7654321 → Alice
USER_C9876543 → Bob
```

Retrieving a user becomes straightforward:

```java
UserData user = dataStore.findById(userId);
```

Instead of searching through a list.

### `Map` operations

|Method|Purpose|
|---|---|
|`put(key, value)`|Stores user data using the ID|
|`get(key)`|Retrieves user data by ID|
|`containsKey(key)`|Checks whether an ID exists|

# 5. Update `UserRegistrationService`

The service now receives an `IIDGenerator` dependency.

## Constructor

### Before

```java
public UserRegistrationService(IDataStore dataStore) {
    this.dataStore = dataStore;
    this.userValidator = new UserValidator();
    this.addressValidator = new AddressValidator();
    this.dataNormalizer = new DataNormalizer();
}
```

### After

```java
public UserRegistrationService(IDataStore dataStore, IIDGenerator idGenerator) {
    this.dataStore = dataStore;
    this.idGenerator = idGenerator;
    this.userValidator = new UserValidator();
    this.addressValidator = new AddressValidator();
    this.dataNormalizer = new DataNormalizer();
}
```

The service now depends on the **interface** rather than the concrete `IDGenerator`.

This is an example of **Dependency Injection**.

---

## Updated `UserRegistrationService.java`

```java
import datastore.*;
import models.*;

public class UserRegistrationService {

    private final IDataStore dataStore;
    private final IIDGenerator idGenerator;
    private final UserValidator userValidator;
    private final AddressValidator addressValidator;
    private final DataNormalizer dataNormalizer;

    public UserRegistrationService(IDataStore dataStore, IIDGenerator idGenerator) {
        this.dataStore = dataStore;
        this.idGenerator = idGenerator;
        this.userValidator = new UserValidator();
        this.addressValidator = new AddressValidator();
        this.dataNormalizer = new DataNormalizer();
    }

    public RegistrationResponse processUserRegistration(UserData userData) {
        try {
            // Validate data
            userValidator.validateUserData(userData);
            addressValidator.validateAddress(userData.getAddress());

            // Normalize data
            UserData normalizedData =
                    dataNormalizer.normalizeUserData(userData);

            // Generate user ID
            String userId = idGenerator.generateId();

            // Store data using the generated user ID
            dataStore.store(userId, normalizedData);

            return new RegistrationResponse(
                true,
                "User registered successfully",
                userId
            );

        } catch (ValidationException e) {
            return new RegistrationResponse(
                false,
                e.getMessage(),
                null
            );

        } catch (Exception e) {
            return new RegistrationResponse(
                false,
                "Registration failed: " + e.getMessage(),
                ""
            );
        }
    }
}
```

# 6. Updated Registration Flow

The registration process now follows this sequence:

```text
UserData
   │
   ▼
UserValidator
   │
   ▼
AddressValidator
   │
   ▼
DataNormalizer
   │
   ▼
IIDGenerator
   │
   ▼
Generate userId
   │
   ▼
IDataStore.store(userId, normalizedData)
   │
   ▼
RegistrationResponse
```

The important change is that the generated ID is now used by the storage layer.

# 8. Update the Normalization Test

Previously, the test expected `FakeDataStore` to expose a list:

```java
assertEquals(1, dataStore.getStoredData().size());

UserData loggedData = dataStore.getStoredData().get(0);
```

This no longer works because `FakeDataStore` now uses a `Map`.

Instead, the test obtains the generated ID from the registration response:

```java
String userId = result.getUserId();
```

Then it retrieves the user using that ID:

```java
UserData loggedData = dataStore.findById(userId);
```

## Updated test

```java
@Test
public void testProcessUserRegistrationNormalizesDataSuccess() {

    UserData mixedCaseData = getValidUserData();

    mixedCaseData.setUsername("JohnDOE");
    mixedCaseData.setEmail("John.Doe@EXAMPLE.com");
    mixedCaseData.getAddress().setCountry("usa");

    RegistrationResponse result =
            service.processUserRegistration(mixedCaseData);

    // Verify registration succeeded
    assertTrue(result.isSuccess());
    assertNotNull(result.getUserId());

    // Retrieve the user using the generated ID
    UserData loggedData =
            dataStore.findById(result.getUserId());

    assertNotNull(
            loggedData,
            "User data should be present in the dataStore"
    );

    // Verify normalization
    assertEquals("johndoe", loggedData.getUsername());
    assertEquals("john.doe@example.com", loggedData.getEmail());
    assertEquals("USA", loggedData.getAddress().getCountry());
    assertEquals("10001", loggedData.getAddress().getPostalCode());
}
```

# 9. Why the Test Changed

### Before

The test accessed the first element in a list:

```java
dataStore.getStoredData().get(0);
```

The test essentially assumed:

> "There should be one stored user, so I'll get the first one."

### After

The test uses the actual ID returned by the service:

```java
UserData loggedData =
        dataStore.findById(result.getUserId());
```

This verifies something more meaningful:

> "The user generated by this registration request was stored using the same ID returned to the caller."

This directly tests the new requirement.

# 10. Dependency Injection

This refactoring introduces another important concept: **Dependency Injection**.

Instead of creating the ID generator inside `UserRegistrationService`:

```java
private final IIDGenerator idGenerator = new IDGenerator();
```

the dependency is provided through the constructor:

```java
public UserRegistrationService(
        IDataStore dataStore,
        IIDGenerator idGenerator) {

    this.dataStore = dataStore;
    this.idGenerator = idGenerator;
}
```

This makes the service less tightly coupled to `IDGenerator`.

### Production

```java
IIDGenerator idGenerator = new IDGenerator();

UserRegistrationService service =
        new UserRegistrationService(dataStore, idGenerator);
```

### Test

A fake or mock implementation could be provided:

```java
IIDGenerator idGenerator = () -> "USER_TEST123";
```

This makes tests deterministic.

---

# 11. Why Abstraction Makes ID Generation More Testable

UUID generation is inherently unpredictable:

```java
UUID.randomUUID()
```

Every execution produces a different value.

For example:

```text
USER_a13f92bc
USER_7b21e4fa
USER_c82d109e
```

That makes exact ID assertions difficult.

With `IIDGenerator`, tests can provide a predictable implementation:

```java
IIDGenerator idGenerator = () -> "USER_TEST123";
```

Then the test can verify exactly which ID was used.

This is one of the main benefits of **programming against an interface**.

# 13. Refactoring Concepts

## Extract Class

ID generation was extracted from `UserRegistrationService` into:

```text
IDGenerator
```

The service no longer handles UUID implementation details.

---

## Dependency Inversion

`UserRegistrationService` depends on:

```java
IIDGenerator
```

rather than:

```java
IDGenerator
```

The high-level service depends on an abstraction.

---

## Dependency Injection

The ID generator is supplied through the constructor:

```java
public UserRegistrationService(
        IDataStore dataStore,
        IIDGenerator idGenerator)
```

This allows different implementations to be used without modifying the service.

---

## Interface-Based Design

The interface defines the contract:

```java
public interface IIDGenerator {

    String generateId();

}
```

Any class implementing this interface can provide an ID-generation strategy.

---

## Map-Based Storage

The `Map` creates a direct association:

```java
Map<String, UserData>
```

Conceptually:

```text
userId → userData
```

This is more appropriate than a list when the ID is the primary way to identify a user.

# 15. Final Class Responsibilities

After this refactoring, responsibilities are well separated:

|Class / Interface|Responsibility|
|---|---|
|`UserRegistrationService`|Coordinates the registration workflow|
|`UserValidator`|Validates user information|
|`AddressValidator`|Validates address information|
|`DataNormalizer`|Normalizes user and address data|
|`IIDGenerator`|Defines the ID-generation contract|
|`IDGenerator`|Generates UUID-based user IDs|
|`IDataStore`|Defines the storage contract|
|`FakeDataStore`|Stores users in memory using IDs|
|`UserData`|Represents user information|
|`Address`|Represents address information|
|`RegistrationResponse`|Represents the registration result|
|`ValidationException`|Represents validation errors|

---

> [!IMPORTANT]  
> **Key idea:** The generated user ID should not only be returned to the caller. It must also be used as the identifier for the stored user data.

---

# Key Takeaways

- **Extract ID generation** into a dedicated `IDGenerator` class.
- Use an **`IIDGenerator` interface** to abstract the generation strategy.
- Use **Dependency Injection** to provide the ID generator to `UserRegistrationService`.
- Avoid coupling business logic directly to `UUID`.
- Update `IDataStore` to accept both `userId` and `UserData`.
- Use `Map<String, UserData>` when data needs to be associated with a unique key.
- Retrieve stored users using their ID rather than a list index.
- Abstractions make unpredictable operations such as UUID generation easier to test.
- The generated ID should be used consistently throughout the system.
- This refactoring improves **separation of concerns, testability, maintainability, and reusability**.
