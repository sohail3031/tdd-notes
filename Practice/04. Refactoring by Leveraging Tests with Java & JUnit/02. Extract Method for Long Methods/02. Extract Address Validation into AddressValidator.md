# Task

Refactor the existing `UserRegistrationService` by extracting the **address validation logic** into a dedicated `AddressValidator` class.

The refactoring should follow the same pattern already established by the `UserValidator` class.

### Goals

1. Create an `AddressValidator` class.    
2. Extract each address validation rule into its own method:
    - `validateStreet`
    - `validateCity`
    - `validateCountry`
    - `validatePostalCode`
3. Create a `validateAddress` method that calls all four validation methods.
4. Replace the large address-validation block in `UserRegistrationService` with a call to `AddressValidator`.
5. Keep the existing test behavior and validation messages unchanged.

---

## Refactoring Concept

The original `UserRegistrationService` had multiple responsibilities:

```text
UserRegistrationService
├── Validate username
├── Validate email
├── Validate password
├── Validate date of birth
├── Validate street
├── Validate city
├── Validate country
├── Validate postal code
├── Normalize data
├── Store user
└── Generate user ID
```

After the refactoring:

```text
UserRegistrationService
├── UserValidator
│   ├── Username validation
│   ├── Email validation
│   ├── Password validation
│   └── Date-of-birth validation
│
├── AddressValidator
│   ├── Street validation
│   ├── City validation
│   ├── Country validation
│   └── Postal-code validation
│
├── Normalize data
├── Store user
└── Generate user ID
```

This makes `UserRegistrationService` easier to read and gives address validation its own focused class.

# 1. Before Refactoring

Previously, `UserRegistrationService` contained all address validation directly inside `processUserRegistration()`:

```java
Address address = userData.getAddress();

if (address.getStreet() == null || address.getStreet().isBlank()
        || address.getStreet().length() < 5) {
    return new RegistrationResponse(false, "Invalid street address", null);
}

if (address.getCity() == null || address.getCity().isBlank()
        || address.getCity().length() < 2) {
    return new RegistrationResponse(false, "Invalid city", null);
}

if (address.getCountry() == null || address.getCountry().isBlank()
        || address.getCountry().length() < 2) {
    return new RegistrationResponse(false, "Invalid country", null);
}

if (address.getPostalCode() == null || address.getPostalCode().isBlank()
        || !Pattern.compile("^[A-Z0-9]{3,10}$")
            .matcher(address.getPostalCode().toUpperCase())
            .matches()) {
    return new RegistrationResponse(false, "Invalid postal code", null);
}
```

### Problems

- `UserRegistrationService` was becoming too large.
- Address validation was mixed with registration logic.
- Validation rules were harder to locate and maintain.
- Adding more address rules would make the service even larger.
- The same validation logic could not easily be reused elsewhere.

# 2. Create `AddressValidator`

Create a new class:

```java
import java.util.regex.Pattern;

import models.Address;

public class AddressValidator {

    private static final Pattern POSTAL_CODE_PATTERN =
            Pattern.compile("^[A-Z0-9]{3,10}$");

    public void validateStreet(String street) throws ValidationException {
        if (street == null || street.isBlank() || street.length() < 5) {
            throw new ValidationException("Invalid street address");
        }
    }

    public void validateCity(String city) throws ValidationException {
        if (city == null || city.isBlank() || city.length() < 2) {
            throw new ValidationException("Invalid city");
        }
    }

    public void validateCountry(String country) throws ValidationException {
        if (country == null || country.isBlank() || country.length() < 2) {
            throw new ValidationException("Invalid country");
        }
    }

    public void validatePostalCode(String postalCode) throws ValidationException {
        if (postalCode == null || postalCode.isBlank()
                || !POSTAL_CODE_PATTERN
                    .matcher(postalCode.toUpperCase())
                    .matches()) {
            throw new ValidationException("Invalid postal code");
        }
    }

    public void validateAddress(Address address) throws ValidationException {
        if (address == null) {
            throw new ValidationException("Address information is missing");
        }

        validateStreet(address.getStreet());
        validateCity(address.getCity());
        validateCountry(address.getCountry());
        validatePostalCode(address.getPostalCode());
    }
}
```

# 3. Individual Validation Methods

## `validateStreet()`

Responsible only for street validation.

```java
public void validateStreet(String street) throws ValidationException {

}
```

Rules:

- Street cannot be `null`.
- Street cannot be blank.

## `validatePostalCode()`

Responsible only for postal-code validation.

```java
private static final Pattern POSTAL_CODE_PATTERN =
        Pattern.compile("^[A-Z0-9]{3,10}$");

public void validatePostalCode(String postalCode) throws ValidationException {
    if (postalCode == null || postalCode.isBlank()
            || !POSTAL_CODE_PATTERN
                .matcher(postalCode.toUpperCase())
                .matches()) {
        throw new ValidationException("Invalid postal code");
    }
}
```

The regular expression:

```text
^[A-Z0-9]{3,10}$
```

means:

|Part|Meaning|
|---|---|
|`^`|Start of string|
|`[A-Z0-9]`|Uppercase letters or digits|
|`{3,10}`|Between 3 and 10 characters|
|`$`|End of string|

Examples:

```text
10001       → Valid
ABC123      → Valid
ABC         → Valid
12          → Invalid
ABC-123     → Invalid
```

### Why use a constant?

Instead of compiling the pattern every time:

```java
Pattern.compile("^[A-Z0-9]{3,10}$")
```

the pattern is compiled once:

```java
private static final Pattern POSTAL_CODE_PATTERN =
        Pattern.compile("^[A-Z0-9]{3,10}$");
```

This also gives the validation rule a meaningful name.

# 4. Create `validateAddress()`

The individual validation methods are combined through a higher-level method:

```java
public void validateAddress(Address address) throws ValidationException {
    if (address == null) {
        throw new ValidationException("Address information is missing");
    }

    validateStreet(address.getStreet());
    validateCity(address.getCity());
    validateCountry(address.getCountry());
    validatePostalCode(address.getPostalCode());
}
```

This method acts as the **entry point** for address validation.

Instead of the service needing to know how each field is validated:

```java
validateStreet(...);
validateCity(...);
validateCountry(...);
validatePostalCode(...);
```

the service only needs:

```java
addressValidator.validateAddress(userData.getAddress());
```

### Validation flow

```text
validateAddress(address)
        │
        ├── validateStreet()
        │
        ├── validateCity()
        │
        ├── validateCountry()
        │
        └── validatePostalCode()
```

If any method throws a `ValidationException`, execution stops and the exception is handled by `UserRegistrationService`.

# 6. Final `UserRegistrationService`

```java
import java.util.UUID;

import models.*;
import datastore.*;

public class UserRegistrationService {

    private final IDataStore dataStore;
    private final UserValidator userValidator;
    private final AddressValidator addressValidator;

    public UserRegistrationService(IDataStore dataStore) {
        this.dataStore = dataStore;
        this.userValidator = new UserValidator();
        this.addressValidator = new AddressValidator();
    }

    public RegistrationResponse processUserRegistration(UserData userData) {
        try {
            // Validate user data
            userValidator.validateUserData(userData);

            // Validate address
            addressValidator.validateAddress(userData.getAddress());

            // Data transformation
            String userId = "USER_" + UUID.randomUUID().toString().substring(0, 8);

            UserData normalizedData = new UserData(
                userData.getUsername().toLowerCase(),
                userData.getEmail().toLowerCase(),
                userData.getPassword(),
                userData.getDateOfBirth(),
                new Address(
                    userData.getAddress().getStreet().trim(),
                    userData.getAddress().getCity().trim(),
                    userData.getAddress().getCountry().toUpperCase(),
                    userData.getAddress().getPostalCode().toUpperCase()
                )
            );

            dataStore.store(normalizedData);

            return new RegistrationResponse(
                true,
                "User registered successfully",
                userId
            );

        } catch (ValidationException e) {
            return new RegistrationResponse(
                false,
                e.getMessage(),
                null
            );

        } catch (Exception e) {
            return new RegistrationResponse(
                false,
                "Registration failed: " + e.getMessage(),
                ""
            );
        }
    }
}
```

# 7. Why Does `ValidationException` Still Work?

A key point in this refactoring is that we **did not change the exception-handling design**.

`AddressValidator` throws:

```java
throw new ValidationException("Invalid city");
```

`UserRegistrationService` already has:

```java
catch (ValidationException e) {
    return new RegistrationResponse(false, e.getMessage(), null);
}
```

Therefore, the exception flows naturally back to the service.

```text
AddressValidator
       │
       │ throws ValidationException
       ▼
UserRegistrationService
       │
       │ catch (ValidationException)
       ▼
RegistrationResponse(false, message, null)
```

This allows us to move the validation logic without changing the externally visible behavior.

# 8. Refactoring vs. Behavior Change

This task is a **pure refactoring**.

The validation rules remain the same.

|Validation|Original behavior|After refactoring|
|---|---|---|
|Missing street|`"Invalid street address"`|Same|
|Short street|`"Invalid street address"`|Same|
|Missing city|`"Invalid city"`|Same|
|Short city|`"Invalid city"`|Same|
|Missing country|`"Invalid country"`|Same|
|Short country|`"Invalid country"`|Same|
|Missing postal code|`"Invalid postal code"`|Same|
|Invalid postal code|`"Invalid postal code"`|Same|
|Valid address|Continue registration|Same|

The main change is **where the code lives**, not what the application does.

> [!IMPORTANT]  
> **Refactoring should preserve behavior.**  
> If the tests passed before the refactoring, they should continue to pass afterward.

# 9. Why This Is Better

### Before

`UserRegistrationService` knew the implementation details of every address field.

```java
if (street ...) { ... }
if (city ...) { ... }
if (country ...) { ... }
if (postalCode ...) { ... }
```

### After

`UserRegistrationService` only knows that an address needs to be validated:

```java
addressValidator.validateAddress(userData.getAddress());
```

This follows the **Single Responsibility Principle (SRP)** more closely.

### Benefits

- **Better readability** — the registration workflow is easier to understand.
    
- **Better maintainability** — address rules are centralized.
    
- **Reusability** — `AddressValidator` can be used by other services.
    
- **Easier testing** — address validation can be tested independently.
    
- **Reduced complexity** — `UserRegistrationService` is smaller.
    
- **Better separation of concerns** — registration logic and validation logic are separated.

# 11. Important TDD/Refactoring Lesson

This task demonstrates **Extract Class** and **Extract Method** refactoring.

### Extract Method

Move a specific piece of logic into its own method:

```java
validateStreet(...)
validateCity(...)
validateCountry(...)
validatePostalCode(...)
```

### Extract Class

Move a group of related methods into a dedicated class:

```text
UserRegistrationService
        │
        └── AddressValidator
              ├── validateStreet()
              ├── validateCity()
              ├── validateCountry()
              └── validatePostalCode()
```

The existing tests provide a **safety net** while performing the refactoring.

The ideal workflow is:

```text
1. Run existing tests
       ↓
2. Refactor
       ↓
3. Run tests again
       ↓
4. Confirm behavior is unchanged
```

# Key Takeaways

- **Extract Class** moves a group of related responsibilities into a dedicated class.
- **Extract Method** breaks a large method into smaller focused methods.
- `AddressValidator` now owns all address-validation rules.
- `UserRegistrationService` coordinates the registration process instead of implementing every validation rule.
- `validateAddress()` provides a single entry point for address validation.
- `ValidationException` allows validation failures to flow back to the existing exception handler.
- Existing validation messages and behavior should remain unchanged.
- `private static final Pattern` avoids repeatedly compiling the postal-code regex.
- TDD makes refactoring safer because existing tests verify that behavior has not changed.
- This refactoring improves **SRP, readability, maintainability, and reusability**.
