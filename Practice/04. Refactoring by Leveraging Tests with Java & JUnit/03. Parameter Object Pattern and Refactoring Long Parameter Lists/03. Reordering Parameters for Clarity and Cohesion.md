# Task

Refactor the `processExamScore` method by **reordering its parameters** to improve clarity, readability, and maintainability.

The existing method has parameters in an arbitrary order, mixing different types of information. The goal is to organize the parameters into logical groups.

### Required Parameter Order

The parameters should be organized into three logical groups:

1. **Course context**    
    - `courseCode`
2. **Student's individual performance**
    - `examScore`
    - `isHomeworkComplete`
    - `attendanceScore`
    - `bonusActivities`
    - `isRetake`
3. **Course configuration**
    - `scoreWeights`
    - `coursePolicy`

### Important

This is a **refactoring-only task**. The goal is to improve the organization of the method signature without changing its existing behavior.

---

## Before Refactoring

The original method signature was:

```java
public ExamResult processExamScore(
```

The parameters are mixed together:

# Refactoring the Method Signature

The parameters are reordered into logical groups.

## After Refactoring

```java
public ExamResult processExamScore(
    String courseCode,
    double examScore,
    boolean isHomeworkComplete,
    int attendanceScore,
    List<String> bonusActivities,
    boolean isRetake,
    ScoreWeights scoreWeights,
    CoursePolicy coursePolicy
```

The new order is:

| Group               | Parameters           | Purpose                        |
| ------------------- | -------------------- | ------------------------------ |
| Course context      | `courseCode`         | Identifies the course          |
| Student performance | `examScore`          | Student's exam score           |
| Student performance | `isHomeworkComplete` | Whether homework was completed |
| Student performance | `attendanceScore`    | Student's attendance           |
| Student performance | `bonusActivities`    | Student's bonus activities     |
| Student performance | `isRetake`           | Whether the exam is a retake   |
| Configuration       | `scoreWeights`       | Defines component weights      |
| Configuration       | `coursePolicy`       | Defines course-specific rules  |

# Updated `ExamProcessor.java`

```java
import java.util.List;

public class ExamProcessor {

    public ExamResult processExamScore(
        String courseCode,
        double examScore,
        boolean isHomeworkComplete,
        int attendanceScore,
        List<String> bonusActivities,
        boolean isRetake,
        ScoreWeights scoreWeights,
        CoursePolicy coursePolicy
    ) {
        // Normalize input scores to handle edge cases
        double normalizedExamScore = clamp(examScore, 0, 100);
        double normalizedAttendanceScore = clamp(attendanceScore, 0, 3);

        // Calculate weighted exam score
        double weightedScore = normalizedExamScore * scoreWeights.getExam();

        // Calculate homework component
        // 100% if complete, apply missedHomeworkPenaltyPercentage if incomplete
        double homeworkScore = isHomeworkComplete
            ? 100.0
            : 100.0 * coursePolicy.getMissedHomeworkPenaltyPercentage();

        weightedScore += homeworkScore * scoreWeights.getHomework();

        // Calculate attendance component
        // Convert 0-3 scale to percentage
        double normalizedAttendancePercentage =
            (normalizedAttendanceScore / 3.0) * 100.0;

        weightedScore +=
            normalizedAttendancePercentage * scoreWeights.getAttendance();

        // Add bonus points after weights are applied
        double bonusPoints =
            bonusActivities.size() * coursePolicy.getBonusPointsPerActivity();

        weightedScore += bonusPoints;

        // Apply retake penalty if applicable
        if (isRetake) {
            weightedScore *= coursePolicy.getRetakePenaltyPercentage();
        }

        // Ensure score doesn't exceed 100 even with bonus points
        weightedScore = Math.min(100.0, weightedScore);

        // Round to the nearest 0.5
        double finalScore = roundToNearestHalf(weightedScore);

        return new ExamResult(
            finalScore,
            finalScore >= coursePolicy.getPassingThreshold(),
            calculateGradeLevel(finalScore)
        );
    }

    private double clamp(double value, double min, double max) {
        return Math.max(min, Math.min(max, value));
    }

    private double roundToNearestHalf(double value) {
        return Math.round(value * 2.0) / 2.0;
    }

    private GradeLevel calculateGradeLevel(double score) {
        if (score >= 93) return GradeLevel.A;
        if (score >= 90) return GradeLevel.AMinus;
        if (score >= 87) return GradeLevel.BPlus;
        if (score >= 83) return GradeLevel.B;
        if (score >= 80) return GradeLevel.BMinus;
        if (score >= 77) return GradeLevel.CPlus;
        if (score >= 73) return GradeLevel.C;
        if (score >= 70) return GradeLevel.CMinus;
        if (score >= 60) return GradeLevel.D;
        return GradeLevel.F;
    }
}
```

> **Note:** `courseCode` is reordered for readability, but the current implementation does not actually use it inside the method body.

# Example Test

```java
@Test
public void testCalculatesFinalGradeWithAllFactors() {
    ExamProcessor examProcessor = new ExamProcessor();

    ScoreWeights weights =
        new ScoreWeights(0.7, 0.1, 0.1);

    CoursePolicy coursePolicy =
        new CoursePolicy(2, 75.0, 0.95, 0.6);
```

# Why This Refactoring Is Useful

## 1. Better Readability

The method signature now follows a logical structure:

```text
Course
   ↓
Student Performance
   ↓
Configuration
```

Instead of:

```text
Student Performance
   ↓
Configuration
   ↓
Student Performance
   ↓
Course
```

---

## 2. Easier to Understand Method Calls

When someone sees:

```java
examProcessor.processExamScore(
    "MATH101",
    85.0,
    true,
    3,
    bonusActivities,
    false,
    weights,
    coursePolicy
);
```

the structure is easier to recognize:

```text
"MATH101"              → Course
85.0                   → Exam score
true                   → Homework completed
3                      → Attendance
bonusActivities        → Bonus activities
false                  → Not a retake
weights                → Score configuration
coursePolicy           → Course rules
```

---

## 3. Improved Cohesion

Related parameters are kept together.

### Student performance

```java
double examScore,
boolean isHomeworkComplete,
int attendanceScore,
List<String> bonusActivities,
boolean isRetake
```

These all describe the **student's performance**.

### Configuration

```java
ScoreWeights scoreWeights,
CoursePolicy coursePolicy
```

These define the **rules used to calculate the result**.

### Context

```java
String courseCode
```

This identifies **which course** the calculation belongs to.

# TDD Perspective

This is primarily a **refactoring step** in the Red-Green-Refactor cycle.

### Red

Existing tests define the expected behavior.

### Green

The existing implementation passes the tests.

### Refactor

Reorder the parameters without changing behavior:

```java
// Before
examScore, isHomeworkComplete, attendanceScore,
bonusActivities, scoreWeights, coursePolicy,
isRetake, courseCode
```

becomes:

```java
// After
courseCode,
examScore, isHomeworkComplete, attendanceScore,
bonusActivities, isRetake,
scoreWeights, coursePolicy
```

### Verify

Run the complete test suite to ensure that the parameter reordering did not change the behavior.

> **Key principle:** Refactoring should change the **structure of the code**, not its **observable behavior**.

# Key Takeaways

- Parameter order can significantly affect code readability.    
- Put **contextual information** first when it identifies what the operation is about.
- Group related parameters together.
- Keep **student/input data** separate from **configuration**.
- `ScoreWeights` groups scoring configuration.
- `CoursePolicy` groups course-specific business rules.
- Reordering parameters is a behavior-preserving refactoring.
- Existing tests provide confidence that the refactoring did not change functionality.
- Logical parameter grouping makes method calls easier to read and maintain.
- When a method has many parameters, consider whether additional **Parameter Objects** or another design improvement would make the API clearer.
