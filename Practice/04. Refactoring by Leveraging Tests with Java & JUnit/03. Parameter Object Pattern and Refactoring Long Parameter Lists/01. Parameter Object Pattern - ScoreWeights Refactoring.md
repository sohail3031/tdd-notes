# Objective

Refactor the `processExamScore()` method to use a **`ScoreWeights` parameter object**.

Currently, the method receives three separate parameters:

```java
double examWeight,
double homeworkWeight,
double attendanceWeight
```

These values are closely related because they all represent the **weighting configuration used to calculate the final score**.

The goal is to group them into a single `ScoreWeights` object.

### Before Refactoring

The method had three separate weight parameters:

```java
public ExamResult processExamScore(
    double examScore,
    boolean isHomeworkComplete,
    int attendanceScore,
    List<String> bonusActivities,
    double examWeight,
    double homeworkWeight,
    double attendanceWeight,
    int bonusPointsPerActivity,
    double passingThreshold,
    boolean isRetake,
    String courseCode
)
```

This contributes to a **Long Parameter List** and makes method calls harder to read.

For example:

```java
examProcessor.processExamScore(
    85.0,
    true,
    3,
    bonusActivities,
    0.7,
    0.2,
    0.1,
    2,
    75.0,
    false,
    "MATH101"
);
```

It is not immediately obvious what `0.7`, `0.2`, and `0.1` represent.

---

## Refactoring: Create `ScoreWeights`

Create a new class that groups the three related weights.

### `ScoreWeights.java`

```java
public class ScoreWeights {

    private final double examWeight;
    private final double homeworkWeight;
    private final double attendanceWeight;

    public ScoreWeights(
        double examWeight,
        double homeworkWeight,
        double attendanceWeight
    ) {
        this.examWeight = examWeight;
        this.homeworkWeight = homeworkWeight;
        this.attendanceWeight = attendanceWeight;
    }

    public double getExamWeight() {
        return examWeight;
    }

    public double getHomeworkWeight() {
        return homeworkWeight;
    }

    public double getAttendanceWeight() {
        return attendanceWeight;
    }
}
```

### Why use `final`?

The fields are configuration values that should not change after the object is created.

```java
private final double examWeight;
```

This makes `ScoreWeights` effectively immutable.

Replace the three individual weight parameters with one `ScoreWeights` parameter.

### Before

### After

The calculation now accesses the values through the `ScoreWeights` object:

```java
double weightedScore =
    normalizedExamScore * weights.getExamWeight();
```

Homework:

```java

```

Attendance:

```java
weightedScore +=
    normalizedAttendancePercentage * weights.getAttendanceWeight();
```

### Complete `ExamProcessor.java`

```java
import java.util.List;

public class ExamProcessor {

    public ExamResult processExamScore(
        double examScore,
        boolean isHomeworkComplete,
        int attendanceScore,
        List<String> bonusActivities,
        ScoreWeights weights,
        int bonusPointsPerActivity,
        double passingThreshold,
        boolean isRetake,
        String courseCode
    ) {
        // Normalize input scores to handle edge cases
        double normalizedExamScore = clamp(examScore, 0, 100);
        double normalizedAttendanceScore = clamp(attendanceScore, 0, 3);

        // Calculate weighted exam score
        double weightedScore =
            normalizedExamScore * weights.getExamWeight();

        // Calculate homework component
        // 100% if complete, 60% if incomplete
        double homeworkScore =
            isHomeworkComplete ? 100.0 : 60.0;

        weightedScore +=
            homeworkScore * weights.getHomeworkWeight();

        // Calculate attendance component
        // Convert 0-3 scale to percentage
        double normalizedAttendancePercentage =
            (normalizedAttendanceScore / 3.0) * 100.0;

        weightedScore +=
            normalizedAttendancePercentage *
            weights.getAttendanceWeight();

        // Add bonus points after weights are applied
        double bonusPoints =
            bonusActivities.size() * bonusPointsPerActivity;

        weightedScore += bonusPoints;

        // Apply retake penalty if applicable
        if (isRetake) {
            weightedScore *= 0.95;
        }

        // Ensure score doesn't exceed 100
        weightedScore = Math.min(100.0, weightedScore);

        // Round to the nearest 0.5
        double finalScore =
            roundToNearestHalf(weightedScore);

        return new ExamResult(
            finalScore,
            finalScore >= passingThreshold,
            calculateGradeLevel(finalScore)
        );
    }

    private double clamp(double value, double min, double max) {
        return Math.max(min, Math.min(max, value));
    }

    private double roundToNearestHalf(double value) {
        return Math.round(value * 2.0) / 2.0;
    }

    private GradeLevel calculateGradeLevel(double score) {
        if (score >= 93) return GradeLevel.A;
        if (score >= 90) return GradeLevel.AMinus;
        if (score >= 87) return GradeLevel.BPlus;
        if (score >= 83) return GradeLevel.B;
        if (score >= 80) return GradeLevel.BMinus;
        if (score >= 77) return GradeLevel.CPlus;
        if (score >= 73) return GradeLevel.C;
        if (score >= 70) return GradeLevel.CMinus;
        if (score >= 60) return GradeLevel.D;
        return GradeLevel.F;
    }
}
```

# Why This Refactoring Is Better

### 1. Reduces the Parameter List

Before:

```java
double examWeight,
double homeworkWeight,
double attendanceWeight,
```

After:

```java
ScoreWeights weights,
```

Three parameters become one.

---

### 2. Groups Related Data

These values all describe the same concept:

```text
ScoreWeights
├── examWeight
├── homeworkWeight
└── attendanceWeight
```

Instead of treating them as unrelated primitive values, the code represents their relationship explicitly.

---

### 3. Improves Readability

Compare:

```java
processExamScore(
    85.0,
    true,
    3,
    bonusActivities,
    0.7,
    0.2,
    0.1,
    2,
    75.0,
    false,
    "MATH101"
);
```

with:

```java
ScoreWeights weights =
    new ScoreWeights(0.7, 0.2, 0.1);

processExamScore(
    85.0,
    true,
    3,
    bonusActivities,
    weights,
    2,
    75.0,
    false,
    "MATH101"
);
```

The second version communicates that the three values represent a single configuration.

---

### 4. Easier to Extend

Suppose the application later needs another score weight:

```java
double projectWeight;
```

Without a parameter object, the method would need another parameter:

```java
double examWeight,
double homeworkWeight,
double attendanceWeight,
double projectWeight,
```

With `ScoreWeights`, only the class needs to change:

```java
public class ScoreWeights {

    private final double examWeight;
    private final double homeworkWeight;
    private final double attendanceWeight;
    private final double projectWeight;

    // ...
}
```

The method can continue accepting:

```java
ScoreWeights weights
```

# Refactoring Pattern

This task is an example of the **Parameter Object** refactoring technique.

### Before

```text
Method
  │
  ├── examWeight
  ├── homeworkWeight
  └── attendanceWeight
```

### After

```text
Method
  │
  └── ScoreWeights
        ├── examWeight
        ├── homeworkWeight
        └── attendanceWeight
```

The method now works with a meaningful domain concept instead of several unrelated primitive parameters.

# TDD Perspective

The refactoring follows the **Red → Green → Refactor** cycle.

### Red

Existing tests describe the expected behavior using the old method signature.

### Green

The existing implementation passes the tests.

### Refactor

Introduce:

```java
ScoreWeights
```

Then update:

- `ExamProcessor`
- `ExamProcessorTest`
- Method calls
- Weight-related calculations

The important goal is that **behavior does not change**.

The score calculations should remain exactly the same.

### Final verification

All existing tests should continue to pass after replacing the three weight parameters with the `ScoreWeights` parameter object.

---

# Key Takeaways

> [!important] Parameter Object  
> Use a Parameter Object when several parameters are **logically related** and represent a cohesive concept.

- `ScoreWeights` groups related score-weight configuration.
- Three parameters become one meaningful object.
- The method signature becomes easier to understand.
- Related data is encapsulated in one class.
- Future changes to score-weight configuration become easier.
- Tests remain focused on behavior rather than changing implementation details.
- This is one way to address the **Long Parameter List** code smell.
- Do not create a Parameter Object merely because a method has several parameters; the parameters should represent a meaningful, cohesive concept.
