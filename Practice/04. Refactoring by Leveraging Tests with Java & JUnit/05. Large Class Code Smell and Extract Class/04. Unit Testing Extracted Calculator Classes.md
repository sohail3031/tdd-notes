# Unit Testing Extracted Calculator Classes

## Task Objective

The previous refactoring extracted several responsibilities from the large `ShoppingCart` class into smaller calculator classes:

```text
ShoppingCart
├── PriceCalculator
├── DiscountCalculator
├── ShippingCalculator
└── LoyaltyPointsCalculator
```

The `ShippingCalculator` and `LoyaltyPointsCalculator` classes already have their own tests.

The task is to implement the missing tests for:

- `DiscountCalculator`
- `PriceCalculator`

The main objective is to verify that the extracted classes work correctly **in isolation**.

---

# Why Test Extracted Classes Separately?

One of the major benefits of **Extract Class** is that the new classes become easier to test.

Before extraction, discount logic was tested indirectly through `ShoppingCart`:

```text
ShoppingCartTest
      │
      ▼
ShoppingCart
      │
      └── Discount logic
```

After extraction, we can test the discount logic directly:

```text
DiscountCalculatorTest
        │
        ▼
DiscountCalculator
```

The same applies to pricing:

```text
PriceCalculatorTest
        │
        ▼
PriceCalculator
```

This makes tests:

- Smaller
- More focused
- Easier to understand
- Easier to maintain
- Faster to execute
- Better at identifying which class contains a defect

# Part 1: Testing `DiscountCalculator`

## Responsibilities Being Tested

`DiscountCalculator` is responsible for:

1. Accepting valid discount codes.
2. Rejecting invalid discount codes.
3. Remembering the currently applied discount code.
4. Calculating the appropriate discount amount.

The available discount codes are:

|Code|Discount|
|---|--:|
|`SAVE10`|10%|
|`SUMMER20`|20%|
|`VIP15`|15%|

---

# Test Setup

A fresh `DiscountCalculator` is created before every test:

```java
@BeforeEach
public void setUp() {
    calculator = new DiscountCalculator();
}
```

This ensures that tests do not share the same calculator state.

For example:

```text
Test 1 → new DiscountCalculator()
Test 2 → new DiscountCalculator()
Test 3 → new DiscountCalculator()
```

This prevents one test's applied discount code from affecting another test.

---

# Test 1: Valid Discount Codes

The test uses a parameterized test:

```java
@ParameterizedTest
@ValueSource(strings = {"SAVE10", "SUMMER20", "VIP15"})
```

Instead of writing three separate tests, the same test runs once for each valid code.

The assertion is:

```java
assertDoesNotThrow(() -> calculator.applyDiscountCode(code));
```

This verifies that valid codes are accepted.

### Why `assertDoesNotThrow()`?

It explicitly verifies that the operation completes without throwing an exception.

---

# Test 2: Calculate Discount

The test applies `SAVE10`:

```java
calculator.applyDiscountCode("SAVE10");
```

Then calculates the discount on a `$100` subtotal:

```java
double discount = calculator.calculateDiscount(100.0);
```

Expected result:

```text
$100 × 10%
= $10
```

The assertion is:

```java
assertEquals(10.0, discount, 0.001);
```

The third argument is a floating-point tolerance.

---

# Test 3: Invalid Discount Codes

Invalid codes are tested using another parameterized test:

```java
@ParameterizedTest
@ValueSource(strings = {"INVALID", "TEST123", "save10"})
```

The test verifies that applying an invalid code throws an exception:

```java
assertThrows(IllegalArgumentException.class, () -> {
    calculator.applyDiscountCode(code);
});
```

### Important Note About the Provided Code

There is a mismatch between the provided `DiscountCalculator` implementation and this test.

The `DiscountCalculator` shown in the task throws:

```java
throw new IllegalStateException("Invalid discount code");
```

but the final test expects:

```java
assertThrows(IllegalArgumentException.class, ...)
```

Therefore, **with the exact `DiscountCalculator` implementation shown earlier, this test would fail**.

The test is correct only if the implementation has been changed to throw:

```java
throw new IllegalArgumentException("Invalid discount code");
```

or if the expected exception in the test is changed to:

```java
assertThrows(IllegalStateException.class, ...)
```

This is an important example of why tests must match the actual contract of the class.

---

# Final `DiscountCalculatorTest.java`

```java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

import static org.junit.jupiter.api.Assertions.*;

public class DiscountCalculatorTest {

    private DiscountCalculator calculator;

    @BeforeEach
    public void setUp() {
        calculator = new DiscountCalculator();
    }

    @ParameterizedTest
    @ValueSource(strings = {"SAVE10", "SUMMER20", "VIP15"})
    public void testApplyValidDiscountCodesDoesNotThrow(String code) {
        assertDoesNotThrow(() -> calculator.applyDiscountCode(code));
    }

    @Test
    public void testCalculateDiscountReturnsCorrectValue() {
        calculator.applyDiscountCode("SAVE10");

        double discount = calculator.calculateDiscount(100.0);

        assertEquals(10.0, discount, 0.001);
    }

    @ParameterizedTest
    @ValueSource(strings = {"INVALID", "TEST123", "save10"})
    public void testApplyInvalidDiscountCodeThrowsException(String code) {
        assertThrows(IllegalArgumentException.class, () -> {
            calculator.applyDiscountCode(code);
        });
    }
}
```

# Part 2: Testing `PriceCalculator`

## Responsibilities Being Tested

`PriceCalculator` is responsible for:

- Calculating item prices based on customer price level.
- Calculating cart subtotal.
- Calculating tax.
- Ignoring cart items whose product IDs do not exist in the supplied product list.

The tests focus on subtotal and tax behavior.

---

# Test Setup

The test creates:

```java
customer = new Customer();
customer.setPriceLevel(PriceLevel.REGULAR);
```

A `CartItemCollection` is also created:

```java
cartItems = new CartItemCollection();
```

Two products are added:

```text
Product 1
ID    = 1
Price = 100

Product 2
ID    = 2
Price = 200
```

Finally:

```java
calculator = new PriceCalculator(customer, cartItems);
```

The calculator now has access to:

```text
Customer
   ↓
Price level

CartItemCollection
   ↓
Cart contents
```

---

# Test 1: Calculate Tax

The test uses:

```java
@ValueSource(doubles = {100, 200, 300})
```

This produces three test cases:

```text
100 → 10
200 → 20
300 → 30
```

The expected calculation is:

```java
subtotal * 0.1
```

The assertion is:

```java
assertEquals(subtotal * 0.1, tax, 0.001);
```

Using a parameterized test avoids duplicating the same test logic three times.

---

# Test 2: Calculate Subtotal with Items

Two items are added:

```java
cartItems.add("1", 2);
cartItems.add("2", 1);
```

The calculation is:

```text
Product 1:
2 × $100 = $200

Product 2:
1 × $200 = $200

Subtotal:
$200 + $200 = $400
```

The test verifies:

```java
assertEquals(400.0, subtotal, 0.001);
```

---

# Test 3: Ignore Non-Existent Products

The test adds an item with an ID that does not exist:

```java
cartItems.add("999", 1);
```

It also adds a valid product:

```java
cartItems.add("1", 1);
```

The calculator should ignore product `999` because it cannot find a corresponding `Product`.

Therefore:

```text
Product 999 → ignored

Product 1:
1 × $100 = $100

Subtotal = $100
```

The test verifies:

```java
assertEquals(100.0, subtotal, 0.001);
```

This confirms that missing products do not cause an exception or contribute to the subtotal.

# Final `PriceCalculatorTest.java`

```java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

import static org.junit.jupiter.api.Assertions.*;

import java.util.ArrayList;
import java.util.List;

public class PriceCalculatorTest {

    private PriceCalculator calculator;
    private List<Product> products;
    private Customer customer;
    private CartItemCollection cartItems;

    @BeforeEach
    public void setUp() {
        customer = new Customer();
        customer.setPriceLevel(PriceLevel.REGULAR);

        cartItems = new CartItemCollection();
        products = new ArrayList<>();

        Product product1 = new Product();
        product1.setId("1");
        product1.setPrice(100);
        products.add(product1);

        Product product2 = new Product();
        product2.setId("2");
        product2.setPrice(200);
        products.add(product2);

        calculator = new PriceCalculator(customer, cartItems);
    }

    @ParameterizedTest
    @ValueSource(doubles = {100, 200, 300})
    public void testCalculateTaxReturnsCorrectValue(double subtotal) {
        double tax = calculator.calculateTax(subtotal);

        // Assuming a standard 10% tax rate based on typical configurations
        assertEquals(subtotal * 0.1, tax, 0.001);
    }

    @Test
    public void testCalculateSubtotalWithItemsReturnsCorrectValue() {
        cartItems.add("1", 2); // 2 * 100 = 200
        cartItems.add("2", 1); // 1 * 200 = 200

        double subtotal = calculator.calculateSubtotal(products);

        assertEquals(400.0, subtotal, 0.001);
    }

    @Test
    public void testCalculateSubtotalIgnoresNonExistentProducts() {
        cartItems.add("999", 1); // Non-existent product ID
        cartItems.add("1", 1);   // 1 * 100 = 100

        double subtotal = calculator.calculateSubtotal(products);

        assertEquals(100.0, subtotal, 0.001);
    }
}
```

# Unit Tests vs. Integration Through `ShoppingCart`

There are now two useful testing levels.

### Unit-level testing

Test each calculator directly:

```java
calculator.calculateDiscount(100);
```

or:

```java
calculator.calculateSubtotal(products);
```

These tests focus on one class.

### Higher-level testing

Test the overall behavior through:

```java
cart.getOrderSummary(products);
```

These tests verify that the different components work together correctly.

So extraction does **not** mean removing higher-level tests.

Instead:

```text
Unit Tests
   ↓
Test individual components

Integration / Higher-Level Tests
   ↓
Test components working together
```

Both provide value.

---

# Why `@BeforeEach` Matters

Both test classes use:

```java
@BeforeEach
public void setUp()
```

This creates a clean test environment before every test.

For `DiscountCalculatorTest`:

```text
Before test
    ↓
new DiscountCalculator()
    ↓
Run test
```

For `PriceCalculatorTest`:

```text
Before test
    ↓
Create Customer
Create CartItemCollection
Create Products
Create PriceCalculator
    ↓
Run test
```

This prevents state leakage between tests.

---

# Why Parameterized Tests Are Useful Here

Parameterized tests are useful when the **same behavior** needs to be verified with multiple inputs.

Instead of:

```java
@Test
void testSave10() { ... }

@Test
void testSummer20() { ... }

@Test
void testVip15() { ... }
```

we can write:

```java
@ParameterizedTest
@ValueSource(strings = {"SAVE10", "SUMMER20", "VIP15"})
```

Similarly, instead of three separate tax tests:

```java
100 → 10
200 → 20
300 → 30
```

we use:

```java
@ValueSource(doubles = {100, 200, 300})
```

This follows the **DRY principle** and makes the test intent clearer.

---

# Floating-Point Assertions

The tests use:

```java
assertEquals(expected, actual, 0.001);
```

rather than:

```java
assertEquals(expected, actual);
```

because Java `double` calculations can have small floating-point precision differences.

For example, mathematically:

```text
0.1 × 3 = 0.3
```

but floating-point representation may produce a value extremely close to, rather than exactly equal to, `0.3`.

The third argument defines an acceptable tolerance:

```java
0.001
```

Meaning the actual value can differ from the expected value by a very small amount.

# Important Testing Principle

A good unit test should focus on **one responsibility**.

For example:

```text
DiscountCalculatorTest
        ↓
Discount behavior
```

rather than:

```text
DiscountCalculatorTest
        ↓
Discount + shipping + loyalty + pricing
```

The smaller the responsibility, the easier it is to understand what a failing test means.

# Potential Further Refactoring

The task encourages exploring the codebase for additional improvements.

Some possible areas to investigate are:

### 1. Dependency Injection

`ShoppingCart` currently creates its calculators itself:

```java
this.discountCalculator = new DiscountCalculator();
```

and:

```java
this.priceCalculator = new PriceCalculator(customer, items);
```

Dependency injection could make these dependencies easier to replace and test.

### 2. Product Lookup

Both `PriceCalculator` and other calculators repeatedly search products:

```java
products.stream()
    .filter(p -> p.getId().equals(...))
    .findFirst()
```

A dedicated product lookup/repository abstraction could potentially reduce duplication.

### 3. Money Representation

The code uses:

```java
double
```

for monetary calculations.

A production system may consider `BigDecimal` to avoid floating-point precision issues with financial values.

### 4. Discount Configuration

The discount rates are currently hard-coded:

```java
discountRates.put("SAVE10", 0.1);
```

A larger application might load these from configuration or another data source.

These are **possible future refactorings**, not requirements of the current exercise.

# Key Takeaways

1. **Extract Class makes unit testing easier** because responsibilities become isolated.
2. `DiscountCalculatorTest` focuses only on discount behavior.
3. `PriceCalculatorTest` focuses only on pricing and tax behavior.
4. `@BeforeEach` provides a fresh test fixture for every test.
5. `@ParameterizedTest` avoids duplicating tests with different inputs.
6. `assertDoesNotThrow()` verifies successful operations.
7. `assertThrows()` verifies expected error behavior.
8. Floating-point calculations should generally use a tolerance when asserting `double` values.
9. Extracted classes can have their own dedicated test suites.
10. Higher-level `ShoppingCart` tests are still valuable because they verify component integration.
11. **Extract Class improves both design and testability.**

> **Core principle:** Smaller, cohesive classes are easier to understand, maintain, refactor, and test independently.
