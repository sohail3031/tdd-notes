# Task Objective

The `ShoppingCart` class has accumulated multiple responsibilities. In this task, the focus is on extracting the **price calculation logic** into a dedicated `PriceCalculator` class.

The two methods targeted for extraction are:

- `calculateSubtotal()`    
- `calculateTax()`

The goal is to:

- Move pricing-related logic out of `ShoppingCart`
- Create a dedicated `PriceCalculator`
- Reduce the responsibilities of `ShoppingCart`
- Improve cohesion
- Follow the **Single Responsibility Principle (SRP)**
- Preserve the existing behavior of the application

The existing tests should continue to pass after the refactoring.

---

# Problem Before Refactoring

`ShoppingCart` was responsible for many different areas:

```text
ShoppingCart
├── Cart item management
├── Subtotal calculation
├── Tax calculation
├── Discount codes
├── Discount calculation
├── Shipping calculation
├── Loyalty points
└── Order summary
```

The pricing logic was embedded directly inside `ShoppingCart`:

```java
public double calculateSubtotal(List<Product> products) {
    // pricing logic
}

public double calculateTax(double subtotal) {
    // tax logic
}
```

This makes `ShoppingCart` responsible for both **managing the cart** and **calculating prices**.

---

# Refactoring Strategy

The pricing responsibilities are extracted into:

```text
PriceCalculator
```

The resulting structure becomes:

```text
ShoppingCart
    │
    ├── CartItemCollection
    │
    └── PriceCalculator
```

`ShoppingCart` will delegate price calculations:

```text
ShoppingCart
      │
      │ delegates
      ▼
PriceCalculator
      │
      ├── calculateSubtotal()
      └── calculateTax()
```

---

# Step 1: Create `PriceCalculator`

The new class owns the tax rate:

```java
private final double taxRate;
```

and receives it through the constructor:

```java
public PriceCalculator(double taxRate) {
    this.taxRate = taxRate;
}
```

This allows the calculator to calculate tax without depending on `ShoppingCart`.

---

# Step 2: Move `calculateSubtotal()`

The original subtotal calculation depended on three pieces of information:

1. Cart items
2. Products
3. Customer price level

Therefore, the extracted method receives these as parameters:

```java
public double calculateSubtotal(
    Collection<CartItem> items,
    List<Product> products,
    PriceLevel priceLevel
)
```

The implementation is:

```java
public double calculateSubtotal(
        Collection<CartItem> items,
        List<Product> products,
        PriceLevel priceLevel) {

    double subtotal = 0;

    for (CartItem entry : items) {
        Product product = products.stream()
                .filter(p -> p.getId().equals(entry.getProductId()))
                .findFirst()
                .orElse(null);

        if (product != null) {
            double price = product.getPrice();

            if (priceLevel == PriceLevel.PREMIUM) {
                price *= 0.9; // 10% off
            } else if (priceLevel == PriceLevel.VIP) {
                price *= 0.85; // 15% off
            }

            subtotal += price * entry.getQuantity();
        }
    }

    return subtotal;
}
```

### Why pass `PriceLevel`?

Previously, the calculation accessed:

```java
customer.getPriceLevel()
```

After extraction, `PriceCalculator` should not need to know about the entire `Customer` object.

Instead, it receives only the information required for the calculation:

```java
PriceLevel priceLevel
```

This reduces coupling.

---

# Step 3: Move `calculateTax()`

The original method was:

```java
public double calculateTax(double subtotal) {
    return subtotal * taxRate;
}
```

It is moved directly into `PriceCalculator`:

```java
public double calculateTax(double subtotal) {
    return subtotal * taxRate;
}
```

The tax rate is now owned by `PriceCalculator`.

# Final `PriceCalculator.java`

```java
import java.util.Collection;
import java.util.List;

public class PriceCalculator {

    private final double taxRate;

    public PriceCalculator(double taxRate) {
        this.taxRate = taxRate;
    }

    public double calculateSubtotal(
            Collection<CartItem> items,
            List<Product> products,
            PriceLevel priceLevel) {

        double subtotal = 0;

        for (CartItem entry : items) {
            Product product = products.stream()
                    .filter(p -> p.getId().equals(entry.getProductId()))
                    .findFirst()
                    .orElse(null);

            if (product != null) {
                double price = product.getPrice();

                if (priceLevel == PriceLevel.PREMIUM) {
                    price *= 0.9; // 10% off
                } else if (priceLevel == PriceLevel.VIP) {
                    price *= 0.85; // 15% off
                }

                subtotal += price * entry.getQuantity();
            }
        }

        return subtotal;
    }

    public double calculateTax(double subtotal) {
        return subtotal * taxRate;
    }
}
```

# Step 4: Update `ShoppingCart`

`ShoppingCart` now creates a `PriceCalculator`:

```java
private final PriceCalculator priceCalculator =
        new PriceCalculator(0.1);
```

The original pricing implementation is removed.

Instead, `ShoppingCart` delegates to the calculator.

### `calculateSubtotal()`

```java
public double calculateSubtotal(List<Product> products) {
    return priceCalculator.calculateSubtotal(
            items.getAll(),
            products,
            customer.getPriceLevel()
    );
}
```

### `calculateTax()`

```java
public double calculateTax(double subtotal) {
    return priceCalculator.calculateTax(subtotal);
}
```

This is an example of **delegation**.

`ShoppingCart` still exposes the same public methods, but the actual calculation is performed by `PriceCalculator`.

---

# Why Keep `calculateSubtotal()` on `ShoppingCart`?

The public API does not need to change.

Existing code can still do:

```java
cart.calculateSubtotal(products);
```

The caller does not need to know that `PriceCalculator` exists.

Internally:

```text
cart.calculateSubtotal(products)
            │
            ▼
    PriceCalculator
            │
            ▼
    calculateSubtotal(...)
```

This preserves the existing API while improving the internal design.

---

# Why Pass `items.getAll()`?

`ShoppingCart` owns the `CartItemCollection`:

```java
private final CartItemCollection items =
        new CartItemCollection();
```

The calculator needs the cart items to calculate the subtotal.

Instead of giving `PriceCalculator` the entire `ShoppingCart`, we pass only the required data:

```java
items.getAll()
```

This follows a useful design principle:

> **Pass the data a class needs rather than giving it unnecessary access to another object's entire state.**

# Responsibility Distribution

|Class|Responsibility|
|---|---|
|`ShoppingCart`|Coordinates cart operations|
|`CartItemCollection`|Manages cart items|
|`CartItem`|Represents an item and quantity|
|`PriceCalculator`|Calculates subtotal and tax|
|`Product`|Stores product information|
|`Customer`|Stores customer information|

This results in better separation of responsibilities.

# Dependency Direction

The new relationship is:

```text
ShoppingCart
      │
      ├──────────────► CartItemCollection
      │
      └──────────────► PriceCalculator
```

`PriceCalculator` does **not** need to know about `ShoppingCart`.

It only receives the information it needs:

```text
CartItem collection
Product list
Price level
Subtotal
Tax rate
```

This keeps the extracted class relatively independent.

---

# Single Responsibility Principle

The refactoring improves SRP because `PriceCalculator` now has a focused responsibility:

> **Calculate prices and taxes.**

`ShoppingCart` remains responsible for coordinating the overall shopping-cart behavior rather than implementing every calculation itself.

A useful mental model is:

```text
One class = one primary reason to change
```

For example:

- Change tax calculation → potentially modify `PriceCalculator`
- Change cart item storage → modify `CartItemCollection`
- Change discount-code behavior → modify `ShoppingCart`
- Change shipping rules → potentially modify shipping-related code

This makes future changes easier to isolate.


calculates the subtotal directly inside `ShoppingCart`.

After:


```text
Before:

Caller
  ↓
ShoppingCart
  ↓

  ↓
Result


After:

Caller
  ↓
ShoppingCart
  ↓
PriceCalculator
  ↓
Calculation
  ↓
```

# Important Design Improvement

The extracted calculator receives:

```java
PriceLevel priceLevel
```

instead of:

```java
Customer customer
```

This is an example of reducing unnecessary coupling.

The calculator only needs to know:

```java
customer.getPriceLevel()
```

Therefore, passing the entire `Customer` object would give it more information than necessary.

Instead:

```java
customer.getPriceLevel()
```

is evaluated by `ShoppingCart`, and only the result is passed:

```java
priceCalculator.calculateSubtotal(
    items.getAll(),
    products,
    customer.getPriceLevel()
);
```

This follows the principle of **providing only the information required by the operation**.

# Refactoring Pattern

This task demonstrates **Extract Class** combined with **Delegation**.

### Extract Class

Move a cohesive group of methods and their supporting data into a new class.

```text
ShoppingCart
     ↓
PriceCalculator
```

### Delegation

The original class keeps its public API but delegates the work:

```java
public double calculateTax(double subtotal) {
    return priceCalculator.calculateTax(subtotal);
}
```

This allows existing callers to continue using `ShoppingCart`.

# Refactoring Checklist

-  Identify pricing-related methods.
-  Create `PriceCalculator`.
-  Move `calculateSubtotal()`.
-  Move `calculateTax()`.
-  Move the tax rate to `PriceCalculator`.
-  Pass only required information to the calculator.
-  Add `PriceCalculator` to `ShoppingCart`.
-  Replace the original implementation with delegation.
-  Keep the existing `ShoppingCart` API.
-  Preserve existing behavior.
-  Run the existing tests.

---

# Key Takeaways

- `ShoppingCart` was becoming responsible for too many operations.
- Price calculation is a cohesive responsibility that can be extracted.
- `PriceCalculator` now owns subtotal and tax calculations.
- `ShoppingCart` delegates pricing operations to `PriceCalculator`.
- The tax rate is now owned by `PriceCalculator`.
- Passing `PriceLevel` instead of the entire `Customer` reduces coupling.
- The existing `ShoppingCart` API remains unchanged.
- Existing tests provide a safety net during refactoring.
- The goal of refactoring is to improve **structure and maintainability without changing behavior**.

> **Core principle:** Extract cohesive responsibilities into focused classes, pass only the information they need, and use delegation to preserve the existing public API.
